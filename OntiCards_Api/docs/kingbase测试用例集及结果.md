# KingBase 测试用例集及结果（检查修正版）

## 复核说明

本文档依据给定的建表语句和初始化数据，对 8 个测试用例的 SQL、预期条数、预期记录及金额计算进行了逐项静态复核。

复核基准如下：

- `products` 表初始化为 10 条记录；
- `orders` 表初始化为 12 条记录；
- 测试表在插入数据前为空；
- `SERIAL` 自增序列从 1 开始，因此商品 ID 为 1～10、订单 ID 为 1～12；
- 本文档的“通过”表示 SQL 逻辑及预期数据静态核算一致，不代表已经连接实际 KingBase 数据库执行。

## 本次检查与修正摘要

| 问题 | 原文情况 | 检查结论 | 修正内容 |
|------|----------|----------|----------|
| 问题1 | 预期 8 条在售商品 | 正确 | 增加 `ORDER BY product_id`，保证结果顺序稳定 |
| 问题2 | 预期 3 条库存不超过 50 的商品 | 错误 | 应为 4 条，补充库存为 0 的 `USB集线器` |
| 问题3 | 各类别商品数量为 6、2、2 | 正确 | 增加排序条件，避免聚合结果顺序不确定 |
| 问题4 | 价格最高的 3 个商品 | 正确 | 增加商品 ID 作为并列价格的次级排序条件 |
| 问题5 | 深圳仓库存总金额为 46245.00 | 正确 | 无数值修正 |
| 问题6 | 12 条订单均能关联到商品 | 正确 | 增加 `ORDER BY o.order_id`，保证结果顺序稳定 |

## 测试数据准备

### 建表语句

```sql
-- 创建商品表
CREATE TABLE IF NOT EXISTS products (
    product_id SERIAL PRIMARY KEY,                     -- 商品ID（主键）
    product_name VARCHAR(100) NOT NULL,                -- 商品名称
    category VARCHAR(50),                              -- 商品类别
    price DECIMAL(10, 2),                              -- 商品单价
    stock_quantity INTEGER DEFAULT 0,                  -- 库存数量
    warehouse VARCHAR(50),                             -- 所属仓库
    status VARCHAR(20) DEFAULT '在售'                  -- 商品状态（在售/下架/缺货）
);

-- 创建订单表
CREATE TABLE IF NOT EXISTS orders (
    order_id SERIAL PRIMARY KEY,                       -- 订单ID（主键）
    order_no VARCHAR(50) NOT NULL UNIQUE,              -- 订单编号
    customer_name VARCHAR(100),                        -- 客户姓名
    product_id INTEGER REFERENCES products(product_id),-- 关联商品ID
    quantity INTEGER NOT NULL,                         -- 订购数量
    total_amount DECIMAL(10, 2),                       -- 订单总金额
    order_status VARCHAR(20) DEFAULT '待支付'          -- 订单状态（待支付/已支付/已完成/已取消）
);
```

### 重复执行前清理数据

为保证测试用例可以重复执行，并确保自增 ID 每次都从 1 开始，建议在初始化数据前执行：

```sql
TRUNCATE TABLE orders, products RESTART IDENTITY CASCADE;
```

> 若当前测试库中还有其他表通过外键关联 `products` 或 `orders`，执行前应先确认 `CASCADE` 的影响范围。仅建议在独立测试环境中使用。

### 问题7：查询已完成订单的总金额

原文中的 SQL 返回的是 6 条已完成订单明细，并没有计算“总金额”。为使 SQL 与测试问题一致，修正为聚合查询。

**修正后 SQL：**

```sql
SELECT SUM(o.total_amount) AS completed_total_amount
FROM orders o
JOIN products p ON o.product_id = p.product_id
WHERE o.order_status = '已完成';
```

**预期结果：1 条记录**

| completed_total_amount |
|------------------------|
| 1837.00 |

**计算明细：**

| order_no | customer_name | product_name | total_amount |
|----------|---------------|--------------|--------------|
| ORD001 | 张三 | 蓝牙耳机 | 398.00 |
| ORD002 | 李四 | 无线鼠标 | 267.00 |
| ORD004 | 赵六 | 移动硬盘 | 399.00 |
| ORD008 | 周九 | 游戏手柄 | 398.00 |
| ORD010 | 郑十一 | 充电宝 | 258.00 |
| ORD011 | 张三 | Type-C数据线 | 117.00 |
| **合计** |  |  | **1837.00** |

计算过程：

```text
398.00 + 267.00 + 399.00 + 398.00 + 258.00 + 117.00
= 1837.00
```

**复核结论：✅ 修正后正确**

> 若测试目标本来是“查询已完成订单明细”，则可保留原 SQL，并把问题标题改为“查询所有已完成订单明细”，此时正确预期仍为 6 条记录。

### 问题8：统计每个客户的全部订单金额

**SQL：**

```sql
SELECT o.customer_name,
       SUM(o.total_amount) AS total_order_amount
FROM orders o
GROUP BY o.customer_name
ORDER BY total_order_amount DESC, o.customer_name ASC;
```

**预期结果：9 条记录**

| customer_name | total_order_amount |
|---------------|--------------------|
| 张三 | 1114.00 |
| 李四 | 466.00 |
| 赵六 | 399.00 |
| 周九 | 398.00 |
| 郑十一 | 258.00 |
| 孙八 | 199.00 |
| 钱七 | 195.00 |
| 王五 | 129.00 |
| 吴十 | 89.00 |

**金额计算明细：**

- 张三：398.00 + 599.00 + 117.00 = **1114.00**
- 李四：267.00 + 199.00 = **466.00**
- 赵六：399.00
- 周九：398.00
- 郑十一：258.00
- 孙八：199.00
- 钱七：195.00
- 王五：129.00

> 当前 SQL 汇总所有订单状态，因此会包含“待支付”和“已取消”订单。若需要统计实际成交金额，应增加类似 `WHERE order_status IN ('已支付', '已完成')` 的过滤条件，并重新计算预期结果。

## 执行验收注意事项

1. **不要依赖未排序查询的自然返回顺序。** 数据库在没有 `ORDER BY` 时不保证记录顺序，因此本修正版为需要逐行比对的查询补充了排序条件。
2. **确保测试数据环境干净。** 若重复执行初始化脚本而不清理数据，商品记录会重复，订单插入还会因 `order_no` 唯一约束而失败。
3. **自增 ID 必须与测试数据一致。** 本文档中的订单关联依赖商品 ID 为 1～10，因此建议在测试前重置自增序列。
4. **金额显示格式可能受客户端影响。** 数据库客户端可能显示为 `1837.00`、`1837.0000` 或不带尾随零，但数值应保持一致。
5. **问题8的统计口径必须明确。** 当前口径是全部订单金额，不等同于实际支付金额或已完成交易金额。
