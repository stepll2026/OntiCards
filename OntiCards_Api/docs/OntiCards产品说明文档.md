## 一、产品概述

### 1.1 产品背景与市场需求

在数字化转型进程中,企业积累了大量业务数据,这些数据分散在不同的业务系统和数据库中。然而,数据的价值挖掘面临诸多挑战:

**技术门槛高**
- 业务人员需要依赖技术团队编写SQL查询,响应周期长达数小时甚至数天
- 数据分析师需要花费大量时间学习和记忆复杂的表结构和字段命名
- 临时性数据需求往往因为技术资源不足而被延迟或放弃

**数据孤岛严重**
- 订单、库存、财务、客户等数据分散在不同系统中
- 跨系统数据整合需要手工导出、Excel拼表,效率低且易出错
- 缺乏统一的数据查询入口,业务决策缺少全局视角

**维护成本高**
- 数据库结构变更后,相关查询脚本和报表需要批量修改
- 缺少统一的数据字典,字段含义依赖口口相传
- 数据质量问题难以及时发现和追溯

OntiCards正是为解决这些痛点而设计的智能数据查询系统,通过自然语言处理和语义理解技术,让数据查询变得像日常对话一样简单。

### 1.2 产品定位

OntiCards是一个**企业级智能数据库连接与自然语言查询平台**,同时具备强大的数据治理能力,定位于:

- **数据查询的统一入口**: 连接企业内多种类型的数据库,提供统一的查询界面
- **业务人员的数据助手**: 零SQL门槛,用自然语言即可完成复杂查询
- **数据团队的效率工具**: 自动化数据卡片生成,减少重复性支持工作
- **数据治理的质检中心**: 内置数据质检规则库,支持灵活的质量检测和报告生成
- **决策支持的基础设施**: 快速响应临时数据需求,支持敏捷决策

**两大核心能力:**

| 能力模块 | 定位 | 核心功能 |
|---------|------|---------|
| 智能查询 | 数据价值挖掘 | 自然语言转SQL查询、跨数据源融合 |
| 数据治理 | 数据质量保障 | 规则库管理、多模式规则创建、质检执行、报告生成 |

### 1.3 核心价值主张

**降低使用门槛**
- 用自然语言提问,无需学习SQL语法
- 用自然语言配置质检规则,业务人员也能管理数据质量
- 自动理解业务术语,无需记忆字段名称
- 智能容错机制,提问不精确也能得到有价值的结果

**提升查询效率**
- 简单查询从30分钟缩短至10秒
- 跨系统查询从1-2天缩短至30秒
- 业务人员自助查询,减少60%的技术支持需求
- 批量规则执行,一键生成质检报告

**打破数据孤岛**
- 支持MySQL、Oracle、PostgreSQL、SQL Server、Trino、**电科金仓（KingBase，原名：人大金仓）**、**OceanBase（MySQL 租户模式）**、**达梦（DMBase）** 等多种数据库
- 一次提问可同时查询多个数据源
- 自动完成结果融合,支持交集、并集、汇总等多种策略

**保障数据安全**
- 严格的只读访问控制,禁止数据修改操作
- 用户级数据源隔离,确保数据访问权限
- 完整的查询审计日志,满足合规要求

**统一业务语言**
- 建立企业级业务术语标准库,消除业务歧义
- 支持术语同义词映射,不同叫法都能准确识别
- 业务术语自动展开为字段条件,提升查询准确率
- 跨部门使用统一术语,提升数据共享效率

**数据质量保障**
- 灵活的数据质检规则库,满足多样化检测需求
- 多模式规则创建:手动精确配置/AI智能理解/模板快速复用
- 量化质量评分和等级划分,直观了解数据健康状况
- 自动生成质检报告和AI改进建议,降低分析门槛

- **高可用性**: 支持Docker部署,可水平扩展
- **质检独立**: 数据治理质检模块独立运行,与查询模块解耦

## 二、核心功能详解

### 2.1 多数据源统一管理

OntiCards提供了完善的数据源管理能力,支持企业内多种类型数据库的统一接入和管理。

**支持的数据库类型**

| 数据库类型 | 版本支持 | 连接方式 | 典型应用场景 |
|-----------|---------|---------|-------------|
| MySQL | 5.7+ | JOntiCards/原生驱动 | 业务系统、电商平台 |
| PostgreSQL | 9.6+ | JOntiCards/原生驱动 | 数据仓库、分析系统 |
| Oracle | 11g+ | JOntiCards | ERP系统、核心业务系统 |
| SQL Server | 2012+ | JOntiCards | 财务系统、CRM系统 |
| SQLite | 3.x | 原生驱动 | 轻量级应用、本地数据 |
| Trino | 最新版 | JOntiCards | 大数据查询、数据湖 |
| **电科金仓（KingBase）** | 最新版 | JOntiCards | 国产数据库，核心业务国产化 |
| **OceanBase（MySQL 租户模式）** | 3.x/4.x | JOntiCards | 国产分布式数据库，金融/电信核心业务 |
| **达梦（DMBase）** | 最新版 | JOntiCards | 国产数据库，武汉达梦出品 |

**核心功能**

1. **数据源添加与配置**
   - 填写数据库连接信息(主机、端口、数据库名、用户名、密码)
   - 支持自定义数据源别名,便于业务识别
   - 支持Schema指定,精确控制访问范围
   - 连接信息加密存储,保障安全性

2. **连接测试与验证**
   - 添加数据源时自动进行连接测试
   - 验证连接参数的正确性和数据库的可访问性
   - 提供详细的错误提示,帮助快速定位问题

3. **表结构自动抽取**
   - 连接成功后自动启动表结构抽取任务
   - 异步处理机制,不阻塞用户操作
   - 支持增量抽取,只处理变更的表结构
   - 使用MD5指纹识别结构变化,避免重复处理

4. **数据源刷新与更新**
   - 支持手动刷新数据源,同步最新的表结构
   - 自动识别新增表、删除表、字段变更
   - 保留历史版本记录,支持变更追溯
   - 刷新过程可随时取消,灵活控制

5. **数据源健康监控**
   - 定期检查数据源连接状态
   - 监控查询响应时间和成功率
   - 异常情况及时告警
   - 提供健康度评分和优化建议

**用户价值**
- 一个界面管理所有数据源,避免多系统切换
- 自动化的表结构维护,减少人工成本
- 增量更新机制,提升刷新效率
- 完善的监控能力,保障系统稳定性

### 2.2 智能数据卡片系统

数据卡片是OntiCards的核心创新,它为每张数据表生成一份"业务说明书",让系统能够理解表的业务含义,从而实现自然语言查询。

**数据卡片的内容结构**

```
数据卡片 = {
  基础信息: {
    表名、数据源、Schema、创建时间
  },
  业务语义: {
    表的业务用途描述
    业务场景说明
    业务关键词和别名
  },
  字段信息: {
    字段名、数据类型、是否可空
    字段业务含义
    典型值示例
    取值范围说明
  },
  关系信息: {
    主键字段
    外键关系
    常见关联表
  },
  查询特征: {
    常见查询场景
    典型查询条件
    聚合统计维度
  }
}
```

**数据卡片生成流程**

1. **表结构抽取**
   - 从数据库元数据中获取表和字段的基础信息
   - 提取数据类型、约束条件、索引信息
   - 识别主键、外键等关系信息

2. **数据采样分析**
   - 智能采样：从数据库采样每个字段的典型数据值，便于后续识别字段特征
   - 数据特征分析：分析取值范围、识别枚举类型、日期格式、数值分布等
   - 多数据库适配：支持 MySQL、PostgreSQL、Oracle、SQL Server、KingBaseES、达梦、OceanBase 等多种数据库类型

3. **敏感字段智能识别与数据脱敏**（已实现，业界领先的安全设计）

   **设计理念**：在数据进入大模型之前先通过预过滤机制识别明显敏感字段，避免将敏感数据暴露给大模型导致的风险，同时由大模型兜底处理"字段名不敏感但实际数据敏感"等复杂场景，确保安全性的同时不影响准确度。

   **三层预过滤架构**：

   | 层级 | 置信度 | 处理方式 | 示例字段类型 |
   |------|--------|----------|----------|
   | 第一层 | 极高 | 直接识别为敏感，不送大模型 | 密码、密钥、身份证、银行卡、令牌等 |
   | 第二层 | 高 | 直接识别为敏感，不送大模型 | 手机号、邮箱、薪资、生物特征、地址、位置、医疗记录等 |
   | 第三层 | 需要大模型二次判断 | 返回采样数据，送大模型分析 | 姓名、生日、性别、民族、社交账号等 |

   **第一层 - 极高置信度敏感字段**（几乎不会误判的字段名，直接识别）：
   - 认证密码类：密码、登录密码、密码哈希等
   - 密钥令牌类：密钥、密钥串、应用密钥、私钥、令牌、访问令牌、刷新令牌、API 密钥、认证密钥、凭证、JWT 等
   - 身份证件类：身份证号、身份证件号、社保证号、证件号等
   - 银行卡号类：银行卡号、卡号、信用卡号、借记卡号、账号等
   - 加密相关：加密密钥、加密盐值、密码哈希等

   **第二层 - 高置信度敏感字段**（误判概率极低的字段名，直接识别）：
   - 联系方式类：手机号、电话号码等
   - 邮箱地址类：邮箱、邮箱地址等
   - 财务信息类：薪资、奖金、佣金、收入、余额、税费、信用额度、负债、贷款等
   - 生物特征类：人脸数据、指纹数据、虹膜、声纹等
   - 地址位置类：详细地址、地理位置、GPS 坐标、经纬度、IP 地址等
   - 医疗健康类：病历、诊断、处方等

   **第三层 - 需要大模型二次判断的字段**（避免误判，送大模型结合数据内容判断）：
   - 标识信息类：姓名、真实姓名（在某些业务中"姓名"可能是产品名或用户名）
   - 个人特征类：生日、出生日期、年龄、出生年份、性别等
   - 通用身份类：民族、国籍、证件类型等
   - 社交账号类：QQ、微信、微博、社交账号等

   **整体处理流程**：
   ```
   采样数据 → 预过滤快速识别明显的敏感字段 → 高/中置信度敏感字段直接脱敏 → 剩余疑似敏感字段送大模型智能兜底
   ```

   **安全保障机制**：
   - **预过滤优先**：明显敏感的字段在预过滤阶段就被识别，不需要发送给大模型，从源头减少数据暴露
   - **大模型智能兜底**：对于预过滤无法准确判断的字段（如"姓名"字段在不同业务中有不同含义），大模型会结合字段名和数据格式综合判断
   - **零数据回显**：识别为敏感的字段不返回实际数据，仅返回数据条数和识别原因
   - **数据格式智能识别**：大模型会基于数据模式识别（如手机号格式、身份证格式、邮箱格式、银行卡号格式）
   - **可配置化**：所有预过滤规则支持灵活调整，便于根据业务场景定制

4. **语义补全**
   - 利用大语言模型分析字段名称和样本值
   - 自动生成字段的业务含义描述
   - 推断表的业务用途和使用场景
   - 提取业务关键词和同义词
   - **敏感字段安全处理**：对识别为敏感的字段，强化大模型提示，确保不暴露真实数据

5. **向量化索引**
   - 将数据卡片的文本内容转换为向量
   - 存储到 Weaviate 向量数据库
   - 建立语义检索索引，支持快速召回

6. **持续优化**
   - 根据用户查询反馈优化卡片内容
   - 定期更新典型值样本
   - 补充新发现的业务关键词

**采样机制对数据卡片质量的增强**

- **枚举值识别**：基于实际数据值，自动识别枚举型字段并标注取值含义
- **数据分布特征**：数值型字段提供取值范围和统计信息，帮助理解字段含义
- **日期范围分析**：日期型字段提供真实数据范围，辅助判断业务时间跨度
- **典型示例展示**：文本型字段展示代表性示例，便于语义检索匹配

**敏感字段处理对数据安全的保障**

- **预过滤优先**：避免将明显敏感的数据发送给大模型，减少数据暴露风险
- **大模型智能兜底**：处理"字段名不敏感但数据敏感"的复杂场景（如名称字段包含真实姓名）
- **零数据回显**：敏感字段不返回真实值，仅返回数据条数和识别原因
- **多层防护**：第一层、第二层预过滤快速拦截，第三层大模型兜底判断，构建纵深防御体系

**数据卡片的应用场景**

| 应用场景 | 具体作用 | 效果 |
|---------|---------|------|
| 语义检索 | 根据用户问题召回相关的表 | 准确率>85% |
| SQL生成 | 提供表结构和字段含义给大模型 | 减少字段错误 |
| 字段映射 | 将业务术语映射到实际字段名 | 支持自然语言 |
| 安全控制 | 定义可访问的表和字段白名单 | 防止越权访问 |
| 数据治理 | 提供统一的数据字典 | 提升数据质量 |

**用户价值**
- 无需记忆字段名,用业务语言即可查询
- 新接入的数据库快速可用,无需人工编写文档
- 数据库结构变更后自动更新,减少维护成本
- 为数据治理提供基础设施

### 2.3 数据盘点系统

OntiCards提供了两种数据盘点模式,帮助企业快速建立数据资产目录和表间关系,为智能查询提供基础支撑。

#### 2.3.1 定向盘点（Target Inventory）

定向盘点是一种精细化的数据治理方式,适用于需要人工审核和确认的场景。

**核心流程**

```
用户选择表 → 字段注释推荐 → 用户确认 → 表关系推断 → 用户确认 → 生成关系卡片 → 入库
```

**功能特点**

1. **智能字段注释推荐**
   - **基于字段画像技术分析字段值域特征**
     - 从数据库采样每个字段的典型数据值
     - 分析数据分布特征和取值范围
     - 识别枚举类型和分类字段
   - **分层敏感字段识别与脱敏**（与数据卡片生成共享同一套安全保障机制）
     - 第一层（极高置信度）：密码、密钥、身份证、银行卡等 → 直接识别，不送大模型
     - 第二层（高置信度）：手机、邮箱、薪资、生物特征等 → 直接识别，不送大模型
     - 第三层（中性字段）：姓名、生日、性别等 → 送大模型二次判断
     - 确保敏感数据在送入大模型前已被过滤，避免数据泄露风险
   - **从参考表和数据字典中召回候选注释**
   - **使用大模型进行语义理解和裁决**
     - 对非敏感字段，结合字段名、采样数据、候选注释，生成准确的业务注释
   - **支持用户确认和修改**
     - 用户可对大模型推荐的注释进行人工修订
     - 系统记录用户的修改偏好，用于后续推荐优化

2. **表关系推断**
   - 基于字段映射分析表间关系
   - 识别主外键关系、语义关联等
   - 计算关系置信度和基数（1:1、1:N、N:M）
   - 生成JOIN条件建议

3. **关系卡片生成**
   - 将确认的表关系结构化存储
   - 包含JOIN条件、关系类型、置信度等信息
   - 同时入库到数据库和向量库
   - 支持语义检索和精确查询

**适用场景**
- 核心业务表的精细化治理
- 需要人工审核确认的场景
- 数据质量要求高的场景
- 逐步推进的数据治理项目

**核心流程**

```
选择数据源 → 自动扫描所有表 → 批量关系发现 → 生成关系卡片 → 入库
```

2. **多数据源支持**

3. **智能关系分类**
   - 识别关系类型（主外键、语义关联等）

**适用场景**

#### 2.3.3 关系卡片体系

关系卡片是盘点系统的核心输出,它为表间关系提供了结构化的描述,是实现智能多表查询的关键。

**关系卡片内容结构**

关系卡片包含以下核心信息：

| 组成部分 | 说明 |
|---------|------|
| **基础信息** | 源表的表名、所属数据源标识 |
| **关联关系列表** | 该表与其他表的所有关联关系 |
| **关联目标** | 目标表的表名、所属数据源 |
| **关联条件** | 关联字段的对应关系（如源表customer_id = 目标表id） |
| **关系类型** | 关系类型（主外键foreign_key、语义关联等） |
| **关系强度** | 关系置信度（0-1之间的数值，越接近1表示关系越确定） |
| **基数类型** | 表示关联的数量关系（如N:1表示多条源记录对应1条目标记录） |
| **跨源标识** | 标识是否为跨数据源的关联关系 |
| **涉及数据源** | 列出所有涉及的外部数据源ID |

**关系卡片的应用**

| 应用场景 | 具体作用 | 效果 |
|---------|---------|------|
| SQL生成增强 | 提供准确的JOIN条件 | 多表查询准确率提升30% |
| 跨源查询 | 识别跨数据源关系 | 支持异构数据融合 |
| 结果融合 | 提供关系信息用于智能融合 | 融合准确率提升25% |
| 数据血缘 | 构建表间依赖关系图 | 支持影响分析 |

**用户价值**
- 自动建立数据资产目录,无需人工梳理
- 支持单表和多表查询的智能切换
- 跨数据源关系自动识别,打破数据孤岛
- 为数据治理提供基础设施

### 2.4 自然语言查询引擎

自然语言查询引擎是OntiCards的核心能力,它将用户的业务问题转换为可执行的SQL查询,并返回结构化的结果。

**查询处理流程**

```
用户提问 → 意图识别 → 语义检索 → 表关系分析 → SQL生成 → 安全校验 → 执行查询 → 结果返回
```

**核心技术组件**

1. **意图识别与理解**
   - 识别查询意图(数据查询、统计分析、对比分析等)
   - 提取查询对象(商品、订单、用户等)
   - 识别查询条件(时间范围、数值区间、分类筛选等)
   - 识别聚合要求(求和、计数、平均值、分组等)

2. **语义检索与表召回**
   - 将用户问题转换为向量表示
   - 在Weaviate中检索相关的数据卡片
   - 召回Top-K候选表(默认80张)
   - 使用重排序模型精选最相关的表(通常5-10张)

3. **表关系分析**
   - 分析候选表之间的关联关系
   - 识别主外键关系和JOIN条件
   - 构建表关系图谱
   - 确定查询所需的表组合

4. **SQL生成**
   - 基于数据卡片和表关系构建Prompt
   - 调用大语言模型生成SQL语句
   - 支持多种数据库方言(MySQL、Oracle、PostgreSQL、**电科金仓KingBase**、**OceanBase MySQL 租户模式**、**达梦DMBase** 等)
   - 自动处理不同数据库的语法差异

5. **安全校验**
   - 验证SQL语句只包含SELECT操作
   - 检查访问的表和字段是否在白名单内
   - 禁止危险操作(DROP、DELETE、UPDATE等)
   - 限制查询结果数量,防止资源耗尽

6. **查询执行**
   - 连接目标数据库执行SQL
   - 设置查询超时时间(默认30秒)
   - 捕获并处理执行错误
   - 记录查询日志用于审计

7. **结果处理与展示**
   - 格式化查询结果为表格
   - 标注数据来源(数据源、表名)
   - 生成查询说明(系统如何理解问题)
   - 提示被忽略或降级的条件

**智能容错机制**

| 场景 | 处理策略 | 示例 |
|-----|---------|------|
| 字段不存在 | 忽略该条件,执行其他条件 | "价格<100且好评率>90%"中好评率字段不存在,则只执行价格条件 |
| 表名模糊 | 使用语义相似度匹配最接近的表 | "产品表"可能匹配到"product_info"或"goods" |
| 条件冲突 | 提示用户并使用更宽松的条件 | "价格>1000且价格<500"会提示冲突 |
| 跨库字段不一致 | 只在包含该字段的数据源执行 | 广州库有"仓库位置"字段,深圳库没有,则只在广州库使用该条件 |

| 业务术语识别 | 自动识别并展开术语 | "高价值客户"自动展开为VIP+消费>1万的条件 |

**业务术语集成**

OntiCards支持业务术语库的智能集成,通过术语识别与重写技术,实现业务语言的标准化查询:

- **术语识别**: 自动识别用户提问中的业务术语(如"高价值客户"、"核心商品")
- **术语展开**: 将业务术语转换为对应的数据库字段条件和值
- **问题重写**: 生成语义更明确的问题供LLM理解
- **透明返回**: 在结果中展示匹配的术语及其定义

**支持的查询类型**

- **简单筛选**: "价格低于100元的商品"
- **时间范围**: "最近7天的订单"、"2024年1月的销售数据"
- **聚合统计**: "各个品类的销售总额"、"库存数量最多的前10个商品"
- **多条件组合**: "价格在100-500之间且库存大于10的电子产品"
- **排序**: "按销量降序排列"、"价格从低到高"
- **分组对比**: "各个区域的销售额对比"
- **跨表关联**: "订单及其对应的商品信息"

**用户价值**
- 零SQL门槛,会说话就会查数据
- 智能容错,提问不精确也能得到结果
- 支持复杂查询,满足多样化需求
- 查询说明透明,便于理解和调整

### 2.5 跨数据源查询与结果融合（关系卡片增强版）

OntiCards支持在多个数据源之间进行查询,并根据业务语义自动完成结果融合,这是打破数据孤岛的关键能力。引入关系卡片体系后,多表查询和结果融合的准确性得到显著提升。

**关系卡片在查询中的增强作用**

1. **SQL生成阶段增强**
   - 优先使用关系卡片中的JOIN条件（准确率高）
   - 回退到传统的外键推断和启发式匹配
   - 提供置信度信息辅助LLM决策
   - 减少JOIN条件错误和笛卡尔积问题

2. **结果融合阶段增强**
   - 利用关系信息进行智能的跨簇融合
   - 基于关系强度选择融合策略
   - 支持跨数据源的关系识别
   - 提升融合结果的准确性和完整性

**跨数据源查询场景**

| 场景类型 | 业务需求 | 融合策略 | 示例 |
|---------|---------|---------|------|
| 交集查询 | 在多个系统中都存在的数据 | AND/INTERSECT | "在广州和深圳都有库存的商品" |
| 并集查询 | 在任一系统中存在的数据 | OR/UNION | "在广州或深圳有库存的商品" |
| 汇总查询 | 多个系统数据的合并统计 | SUM/AGGREGATE | "所有仓库的商品总库存" |
| 对比查询 | 不同系统数据的对比分析 | COMPARE | "广州和深圳的库存对比" |
| 优先级查询 | 按优先级选择数据源 | PRIORITY | "优先从主库查询,主库无数据则查备库" |

**融合策略详解**

1. **AND策略(交集)**
   - 适用场景: 需要在所有数据源中都满足条件
   - 实现方式: 分别查询各数据源,对结果按关键字段取交集
   - 关键字段: 通常是商品ID、订单号等唯一标识
   - 结果处理: 保留所有数据源都有的记录,合并各数据源的字段

2. **OR策略(并集)**
   - 适用场景: 只要在任一数据源中满足条件即可
   - 实现方式: 分别查询各数据源,对结果按关键字段去重合并
   - 去重规则: 相同关键字段的记录只保留一条
   - 字段冲突: 优先使用第一个数据源的值,或标注来源

3. **AGGREGATE策略(汇总)**
   - 适用场景: 需要对多个数据源的数据进行统计
   - 实现方式: 分别查询各数据源,对数值字段进行求和、计数等
   - 支持操作: SUM(求和)、COUNT(计数)、AVG(平均)、MAX(最大)、MIN(最小)
   - 分组汇总: 支持按维度字段分组后汇总

4. **COMPARE策略(对比)**
   - 适用场景: 需要对比不同数据源的数据
   - 实现方式: 分别查询各数据源,保留数据源标识,并排展示
   - 结果格式: 每条记录标注来源数据源
   - 差异标注: 可选择性高亮差异字段

5. **PRIORITY策略(优先级)**
   - 适用场景: 有主备数据源,优先使用主数据源
   - 实现方式: 按优先级顺序查询,有结果则停止
   - 失败切换: 主数据源失败自动切换到备数据源
   - 结果标注: 标明实际使用的数据源

**智能融合策略选择**

系统会根据用户问题中的关键词自动选择融合策略:

| 关键词 | 推断策略 | 示例 |
|-------|---------|------|
| "都"、"同时"、"既...又..." | AND | "在广州和深圳都有的商品" |
| "或"、"任一"、"任何" | OR | "在广州或深圳有库存的商品" |
| "总"、"汇总"、"合计" | AGGREGATE | "所有仓库的总库存" |
| "对比"、"比较"、"差异" | COMPARE | "广州和深圳的库存对比" |

**字段映射与冲突处理**

在跨数据源查询中,不同数据源的表结构可能存在差异:

1. **字段名不一致**
   - 问题: 同一业务含义的字段在不同数据源中名称不同
   - 解决: 通过数据卡片的语义信息进行字段映射
   - 示例: "price"和"单价"都映射为价格字段

2. **字段缺失**
   - 问题: 某些字段只在部分数据源中存在
   - 解决: 只在包含该字段的数据源中使用该条件
   - 提示: 在结果中说明哪些数据源缺少该字段

3. **数据类型不一致**
   - 问题: 同一字段在不同数据源中类型不同
   - 解决: 自动进行类型转换,或提示用户
   - 示例: 价格字段在A库是DECIMAL,在B库是VARCHAR

4. **取值范围不一致**
   - 问题: 枚举值或分类在不同数据源中定义不同
   - 解决: 通过数据卡片的典型值进行映射
   - 示例: 状态字段在A库是"1/0",在B库是"启用/禁用"

**性能优化**

- **并行查询**: 多个数据源的查询并行执行,减少总耗时

### 2.12 SSO单点登录

OntiCards支持SSO（Single Sign-On，单点登录）功能，通过JWT Token模式实现企业统一身份认证集成，让用户可以使用企业账号直接登录OntiCards。

#### 2.12.1 什么是SSO单点登录

SSO单点登录是一种企业级身份认证方式，允许用户通过企业统一的身份认证系统登录OntiCards，实现一次登录、多系统通行。

**核心价值：**
- **统一身份管理**：员工使用企业统一账号，无需单独注册OntiCards账号
- **提升安全性**：集中管控登录入口，减少密码泄露风险
- **改善用户体验**：一次登录，多系统通行
- **降低运维成本**：无需单独维护OntiCards账号体系

#### 2.12.2 JWT Token模式

JWT（JSON Web Token）是一种开放标准（RFC 7519），用于在各方之间安全地传输信息。OntiCards采用JWT Token模式实现与第三方系统的SSO对接。

**JWT Token结构：**

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VybmFtZSI6InpoYW5nX3NhbiJ9.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
|______________|.|__________________________________________|.______________|
    Header      |              Payload                      |   Signature
     头部        |              用户数据                      |     签名
```

**Token各部分说明：**

| 部分 | 名称 | 作用 | 示例内容 |
|------|------|------|----------|
| 第一部分 | Header（头部） | 声明算法和类型 | `{"alg":"HS256","typ":"JWT"}` |
| 第二部分 | Payload（负载） | 存放实际的用户数据 | `{"username":"zhang_san","user_id":"001",...}` |
| 第三部分 | Signature（签名） | 用密钥对前两部分签名，确保不被篡改 | `SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c` |

#### 2.12.3 Token字段说明

**必填字段：**

| 字段 | 类型 | 说明 |
|------|------|------|
| username | string | 用户的唯一标识，不能为空 |
| user_id | string | 用户在企业系统中的ID，不能为空 |
| exp | number | Token过期时间（Unix时间戳），建议设置为5分钟后 |

**可选字段：**

| 字段 | 类型 | 说明 |
|------|------|------|
| nickname | string | 用户昵称 |
| email | string | 用户邮箱 |
| source | string | 来源标识，用于区分不同系统，默认default |
| iat | number | Token签发时间（Unix时间戳） |

#### 2.12.4 SSO登录流程

```
1. 企业系统验证用户身份
   ↓
2. 企业后端生成JWT Token（包含用户信息）
   ↓
3. 拼接SSO登录URL
   {OntiCards API地址}/sso/login?token={JWT Token}&redirect_url={回调地址}
   ↓
4. 用户浏览器跳转到OntiCards SSO接口
   ↓
5. OntiCards验证JWT签名和有效期
   ↓
6. 创建/关联用户，生成平台Token
   ↓
7. 跳转到回调地址，携带access_token
   ↓
8. 前端接收Token，登录完成
```

#### 2.12.5 用户创建/关联逻辑

当用户首次通过SSO访问时，OntiCards系统会：

1. **接收JWT Token** → 获取URL中的token参数
2. **解析Header** → 获取算法信息（HS256）
3. **验证签名** → 用共享密钥验证token是否被篡改
4. **检查过期** → 验证exp是否有效
5. **提取Payload** → 获取username、user_id等用户信息
6. **查询用户** → 根据 `idp_user_id` + `idp_source` 查找已存在用户
7. **创建/关联** → 新用户自动创建，老用户关联登录
8. **生成Token** → 生成OntiCards自己的登录Token
9. **跳转回调** → 携带新Token跳转到 redirect_url

**Token生成规范：**

企业后端在生成JWT Token时，需要包含以下信息：

| 字段 | 类型 | 说明 |
|------|------|------|
| username | string | 用户的唯一标识，不能为空 |
| user_id | string | 用户在企业系统中的ID，不能为空 |
| exp | number | Token过期时间（Unix时间戳），建议设置为5分钟后 |
| nickname | string | 用户昵称（可选） |
| email | string | 用户邮箱（可选） |
| source | string | 来源标识，用于区分不同系统（可选，默认default） |

#### 2.12.6 安全机制

| 安全措施 | 说明 |
|----------|------|
| Token有效期限制 | 建议设置为5分钟内，防止Token泄露风险 |
| HMAC-SHA256签名 | 使用共享密钥对Token签名，防止篡改 |
| 用户级数据隔离 | SSO用户与其他用户数据完全隔离 |
| 完整的审计日志 | 记录所有SSO登录行为 |

#### 2.12.7 错误码说明

| HTTP状态码 | error字段 | 原因 |
|------------|-----------|------|
| 400 | `缺少token参数` | URL中没有传token |
| 400 | `token中缺少必要的用户信息` | Payload中username或user_id为空 |
| 401 | `token已过期` | Token的exp已过期 |
| 401 | `token无效` | 签名验证失败（密钥不匹配或内容被篡改） |

#### 2.12.8 配置汇总

**OntiCards提供：**

| 项目 | 说明 |
|------|------|
| SSO登录接口 | `{OntiCards API地址}/sso/login` |
| SSO共享密钥 | 客户提供，OntiCards存储，用于验证JWT签名 |

**客户提供：**

| 项目 | 示例值 | 说明 |
|------|--------|------|
| 共享密钥 | `K7x#9mP$2nL@qR8` | 建议64位以上的随机字符串 |
| 回调地址 | `https://frontend.onticards.com/overview` | 登录成功后跳转的前端页面 |

#### 2.12.9 适用场景

| 场景 | 说明 |
|------|------|
| 企业SSO集成 | 与钉钉、企业微信、飞书等企业系统集成 |
| 统一身份认证 | 对接LDAP、OAuth、OIDC等身份认证平台 |
| 第三方平台接入 | 第三方平台免登录访问OntiCards |
| 智能体平台集成 | 为AI智能体提供身份桥接能力 |

### 2.13 业务术语库管理

OntiCards提供了业务术语库管理功能，帮助企业建立统一的业务术语标准，实现业务语言的标准化查询，让不同业务背景的用户都能用自己熟悉的术语准确查询数据。

#### 2.13.1 什么是业务术语库

业务术语库是一套企业级业务术语标准化管理体系，它包含：

- **术语定义**：每个业务术语的正式名称、定义和业务含义
- **同义词映射**：业务术语的各种叫法（如"销售额"和"营收"、"收入"）
- **关联字段**：术语与数据库字段的映射关系
- **关联数据卡片**：术语涉及的原始数据卡片

**典型应用场景**：

| 用户提问 | 系统理解 |
|---------|---------|
| "查询本月高价值客户的购买情况" | 高价值客户 → VIP等级=1 + 累计消费>10000 |
| "看看核心商品的库存" | 核心商品 → 产品分类 IN ('A类', 'B类') |
| "VIP用户的订单转化率" | VIP用户 → 会员等级='钻石' |

#### 2.13.2 术语库层级结构

```
业务术语库
├── 术语库（Library）
│   ├── 术语库名称：如"销售术语库"、"库存术语库"
│   ├── 术语库描述：说明术语库的用途和范围
│   ├── 关联数据源：可选择关联到特定数据源
│   └── 启用状态：控制是否在查询中使用
│
├── 术语（Term）
│   ├── 术语名称：如"高价值客户"
│   ├── 术语定义：如"累计消费超过1万元且最近6个月有购买行为的客户"
│   ├── 同义词：如"VIP客户"、"优质客户"、"大客户"
│   ├── 关联字段：如 customer_type='VIP', total_amount>10000
│   ├── 关联数据卡片：如 customers, vip_members
│   └── 启用状态：控制术语是否生效
│
└── 术语模板（Template）
    ├── 模板名称：如"VIP客户分析模板"
    ├── 模板内容：包含多个术语的组合查询
    └── 适用场景：说明模板的使用场景
```

#### 2.13.3 术语库管理功能

**1. 术语库管理**

- 创建、编辑、删除术语库
- 为术语库设置名称、描述和关联数据源
- 启用/禁用术语库，控制是否在查询中生效
- 术语库级别的权限控制

**2. 术语管理**

- 创建、编辑、删除业务术语
- 设置术语名称、定义和同义词列表
- 关联术语到数据库字段和数据卡片
- 支持批量导入/导出术语
- 启用/禁用术语，灵活控制生效范围

**3. 术语模板管理**

- 创建标准化的查询模板
- 模板中可以包含多个术语组合
- 快速应用到常见业务场景

**4. 数据源关联**

- 将术语库关联到特定数据源
- 跨数据源术语库支持多数据源场景
- 按数据源启用不同的术语库组合

#### 2.13.4 术语识别与重写

当用户提交查询时，系统会：

1. **术语识别**：自动识别用户提问中的业务术语
2. **术语展开**：将业务术语转换为对应的字段条件和值
3. **问题重写**：生成语义更明确的查询语句
4. **SQL生成**：基于重写后的问题生成SQL

**示例**：

| 用户原始问题 | 系统识别 | 重写后的问题 |
|-------------|---------|-------------|
| "高价值客户的订单" | 高价值客户 → VIP + 消费>1万 | "VIP等级客户且累计消费超过1万元的客户的订单" |
| "核心商品的库存" | 核心商品 → A类+B类 | "产品分类为A类或B类的商品的库存" |

#### 2.13.5 术语重写在查询中的集成

**启用方式**

在聚合查询接口中，通过`enable_term_rewrite`参数启用术语重写功能，并指定要使用的术语库列表。

**返回结果说明**

当启用术语重写时，返回结果会包含以下术语相关信息：

| 返回字段 | 说明 |
|---------|------|
| enabled | 是否启用了术语重写 |
| matched_terms | 匹配到的业务术语列表 |
| term_name | 术语名称 |
| term_definition | 术语的业务定义 |
| library_id | 所属术语库标识 |
| library_name | 所属术语库名称 |
| related_fields | 关联的数据库字段列表 |
| related_datacards | 关联的数据卡片列表 |
| rewritten_question | 重写后的查询问题 |

### 2.14 数据治理模块 - 数据质检（第一阶段）

OntiCards提供了完善的数据治理能力，帮助企业建立数据质量保障体系。数据治理分为两个阶段：**第一阶段为数据质检**（已完成），**第二阶段为实际治理**（规划中）。本章节详细介绍第一阶段"数据质检"的完整功能和价值。

#### 2.14.1 什么是数据治理

数据治理是企业数据管理的重要组成部分，旨在建立数据质量标准、监控数据质量状况、发现并解决数据问题。OntiCards的数据治理模块帮助企业实现：

- **数据标准化**：建立统一的规则库，规范数据质量标准
- **质量监控**：持续监控数据质量状况，及时发现质量问题
- **问题追溯**：定位数据问题的根源，指导数据修复
- **持续改进**：通过质量报告分析，推动数据质量不断提升

**两阶段设计理念：**

```
┌─────────────────────────────────────────────────────────────────┐
│                          数据治理完整链路                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  【第一阶段：数据质检】  ← 当前已完成                              │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  规则库构建 → 规则创建（多模式） → 规则执行 → 报告生成     │   │
│  │                                                           │   │
│  │  核心产出: 质检报告（发现问题 + 量化评分 + 改进建议）      │   │
│  └─────────────────────────────────────────────────────────┘   │
│                              ↓                                    │
│  【第二阶段：实际治理】  ← 规划中                                  │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  问题确认 → 治理动作执行 → 治理结果验证                    │   │
│  │                                                           │   │
│  │  核心产出: 问题数据修复/对账处理/告警通知                  │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

#### 2.14.2 规则库管理

规则库是数据质检的基础设施，用于组织和管理针对特定数据源的质检规则。

**核心功能：**

1. **规则库创建**
   - 必须关联数据源，确保规则的针对性和准确性
   - 支持自定义规则库名称和描述，便于识别和管理
   - 规则库级别的启用/禁用控制

2. **规则库组织**
   - 按数据源分类管理规则库
   - 支持搜索和筛选，快速定位目标规则库
   - 规则库详情展示包含规则列表

**用户价值：**
- 规范化管理数据质检规则
- 便于按业务场景组织和复用规则
- 支持团队协作和规则共享

#### 2.14.3 规则管理

规则是质检的核心，定义了对数据的具体检查条件。OntiCards提供了三种规则创建模式，适应不同用户的使用习惯和技术水平。

**规则创建模式对比：**

| 创建模式 | 适用用户 | 核心价值 | 典型场景 |
|---------|---------|---------|---------|
| 手动专家模式 | 技术团队、DBA | 精确控制，满足复杂质检需求 | 已有的质检规则，需要精确控制 |
| AI自然语言模式 | 业务人员 | 零门槛，智能分析推荐 | 业务人员快速创建规则 |
| 模板导入模式 | 所有用户 | 快速复用，二次编辑 | 常见质检场景的快速复用 |

---

**手动专家模式 - 精确质检**

手动专家模式面向具备SQL能力的技术人员，提供最精确的规则配置能力：

- **精确控制**: 直接编写SQL条件表达式，完全掌控质检逻辑
- **复杂规则**: 支持自定义SQL，可实现任意复杂的质检需求
- **已有规则迁移**: 可直接将现有的质检规则迁移到系统中
- **适用场景**: 数据治理专家、DBA、技术团队进行精确质检配置

**典型示例**:
- `phone IS NOT NULL` → 手机号不能为空
- `amount > 0` → 订单金额必须大于0
- `created_at >= CURRENT_DATE - INTERVAL '7 days'` → 数据更新必须在7天内

---

**AI自然语言模式 - 智能理解与推荐**

AI自然语言模式面向业务人员，通过智能分析降低使用门槛：

- **自然语言输入**: 直接输入"订单金额不能为负"等口语化描述
- **智能表列识别**: 系统自动分析目标表结构，智能识别可能需要质检的列
- **候选方案展示**: 根据用户描述推荐多个可能的规则方案供确认
- **置信度评估**: 高置信度自动通过，低置信度提示确认，减少误判
- **适用场景**: 业务人员快速创建规则，无需了解数据库结构

**智能分析流程**:
```
用户输入: "订单金额不能为负"
    ↓
系统智能分析:
├── 分析表结构，理解字段含义
├── 识别相关列（如 amount, price, total_amount）
├── 生成候选规则方案
└── 展示推荐结果供用户确认
    ↓
用户确认 → 规则创建成功
```

---

**模板导入模式 - 快速复用**

模板导入模式提供预置的质检模板，用户可快速选择并二次编辑：

- **预置模板库**: 内置常见质检场景模板，开箱即用
- **快速创建**: 选择模板后填入表名、字段名等参数即可
- **二次编辑**: 支持在模板基础上调整参数，满足个性化需求
- **适用场景**: 常见质检场景的快速复用，如手机号格式、邮箱格式、日期范围等

**模板类型示例**:
| 模板名称 | 适用场景 | 可配置参数 |
|---------|---------|-----------|
| 手机号格式检验 | 检查手机号是否为11位数字 | 目标字段 |
| 邮箱格式检验 | 检查邮箱格式是否正确 | 目标字段 |
| 日期范围检验 | 检查日期是否在合理范围内 | 开始字段、结束字段 |
| 金额阈值检验 | 检查金额是否在合理范围 | 金额字段、最小值、最大值 |

---

**支持的规则类型：**

| 规则类型 | 说明 | 典型场景 |
|---------|------|---------|
| 空值检测 | 检查字段是否为空 | "手机号不能为空" |
| 唯一性检测 | 检查字段值是否唯一 | "订单号不能重复" |
| 格式检测 | 检查字段格式是否符合规范 | "手机号必须是11位数字" |
| 阈值检测 | 检查数值是否在合理范围内 | "订单金额必须大于0" |
| 枚举值检测 | 检查字段值是否在允许范围内 | "订单状态必须是'待支付'、'已支付'" |
| 长度检测 | 检查字段长度是否符合要求 | "身份证号必须是18位" |
| 范围检测 | 检查数值是否在指定范围内 | "年龄必须在0-150之间" |
| 日期逻辑检测 | 检查日期字段的逻辑关系 | "订单日期不能晚于发货日期" |
| 一致性检测 | 检查关联字段的数据一致性 | "开始日期必须早于结束日期" |
| 新鲜度检测 | 检查数据是否及时更新 | "更新时间必须在最近7天内" |
| 值分布检测 | 分析字段值的分布特征 | 自动分析数据分布情况 |
| 自定义规则 | 完全由用户自定义检查逻辑 | 特殊业务场景 |
| 复合规则 | 多个条件组合检测 | "金额必须为正且不为空" |
| 表统计 | 表级别的数据统计 | 自动统计表记录数等指标 |

---

**复合规则特点：**

- 支持多条件组合检测（AND/OR）
- 如"订单金额必须大于0且不为空"
- 自动处理复杂的业务逻辑判断

**用户价值：**
- 三种模式满足不同技术背景用户的需求
- 手动模式提供精确控制能力
- AI模式降低使用门槛，业务人员也能创建规则
- 模板模式提升复用效率，避免重复工作
- 复合规则支持复杂业务场景

#### 2.14.4 多数据库支持

OntiCards支持多种数据库类型，自动适配不同数据库的语法规则。

**支持的数据库：**

| PostgreSQL | 功能强大的开源数据库 |
| SQL Server | 微软企业级数据库 |
| Oracle | 大型企业核心系统常用 |
| SQLite | 轻量级嵌入式数据库 |

#### 2.14.5 规则执行

规则执行是数据质检的核心环节，系统会批量执行配置的规则并收集结果。

数据质检模块提供两种检测模式，满足不同的质检需求：

**模式一：基于规则库的质检**

通过自定义质检规则，对数据进行系统性检查。适合有明确质量标准的数据检测场景。

- **规则库管理**：按业务领域或数据类型创建规则库
- **多模式规则创建**：支持模板模式、AI自然语言模式、手动模式三种方式
- **多类型规则支持**：非空检查、唯一性检查、格式校验、范围检查、枚举值检查、正则匹配等

**模式二：基础空值检测**

自动扫描数据库中各表的空值情况，快速发现数据完整性问题。适合快速了解数据健康状况。

- **自动扫描**：无需配置，系统自动扫描所有表的空值情况
- **统计全面**：统计每个字段的空值率，帮助定位问题
- **快速上手**：一键执行，即刻了解数据完整性

**统一体验**

两种模式的执行明细统一存储，形成完整的质量检测记录，便于：
- 后续数据治理阶段的实施，提供可追溯的检测历史
- 统一查看和管理所有质检结果
- 质量趋势分析，了解数据质量变化

> **执行质检的重要注意事项**
>
> 1. **数据静态性要求**：如果要使用质检功能，最好确保业务系统数据库（数据源或数据空间中的相关数据库表）中没有实时数据中途更新，否则会影响质检结果。质检过程中针对的数据范围是静态数据场景，请合理安排执行时间。
>
> 2. **执行时间建议**：质检执行可能消耗一定数据库资源，建议在业务低峰期执行大规模质检。

**执行过程：**

1. **规则选择**
   - 可按规则库批量执行
   - 也可指定具体规则执行
   - 可选择执行模式（基于规则库/基础空值检测）

2. **自动检测**
   - 系统自动对每条规则生成对应的检测SQL
   - 在目标数据库上执行检测
   - 统计通过数量和失败数量

3. **结果采集**
   - 记录总数据量、通过量、失败量
   - 计算失败率和通过率
   - 采集违规数据的样本供分析
   - 两种模式的执行明细统一存储

4. **评分计算**
   - 基于通过率和失败严重程度计算质量评分
   - 量化评估数据质量水平

**质量评分体系：**

| 等级 | 评分范围 | 说明 |
|------|---------|------|
| 优秀 | ≥95分 | 数据质量非常好，值得信赖 |
| 良好 | ≥85分 | 数据质量良好，可以正常使用 |
| 一般 | ≥70分 | 数据质量一般，存在改进空间 |
| 较差 | ≥60分 | 数据质量问题较多，需要关注 |
| 差 | <60分 | 数据质量存在严重问题 |

**用户价值：**
- 一键执行批量质检规则，无需逐条检查
- 实时获取质量评分和等级，直观了解数据状况
- 可选的扩展模块满足深度质检需求

#### 2.14.6 质检报告生成

质检报告是质检结果的最终呈现，包含详细的质量分析和建议。

**报告内容结构：**

| 章节 | 内容 | 说明 |
|------|------|------|
| 基本信息 | 报告概览 | 数据源、执行时间、规则数量等基础信息 |
| 质量概览 | 评分汇总 | 规则库质检、空值检测的质量评分（统一呈现） |
| 基础空值检测 | 字段级空值统计 | 以表为单位展示各字段的空值情况 |
| 执行明细 | 规则执行结果 | 每条规则的执行情况和结果（含两种模式） |
| 失败样本 | 违规数据 | 实际违规的数据样本，便于定位问题 |
| AI智能总结 | 分析与建议 | 基于执行结果自动生成的自然语言总结和改进建议 |

**报告导出格式：**

| 格式 | 说明 | 适用场景 |
|------|------|---------|
| Word文档（DOCX） | 正式文档格式 | 正式汇报、存档归档 |
| PDF文档 | 便携式文档 | 分享打印 |
| Excel表格（XLSX） | 表格数据 | 数据分析，二次处理 |
| Markdown | 轻量级格式 | 快速查看、版本控制 |

## 三、技术实现深度解析

本章节详细解析OntiCards的核心技术实现,帮助客户深入理解系统的技术能力和实现原理。

### 3.1 多步推理与SQL生成技术

OntiCards的多步推理能力是实现复杂查询的关键技术,它能够将复杂的业务问题分解为多个子问题,逐步求解并整合结果。

**技术实现层次**

多步推理主要在**智能体(Agent)层面**实现,而非在应用层面硬编码。这种设计使系统具有更强的灵活性和扩展性。

**实现方式一: 子问题拆解**

当用户提出复杂问题时,智能体会自动进行问题分解:

```
用户问题: "计算2024年相比2023年的销售额同比增长率"

智能体推理过程:
Step 1: 识别这是一个同比增长率计算问题
Step 2: 拆解为两个子问题:
   - 子问题1: 查询2024年的销售总额
   - 子问题2: 查询2023年的销售总额
Step 3: 分别生成SQL并执行:
   - SQL1: SELECT SUM(amount) FROM orders WHERE YEAR(order_date) = 2024
   - SQL2: SELECT SUM(amount) FROM orders WHERE YEAR(order_date) = 2023
Step 4: 获取两个子问题的结果:
   - 2024年销售额: 1,200,000
   - 2023年销售额: 1,000,000
Step 5: 计算增长率:
   - 增长率 = (1,200,000 - 1,000,000) / 1,000,000 = 20%
Step 6: 返回最终结果
```

**实现方式二: 直接生成联表查询**

对于某些复杂查询,智能体可能直接生成包含多表JOIN的SQL,无需多跳:

```
用户问题: "查询每个商品的销售数量和库存数量"

智能体推理过程:
Step 1: 识别需要关联两张表(订单明细表、库存表)
Step 2: 分析表关系,识别JOIN条件(商品ID)
Step 3: 直接生成联表查询SQL:
   SELECT
     p.product_name,
     COALESCE(SUM(o.quantity), 0) as sales_quantity,
     COALESCE(i.stock_quantity, 0) as stock_quantity
   FROM products p
   LEFT JOIN order_items o ON p.product_id = o.product_id
   LEFT JOIN inventory i ON p.product_id = i.product_id
   GROUP BY p.product_id, p.product_name, i.stock_quantity
Step 4: 执行SQL并返回结果
```

**智能体的决策逻辑**

智能体会根据以下因素决定使用哪种方式:

| 决策因素 | 子问题拆解 | 直接联表查询 |
|---------|-----------|-------------|
| 问题复杂度 | 需要多步计算(如增长率、占比) | 单次查询可完成 |
| 表关系 | 表之间无直接关联关系 | 表之间有明确的主外键关系 |
| 数据源分布 | 数据分散在不同数据源 | 数据在同一数据源 |
| 计算逻辑 | 需要中间结果参与后续计算 | 可通过SQL聚合函数完成 |

**Prompt工程的关键作用**

多步推理能力的实现依赖于精心设计的Prompt:

1. **思维链(Chain-of-Thought)提示**
   - 在Prompt中引导大模型进行逐步推理
   - 示例: "请先分析这个问题需要哪些数据,然后逐步说明如何获取这些数据"

2. **问题分解指令**
   - 明确告诉模型可以将复杂问题拆解为子问题
   - 示例: "如果问题涉及多个时间段的对比,请分别查询每个时间段的数据"

3. **上下文保持**
   - 在多轮对话中保持上下文信息
   - 子问题的结果会作为上下文传递给后续步骤

4. **数据库方言适配**
   - 针对不同数据库类型提供特定的SQL示例
   - Oracle使用TO_DATE,MySQL使用STR_TO_DATE等

**技术优势**

- **灵活性**: 无需为每种复杂查询编写专门的代码
- **可扩展性**: 新的查询模式可以通过优化Prompt实现
- **准确性**: 逐步推理减少了一次性生成复杂SQL的错误率
- **可解释性**: 每个步骤的推理过程都可以展示给用户

**实际案例**

```
案例: 计算各品类商品的库存周转率

智能体推理:
1. 识别需要的数据:
   - 各品类的销售数量(来自订单表)
   - 各品类的平均库存(来自库存表)
2. 拆解为子问题:
   - 子问题1: 查询各品类最近30天的销售总量
   - 子问题2: 查询各品类的当前库存
3. 生成并执行SQL:
   - SQL1: 查询销售数据
   - SQL2: 查询库存数据
4. 计算周转率:
   - 周转率 = 销售总量 / 平均库存
5. 返回结果并说明计算逻辑
```

**局限性与改进方向**

- **当前局限**: 对于超过3-4步的复杂推理,准确率会下降
- **改进方向**: 引入更强的推理模型,优化Prompt设计,增加中间结果验证机制

### 3.2 意图识别与确认机制

意图识别与确认是确保查询准确性的关键环节,OntiCards在智能体层面通过提示词工程实现了完善的意图识别和确认机制。

**实现层次: 智能体层面**

意图识别和确认**在智能体应用层面实现**,而非在产品层面硬编码。这种设计使系统能够灵活应对各种复杂场景,并且可以通过优化Prompt持续改进。

**意图识别的核心流程**

```
用户输入 → 语义理解 → 意图分类 → 参数提取 → 完整性检查 → 确认/反问 → 执行查询
```

**意图分类体系**

系统通过Prompt工程识别以下主要意图类型:

| 意图类型 | 描述 | 示例 | 处理方式 |
|---------|------|------|---------|
| 数据查询 | 查询具体数据记录 | "查询价格低于100的商品" | 直接生成SQL查询 |
| 统计分析 | 聚合统计、分组汇总 | "各品类的销售总额" | 生成包含聚合函数的SQL |
| 对比分析 | 不同维度的数据对比 | "广州和深圳的库存对比" | 跨数据源查询或分组对比 |
| 趋势分析 | 时间序列数据分析 | "最近7天的销售趋势" | 按时间维度查询和排序 |
| 异常检测 | 查找异常或特殊情况 | "库存低于安全库存的商品" | 条件筛选查询 |
| 模糊查询 | 意图不明确的提问 | "看看数据" | 触发反问机制 |

**参数提取与验证**

智能体会从用户问题中提取关键参数:

1. **查询对象**: 商品、订单、用户等
2. **查询条件**: 价格范围、时间范围、分类筛选等
3. **聚合维度**: 按品类、按地区、按时间等
4. **排序要求**: 升序、降序、Top-N等
5. **数据源范围**: 单个数据源或多个数据源

**意图确认机制**

当遇到以下情况时,系统会主动反问用户确认:

**场景1: 语义模糊**

```
用户: "查询商品数据"
系统识别: 意图过于宽泛,缺少具体条件
系统反问: "您想查询哪些商品数据?可以告诉我:
  - 需要查询哪些字段?(如商品名称、价格、库存等)
  - 是否有筛选条件?(如价格范围、品类等)
  - 需要查询哪个数据源的数据?"
```

**场景2: 参数缺失**

```
用户: "查询销售额"
系统识别: 缺少时间范围参数
系统反问: "请问您想查询哪个时间段的销售额?
  - 今天
  - 最近7天
  - 本月
  - 自定义时间范围"
```

**场景3: 多义性问题**

```
用户: "查询库存"
系统识别: "库存"可能指多个表(商品库存、原料库存、成品库存)
系统反问: "请问您想查询哪种库存?
  - 商品库存(零售商品)
  - 原料库存(生产原料)
  - 成品库存(生产成品)"
```

**场景4: 不符合应用场景**

```
用户: "帮我写一段Python代码"
系统识别: 请求超出数据查询范围
系统反馈: "抱歉,我是数据查询助手,专注于帮您查询数据库中的数据。
如果您需要查询数据,请告诉我具体的查询需求。"
```

### 3.3 联表查询稳定性分析（关系卡片增强版）

联表查询是数据库查询中的常见需求,也是技术实现的难点之一。引入关系卡片体系后,OntiCards的联表查询稳定性得到显著提升。

**联表查询的实现基础**

OntiCards的联表查询能力建立在以下技术基础上:

1. **关系卡片体系（新增）**
   - 存储经过验证的表间关系
   - 提供准确的JOIN条件和置信度
   - 支持跨数据源关系识别
   - 优先级高于传统推断方式

2. **数据卡片中的关系信息（传统方式）**
   - 主键识别: 自动识别表的主键字段
   - 外键关系: 从数据库元数据中提取外键约束
   - 关联推断: 通过字段名称和数据类型推断潜在关联关系

3. **大语言模型的SQL生成能力**
   - 理解表之间的业务关系
   - 生成正确的JOIN语法
   - 选择合适的JOIN类型(INNER/LEFT/RIGHT JOIN)

**稳定性评估维度**

基于实际测试和使用情况,我们从以下维度评估联表查询的稳定性:

**1. 简单两表关联 (稳定性: 极高)**

| 场景 | 成功率 | 典型案例 | 说明 |
|-----|-------|---------|------|
| 有关系卡片 | >95% | 订单表 JOIN 订单明细表 | 使用关系卡片中的JOIN条件 |
| 有明确外键关系 | >90% | 订单表 JOIN 用户表 | 数据库中定义了外键约束 |
| 字段名称一致 | >85% | product_id关联 | 两表都有product_id字段 |
| 常见业务关系 | >85% | 用户表 JOIN 订单表 | 用户-订单是常见关系模式 |

**稳定性分析:**
- 关系卡片提供的JOIN条件准确率最高,显著减少错误
- 当表之间有明确的主外键关系时,系统能够准确识别并生成正确的JOIN条件
- 字段名称一致性是关键因素,相同名称的字段更容易被正确关联
- 大语言模型对常见业务关系(如用户-订单、商品-库存)有较好的理解

**2. 多表关联 (稳定性: 高)**

| 场景 | 成功率 | 典型案例 | 说明 |
|-----|-------|---------|------|
| 3表关联（有关系卡片） | >90% | 订单+订单明细+商品 | 关系卡片提供完整关系链 |
| 3表关联（传统） | >80% | 订单+订单明细+商品 | 链式关联关系 |
| 4-5表关联（有关系卡片） | 75-85% | 订单+用户+商品+库存+分类 | 关系卡片辅助决策 |

**稳定性分析:**
- 关系卡片显著提升多表关联的成功率（+10-15%）
- 3表关联的成功率较高,大语言模型能够理解链式关联逻辑
- 当关联表数量超过4张时,关系卡片的辅助作用更加明显
- 星型关联(一个中心表关联多个维度表)的稳定性优于复杂的网状关联

**3. 复杂JOIN类型 (稳定性: 中等)**

| JOIN类型 | 成功率 | 适用场景 | 说明 |
|---------|-------|---------|------|
| INNER JOIN | >90% | 只需要匹配的记录 | 最常用,最稳定 |
| LEFT JOIN | >85% | 需要保留左表所有记录 | 较常用,稳定性好 |
| RIGHT JOIN | >75% | 需要保留右表所有记录 | 使用较少,可能被转换为LEFT JOIN |
| FULL OUTER JOIN | 60-70% | 需要保留两表所有记录 | 部分数据库不支持 |
| CROSS JOIN | <60% | 笛卡尔积 | 使用场景少,容易误用 |

**稳定性分析:**
- INNER JOIN和LEFT JOIN的稳定性最高,是最常用的JOIN类型

- 对于不常用的JOIN类型(如FULL OUTER JOIN),可能需要用户明确指定

### 3.4 语义检索与向量化技术

语义检索是OntiCards实现自然语言查询的核心技术之一,它能够根据用户问题的语义含义,快速找到相关的数据表。

**技术架构**

```
用户问题 → 文本向量化 → 向量检索 → 候选表召回 → 重排序 → 精选表集合
```

**核心技术组件**

1. **文本向量化(Embedding)**
   - 使用预训练的Embedding模型将文本转换为向量
   - 支持中文和英文的语义理解
   - 向量维度: 通常为768或1024维
   - 模型选择: 根据性能和成本平衡选择合适的模型

2. **向量数据库(Weaviate)**
   - 存储数据卡片的向量表示
   - 支持高效的向量相似度检索
   - 支持混合检索(向量+关键词)
   - 支持实时更新和增量索引

3. **召回策略**
   - 向量相似度检索: 基于余弦相似度
   - 召回数量: 默认Top-80候选表
   - 召回阈值: 可配置的相似度阈值
   - 多路召回: 结合向量检索和关键词匹配

4. **重排序(Rerank)**
   - 使用专门的重排序模型对召回结果进行精排
   - 支持多种重排序策略: smart/gap/score/hybrid
   - 自适应截断: 根据分数梯度自动筛选
   - 最终输出: 通常5-10张最相关的表

**工作流程详解**

**步骤1: 数据卡片向量化**

在数据卡片生成时,系统会将卡片内容转换为向量:

```
数据卡片文本 = 表名 + 表用途 + 字段名称 + 字段含义 + 业务关键词 + 典型值
↓
Embedding模型
↓
向量表示 (768维或1024维)
↓
存储到Weaviate
```

**步骤2: 用户问题向量化**

当用户提问时,系统将问题转换为向量:

```
用户问题: "查询价格低于100元的商品"
↓
Embedding模型
↓
问题向量 (768维或1024维)
```

**步骤3: 向量检索**

在Weaviate中进行相似度检索:

```
问题向量 → Weaviate检索 → Top-80候选表
计算方式: 余弦相似度
相似度范围: 0-1,越接近1越相似
```

**步骤4: 重排序**

使用重排序模型对候选表进行精排:

```
候选表(80张) + 用户问题 → Rerank模型 → 相关性分数
↓
按分数排序
↓
自适应截断(根据分数梯度)
↓
最终精选表(5-10张)
```

**重排序策略详解**

| 策略 | 说明 | 适用场景 | 效果 |
|-----|------|---------|------|
| smart | 智能截断,根据分数梯度自动确定截断点 | 通用场景 | 平衡准确率和召回率 |
| gap | 基于分数差距截断,当相邻分数差距过大时截断 | 相关性差异明显的场景 | 过滤低相关表 |
| score | 基于绝对分数阈值截断 | 需要严格控制质量的场景 | 高准确率 |
| hybrid | 结合多种策略 | 复杂场景 | 综合效果最优 |

**性能指标**

基于实际测试数据:

| 指标 | 数值 | 说明 |
|-----|------|------|
| 召回准确率 | >85% | Top-80候选中包含正确表的比例 |
| 重排序准确率 | >90% | 精选表中包含正确表的比例 |
| 检索延迟 | <100ms | 向量检索的平均响应时间 |
| 重排序延迟 | <200ms | 重排序的平均响应时间 |
| 总体延迟 | <300ms | 从问题到精选表的总时间 |

**技术优势**

1. **语义理解能力**
   - 不依赖关键词精确匹配
   - 能够理解同义词和近义词
   - 支持模糊表达和口语化提问

2. **高效检索**
   - 向量检索速度快,支持大规模数据
   - 毫秒级响应,用户无感知
   - 支持实时更新,无需重建索引

3. **准确性保障**
   - 两阶段检索(召回+重排序)提升准确率
   - 自适应截断避免噪音干扰
   - 多路召回提升召回率

4. **可扩展性**
   - 支持数万张表的检索
   - 向量数据库可水平扩展
   - 支持分布式部署

**实际案例**

**案例1: 同义词理解**

```
用户问题: "查询单价低于100的产品"
关键词: 单价、产品
语义理解:
  - "单价" → "price"、"unit_price"、"价格"
  - "产品" → "product"、"goods"、"商品"
召回表: products、goods_info、product_price
重排序后: products(0.92)、goods_info(0.85)
```

```
关键词: 库存、不够
语义理解:
  - "库存不够" → "库存低于安全库存"、"缺货"
  - "东西" → "商品"、"产品"、"物料"
召回表: inventory、stock、product_stock
重排序后: inventory(0.88)、product_stock(0.82)
```

**案例3: 业务场景理解**

```
用户问题: "哪些客户最近没有下单"
关键词: 客户、下单

  - 需要关联客户表和订单表
```

**局限性与挑战**

1. **向量化质量依赖**
   - Embedding模型的质量直接影响检索效果
   - 对于专业领域术语,可能需要领域适配

2. **数据卡片质量依赖**
   - 数据卡片内容不完整会影响召回准确率
   - 需要持续优化数据卡片质量

3. **计算成本**
   - 向量化和检索需要一定的计算资源
   - 大规模数据场景下需要优化性能

**优化方向**

- **短期**: 优化数据卡片内容,提升向量质量
- **中期**: 引入领域适配的Embedding模型
- **长期**: 建立用户反馈机制,持续优化检索效果

### 4.4 适用场景与不适用场景

**适用场景**

OntiCards特别适合以下应用场景:

1. **日常业务数据查询**
   - 业务人员需要频繁查询业务数据
   - 查询需求多样化,难以提前固化为报表
   - 技术团队响应不及时,影响业务效率

2. **临时数据分析**
   - 需要快速验证业务假设
   - 探索性数据分析
   - 应急数据支持

3. **跨系统数据整合**
   - 数据分散在多个业务系统
   - 需要跨系统对比和汇总
   - 手工导出拼表效率低

4. **数据异常排查**
   - 业务异常需要快速定位数据问题
   - 需要灵活组合查询条件
   - 传统报表无法覆盖所有场景

5. **新系统数据探索**
   - 接入新的业务系统
   - 不熟悉数据结构
   - 需要快速了解数据内容

**不适用场景**

以下场景不建议使用OntiCards:

1. **固定报表需求**
   - 查询逻辑固定,每天/每周定时执行
   - 建议使用专业BI工具或定时任务

2. **实时数据监控**
   - 需要秒级或分钟级实时刷新
   - 建议使用实时数据平台

3. **复杂数据分析**
   - 需要复杂的统计模型
   - 需要机器学习预测
   - 建议使用专业数据分析工具

4. **大规模数据导出**
   - 需要导出百万级以上数据
   - 建议使用数据仓库或ETL工具

5. **数据写入场景**
   - 需要修改、删除数据
   - 需要批量导入数据
   - 建议使用专业数据管理工具

6. **超高并发场景**
   - 并发查询超过100个
   - 建议优化架构或使用缓存

**与其他工具的配合使用**

| 工具类型 | 配合方式 | 使用建议 |
|---------|---------|---------|
| BI工具 | 互补使用 | BI做固定报表,OntiCards做临时查询 |
| 数据仓库 | 数据源 | OntiCards可查询数据仓库 |
| Excel | 结果处理 | 查询结果可复制到Excel进一步分析 |
| SQL客户端 | 互补使用 | 复杂SQL可在客户端调试后使用 |
| 数据治理平台 | 数据源 | 数据卡片可作为数据字典的补充 |

## 六、数据安全与合规

### 6.1 访问控制机制

**用户级隔离**
- 每个用户只能访问自己添加的数据源
- 用户之间的数据源完全隔离
- 管理员可配置是否查看所有用户数据源

**角色权限**
- 普通用户：只能查询数据
- 管理员：可管理数据源、查看审计日志、管理用户
- 审计员：可查看审计日志，但不能修改配置

### 6.2 数据安全保障

**只读访问**
- 系统只允许SELECT查询
- 明确禁止INSERT/UPDATE/DELETE/DROP等操作
- SQL白名单校验，拦截危险操作

**连接信息保护**
- 数据库密码加密存储
- 界面不展示明文密码
- 日志中对连接信息脱敏

**查询安全**
- 结果数量限制，防止数据泄露
- 查询超时控制，防止资源耗尽
- 字段白名单，只能访问已声明的表和字段

### 6.3 审计与监控

**查询审计**
- 记录每次查询：用户、时间、问题、SQL、数据源、结果
- 支持按用户、时间、操作类型筛选
- 保留完整的查询历史

**异常监控**
- 监控频繁失败的查询
- 监控尝试访问未授权表的行为
- 监控异常大量数据提取

**健康监控**
- 数据源连接状态监控
- 查询响应时间监控
- 系统资源使用监控

### 6.4 合规性说明

**数据驻留**
- 业务数据始终保留在客户的数据库中
- 系统只在查询时临时访问
- 不存储业务数据

**审计要求**
- 完整的操作日志，满足审计要求
- 支持日志导出和归档
- 可追溯所有数据访问行为

**隐私保护**
- 用户数据隔离，保护隐私
- **敏感字段脱敏**（已实现）
  - 数据卡片生成环节：三档置信度分层预过滤 + 大模型智能兜底
  - 字段注释填充环节：复用同一套安全保障机制
- 符合数据保护法规要求

### 10.3 常见问题

**Q1: 系统会不会理解错我的问题?**
A: 系统采用了智能语义理解能力,大多数日常问题都能准确理解。如果理解有偏差,可以查看查询说明,调整表达方式,或使用意图确认功能。

**Q2: 如果数据库结构变了,需要做什么?**
A: 在系统中执行"刷新数据源"操作,系统会自动识别变化并更新数据卡片。

**Q3: 系统会不会泄露我的数据?**
A: 不会。系统采用多层安全机制:密码加密存储、用户数据隔离、只读访问、完整审计。业务数据始终保留在您的数据库中。

**Q4: 可以同时查询多少个数据源?**
A: 没有数量限制,但建议根据实际需求合理选择,过多数据源会影响查询性能。

**Q5: 查询结果的准确性如何保证?**
A: 系统会展示生成的SQL和查询说明,您可以验证查询逻辑。对于关键查询,建议先验证结果的正确性。
