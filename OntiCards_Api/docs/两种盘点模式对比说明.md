# 两种盘点模式对比说明文档(用户版)

> **面向对象**: 系统用户、数据分析师、业务人员
> **文档版本**: v3.0
> **最后更新**: 2026-02-27

---

## 一、为什么需要盘点功能?

想象一下,你的公司有多个数据库系统:
- **订单系统**: 存储订单、支付、物流数据
- **用户系统**: 存储用户信息、会员等级
- **商品系统**: 存储商品、库存、分类

当你想查询"最近购买了手机的VIP用户有哪些"时,就需要从这三个系统中把数据关联起来。

**问题来了**:
1. **字段命名不统一**: 订单系统叫`buyer_id`,用户系统叫`user_id`,怎么关联?
2. **不知道如何关联**: 订单表和用户表该通过哪个字段连接?
3. **AI助手不够聪明**: LLM生成的查询语句经常出错,因为不知道表之间的关系
4. **数据融合困难**: 从多个表查出的数据该如何合并?

**盘点功能就是来解决这些问题的!** 它会帮你:
- 理清数据表之间的关系
- 找出哪些字段可以互相对应
- 让AI助手更准确地生成查询
- 让数据融合更加智能

## 二、两种盘点模式是什么?

系统提供了两种盘点方式,就像"精准手术"和"全面体检"的区别:

### 模式一: **定向盘点** (精准优化)

**比喻**: 就像你去医院做"定向检查" —— 你告诉医生想检查哪些部位,医生针对性地做深度检查,给出详细的改进建议。

**特点**:
- **你主动选择**要盘点哪些表(目标表)和参考哪些表(参考表)
- 系统会深入分析每个字段,推荐更准确的字段注释
- 系统会分析表与表之间的关联关系
- 你可以确认或修改推荐结果
- 适合对特定表做精细化优化

**核心功能**:
1. **字段注释推荐** - 为LLM填充的注释推荐更准确的注释
2. **表关系推断** - 找出目标表和参考表之间的关联关系
3. **关系卡片生成** - 生成表关系说明书

**适用场景**:
- 新接入了几张表,想快速优化它们的字段注释
- 想弄清楚某几张关键表之间的关系
- 需要对局部数据做精细管理
- 你知道哪些表是重点,想针对性优化

---

### 模式二: **全域盘点** (全面扫描)

**比喻**: 就像你去医院做"全面体检" —— 医生自动对全身各个系统做扫描,生成一份完整的健康报告和关系网络图。

**特点**:
- **系统自动扫描**整个数据源的所有表
- 自动分析所有表之间的关系,生成完整的"关系地图"
- 支持跨数据源分析(比如订单库和用户库的关系)
- 一键执行,自动完成
- 适合构建完整的数据关系图谱

**核心功能**:
1. **全表关系发现** - 自动分析数据源中所有表的关系
2. **以表为中心的关系卡片** - 为每张表生成关系档案
3. **跨数据源关系** - 发现不同数据源之间的关联关系

**适用场景**:
- 刚接入一个新数据源,想全面了解它的结构
- 想构建完整的数据关系网络
- 需要支持复杂的跨表查询和数据融合
- 有多个数据源需要打通

---

## 三、两种模式的核心区别(白话版)

### 3.1 选择范围不同

| 对比项 | 定向盘点 | 全域盘点 |
|-------|---------|---------|
| **你要做什么** | 自己选择目标表和参考表 | 系统自动扫描所有表 |
| **就像** | 点菜 —— 你选什么菜就做什么菜 | 自助餐 —— 所有菜品都上齐 |
| **优点** | 精准可控,想盘点什么就盘点什么 | 全面完整,不会遗漏任何表 |
| **缺点** | 需要你知道选哪些表 | 如果表太多会比较慢 |
| **API路径** | `/target_inventory/run` | `/global_inventory/discover` |

---

### 3.2 分析深度不同

| 对比项 | 定向盘点 | 全域盘点 |
|-------|---------|---------|
| **分析粒度** | **字段级 + 表级** | **仅表级** |
| **就像** | 显微镜 —— 看到每个细胞 | 望远镜 —— 看到整体架构 |
| **能做什么** | **优化字段注释** + 发现表关系 | 仅发现表关系 + 构建关系网络 |
| **适合什么** | 精细化数据治理 | 全局关系梳理 |
| **字段注释** | ✅ 推荐更准确的注释 | ❌ 不涉及字段注释 |

---

### 3.3 参与程度不同

| 对比项 | 定向盘点 | 全域盘点 |
|-------|---------|---------|
| **你的参与度** | 高 —— 需要选择表并确认推荐结果 | 低 —— 系统自动完成 |
| **就像** | 定制服装 —— 需要试穿调整 | 成衣 —— 直接穿走 |
| **好处** | 确保结果符合你的预期 | 省时省力,快速见效 |
| **耗时** | 1-5秒(取决于选择的表数量) | 5-120秒(取决于表总数) |

---

### 3.4 支持能力不同

| 对比项 | 定向盘点 | 全域盘点 |
|-------|---------|---------|
| **数据源支持** | 单数据源 | **单数据源 + 多数据源** |
| **跨源关系** | ❌ 不支持 | ✅ 支持（自动标记is_cross_source） |
| **字段画像** | ✅ 支持（用于字段推荐） | ✅ 支持（用于关系推断） |
| **并行策略** | 串行或可配置 | 线程池并行（max_workers=5） |

---

## 四、两种模式的产物和作用

### 4.1 定向盘点的产物

#### 产物一: **字段注释优化建议** (核心特色!)

**是什么**:
系统会对目标表中每个LLM填充的字段,基于参考表和字典文件,推荐更准确的注释。

**举例**:
```
字段: buyer_id
当前注释: 买家标识 (LLM自动填充的,可能不够准确)
推荐注释: 用户唯一标识 (来自参考表 user_info.user_id)
置信度: 85%
推荐理由: 字段名相似、语义相似、数据类型匹配
```

**有什么用**:
- 让字段注释更加规范和准确
- 帮助你和团队快速理解数据含义
- 让AI助手更准确地理解数据结构

**意义**:
提升数据元数据质量,为数据治理打下基础。

---

#### 产物二: **表关系映射**

**是什么**:
系统会分析目标表和参考表的所有字段,找出它们之间的关联关系。

**举例**:
```
关系: orders.buyer_id ←→ users.user_id
类型: 外键关联 (foreign_key)
置信度: 95%
说明: 订单表通过buyer_id字段关联到用户表的user_id字段
```

**有什么用**:
- 让你知道如何把不同表的数据关联起来
- 为后续的跨表查询提供指导
- 帮助AI助手正确生成JOIN语句

**意义**:
理清数据关系,为复杂查询和数据融合做准备。

---

#### 产物三: **关系卡片**

**是什么**:
为每对有关联的表生成一张"关系说明书",包含关联字段、关系类型、使用建议等信息。

**举例**:
```
关系卡片: orders ←→ users
关联方式: orders.buyer_id = users.user_id
关系方向: 多对一 (many_to_one)
业务含义: 每个订单都属于一个用户
联表建议: 使用LEFT JOIN,避免遗漏订单数据
融合建议: 以user_id作为主键进行数据合并
```

**有什么用**:
- 为AI助手提供详细的关系信息
- 指导如何正确地进行数据关联和融合
- 作为数据文档,帮助新人快速理解系统

**意义**:
形成可复用的知识资产,长期提升查询和分析效率。

---

### 4.2 全域盘点的产物

#### 产物一: **完整关系网络**

**是什么**:
系统自动分析数据源中所有表,找出所有可能的关联关系,形成一张完整的"关系地图"。

**举例**:
```
数据源: 电商数据库(8张表)
发现的关系:
1. orders ←→ users (通过buyer_id)
2. orders ←→ products (通过product_id)
3. orders ←→ payments (通过order_id)
4. orders ←→ logistics (通过order_id)
5. products ←→ categories (通过category_id)
... 共25个关系
```

**有什么用**:
- 全面了解数据源的整体结构
- 快速找到任意两张表的关联路径
- 支持复杂的多表联查

**意义**:
构建数据资产地图,为所有下游应用提供基础设施。

---

#### 产物二: **以表为中心的关系卡片** (核心特色!)

**是什么**:
为每张表生成一张"关系档案",记录它与其他所有表的关联情况。

**特点**: 不同于定向盘点的"表对关系卡片",全域盘点生成的是"表中心关系卡片"

**举例**:
```
表: orders (订单表)
关联的表:
1. users —— 通过buyer_id关联,获取用户信息
2. products —— 通过product_id关联,获取商品信息
3. payments —— 通过order_id关联,获取支付信息
4. logistics —— 通过order_id关联,获取物流信息

统计信息:
- 关联表数量: 4张
- 平均置信度: 92%
- 关系强度: 0.89
```

**有什么用**:
- 快速了解某张表的"社交圈"(它跟谁有关系)
- 为AI助手提供上下文信息
- 支持智能推荐(当用户查询订单时,自动推荐可以关联的表)

**意义**:
从表的视角组织关系信息,让查询和分析更加智能化。

---

#### 产物三: **跨数据源关系** (全域盘点独有!)

**是什么**:
如果你对多个数据源同时做全域盘点,系统还能发现不同数据源之间的关联关系。

**举例**:
```
跨源关系:
订单库.orders.buyer_id ←→ 用户库.users.user_id
标记: is_cross_source = true
from_datasource_id: ds-001 (订单库)
to_datasource_id: ds-002 (用户库)
from_datasource_name: "订单数据库"
to_datasource_name: "用户数据库"
```

**有什么用**:
- 支持跨库查询和数据整合
- 打破数据孤岛,实现全局数据视图
- 让AI助手能够处理跨系统的复杂查询

**意义**:
实现企业级数据融合,提升数据价值。

## 五、在聚合检索中的作用(核心价值)

### 5.1 什么是聚合检索?

当你问AI助手"查询最近购买了手机的VIP用户",AI需要:
1. **理解问题**: 涉及用户、订单、商品三张表
2. **生成SQL**: 编写多表联查语句
3. **执行查询**: 从多个表获取数据
4. **融合结果**: 把来自不同表的数据合并成完整的答案

盘点功能在这个过程中的**第2步(生成SQL)**和**第4步(融合结果)**发挥关键作用!

---

### 5.2 作用阶段一: 多表联查SQL生成

#### 没有盘点功能时的问题

**AI助手的困惑**:
```
用户问: "查询最近购买了手机的VIP用户"
AI想: 我需要关联users、orders、products三张表
AI不知道:
- orders表的buyer_id对应users表的哪个字段?
- orders表的product_id对应products表的哪个字段?
- 应该用INNER JOIN还是LEFT JOIN?
```

**结果**: AI生成的SQL经常出错
```sql
-- 错误的SQL (瞎猜字段名)
SELECT u.name, o.order_id
FROM users u
JOIN orders o ON u.id = o.user_id  -- ❌ 错了!实际是buyer_id
JOIN products p ON o.prod_id = p.id  -- ❌ 又错了!实际是product_id
WHERE ...
```

---

#### 有盘点功能后的改进

**AI助手获得的信息(来自关系卡片)**:
```
// 来自定向盘点或全域盘点
关系1: orders.buyer_id ←→ users.user_id (置信度95%)
关系2: orders.product_id ←→ products.id (置信度98%)

// 来自定向盘点的字段注释(额外加分!)
users.vip_level: "会员等级(1-5,5为最高)"
```

**结果**: AI生成的SQL准确无误
```sql
-- 正确的SQL (基于盘点信息)
SELECT u.name, u.vip_level, o.order_id, o.create_time
FROM orders o
LEFT JOIN users u ON o.buyer_id = u.user_id  -- ✓ 正确!
LEFT JOIN products p ON o.product_id = p.id  -- ✓ 正确!
WHERE o.create_time >= DATE_SUB(NOW(), INTERVAL 1 MONTH)
  AND p.category = '手机'
  AND u.vip_level >= 3
```

**提升效果**:
- **JOIN条件准确率**: 从70%提升到95% (↑25%)
- **多表查询成功率**: 从60%提升到90% (↑30%)
- **减少错误**: 笛卡尔积问题减少80%

---

### 5.3 作用阶段二: 结果融合

#### 什么是结果融合?

有时候,AI助手需要分别查询多个表,然后把结果合并:
```
步骤1: 从orders表查出订单数据 → [订单A, 订单B, 订单C]
步骤2: 从users表查出用户数据 → [用户1, 用户2, 用户3]
步骤3: 把订单和用户数据合并 → 订单A属于用户1, 订单B属于用户2...
```

**问题**: 怎么知道哪个订单属于哪个用户?

---

#### 三重融合机制(定向盘点 + 全域盘点的产物)

**机制一: 表结构主外键匹配**
- 识别标准的ID字段(如`user_id`, `order_id`)
- 自动匹配主键和外键关系

**机制二: LLM语义分析**
- 对于没有明显ID模式的字段,通过语义理解匹配
- 例如: `buyer_id` 和 `user_id` 虽然名字不同,但语义相同

**机制三: 关系卡片信息(盘点产物的核心价值!)**
- 从关系卡片(TableRelationship或TableRelationshipCard)中读取明确的关联关系
- 例如: `orders.buyer_id = users.user_id` (置信度95%)
- **优先级最高** —— 如果关系卡片有明确信息,直接使用

**融合策略**:
```
如果关系卡片有明确信息 → 直接使用 (准确率95%+)
否则,使用LLM语义分析 → 推断关系 (准确率80%+)
最后,使用表结构匹配 → 兜底方案 (准确率70%+)
```

---

#### 举例说明

**场景**: 分别查询订单和用户信息后合并

**没有盘点信息时**:
```
订单数据:
[{order_id: 1001, buyer_id: "U123", amount: 299}]

用户数据:
[{user_id: "U123", name: "张三", vip_level: 5}]

系统困惑: buyer_id和user_id是同一个东西吗? 🤔
结果: 可能融合错误或放弃融合
```

**有盘点信息时**:
```
订单数据:
[{order_id: 1001, buyer_id: "U123", amount: 299}]

用户数据:
[{user_id: "U123", name: "张三", vip_level: 5}]

关系卡片告诉系统: orders.buyer_id = users.user_id ✓

融合结果:
[{
  order_id: 1001,
  buyer_id: "U123",
  amount: 299,
  user_name: "张三",  ← 自动合并
  vip_level: 5        ← 自动合并
}]
```

**提升效果**:
- **融合准确率**: 从75%提升到95% (↑20%)
- **融合速度**: 减少50%的LLM推断时间
- **用户体验**: 答案更完整,更可靠

## 六、如何选择使用哪种模式?

### 决策树

```
你的需求是什么?
│
├─ 我想优化某几张表的字段注释
│  └─ 使用 **定向盘点**
│     场景: 新接入表、注释缺失、需要精细化管理
│     特点: 提供字段注释推荐 (全域盘点不提供)
│
├─ 我想全面了解数据源的表关系
│  └─ 使用 **全域盘点**
│     场景: 新数据源、构建关系图谱、支持复杂查询
│     特点: 一键扫描所有表
│
├─ 我想打通多个数据源
│  └─ 使用 **全域盘点(多数据源模式)**
│     场景: 跨库查询、数据整合
│     特点: 支持跨数据源关系发现 (定向盘点不支持)
│
└─ 我想两个都做
   └─ 推荐策略: 先全域后定向
      Step 1: 全域盘点 → 构建完整关系网络
      Step 2: 定向盘点 → 对重点表做字段注释优化
```

---

### 常见场景推荐

| 场景 | 推荐模式 | 理由 |
|-----|---------|------|
| 刚接入新数据源 | 全域盘点 | 快速了解整体结构 |
| 新接入一批表 | 定向盘点 | 精准优化字段注释,节省时间 |
| 字段注释质量差 | **定向盘点** | 提供字段注释推荐 (全域盘点不提供) |
| 需要复杂跨表查询 | 全域盘点 | 构建完整关系网络 |
| 跨数据源分析 | **全域盘点(多源)** | 发现跨源关系 (定向盘点不支持) |
| 数据治理项目 | 先全域后定向 | 全面梳理+重点优化 |

## 七、两种模式的协同效应

### 推荐组合策略

#### 策略一: 全域打基础,定向做优化

```
第1步: 全域盘点
  目的: 构建完整的数据关系地图
  产物: 所有表的关系网络 + 以表为中心的关系卡片

第2步: 分析全域盘点结果
  发现: 哪些表是核心表? 哪些关系不够清晰?

第3步: 针对核心表执行定向盘点
  目的: 优化字段注释,精细化管理
  产物: 准确的字段注释推荐 + 精确的表关系

第4步: 持续维护
  全域盘点: 每月执行1次,保持关系地图最新
  定向盘点: 按需执行,持续优化重点表
```

---

#### 策略二: 分层管理

```
第一层: 数据源级(全域盘点)
  管理: 整个数据源的表关系网络
  频率: 每月1次

第二层: 主题域级(定向盘点)
  管理: 按业务域分组的表(如订单域、用户域、商品域)
  频率: 每季度1次

第三层: 核心表级(定向盘点)
  管理: 单张表的精细化优化(字段注释)
  频率: 按需执行
```

## 十、常见问题解答

### Q1: 我该先用哪种模式?

**建议**: 如果是新数据源,先用**全域盘点**,再用**定向盘点**。
- 全域盘点让你快速了解全貌
- 定向盘点让你精细优化字段注释

---

### Q2: 两种模式的结果会冲突吗?

**不会**。两种模式是互补的:
- 定向盘点: 优化字段注释 + 局部关系 (存储在TargetInventoryJobResult)
- 全域盘点: 完整关系网络 (存储在TableRelationship和TableRelationshipCard)

它们的结果存储在不同的表中,互不影响,可以叠加使用。

---

### Q3: 执行盘点会影响数据库性能吗?

**影响很小**:
- 盘点只读取元数据(表结构、字段信息)和数据卡片
- 不会修改业务数据
- 不会执行复杂的业务查询
- 对数据库的负载可以忽略不计

---

### Q4: 盘点结果需要定期更新吗?

**建议**:
- **全域盘点**: 每月执行1次,保持关系地图最新
- **定向盘点**: 按需执行,当表结构变化或新增表时
- 如果数据结构稳定,全域盘点可以延长到每季度1次

---

### Q5: 盘点后,AI助手的准确率能提升多少?

**实际效果**(基于内部测试):
- SQL生成准确率: 70% → 95% (↑25%)
- 多表查询成功率: 60% → 90% (↑30%)
- 数据融合准确率: 75% → 95% (↑20%)
- 用户满意度: 显著提升

---

### Q6: 我需要懂技术才能使用盘点功能吗?

**不需要**!
- 界面操作简单,点几个按钮就能完成
- 系统会给出清晰的推荐和说明
- 你只需要根据业务知识做确认即可
- 就像用体检报告一样,看懂结果比懂医学更重要

---

### Q7: 定向盘点和全域盘点的API路径是什么?

**定向盘点**:
- 获取表列表: `GET /target_inventory/tables?datasource_id=xxx`
- 启动盘点: `POST /target_inventory/run`
- 确认结果: `POST /target_inventory/confirm`

**全域盘点**:
- 启动盘点: `POST /global_inventory/discover`
- 查询关系卡片: `GET /global_inventory/card/{datasource_id}/{table_name}`
- 批量查询: `POST /global_inventory/batch_cards`
