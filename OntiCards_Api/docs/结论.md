## 结论

我把你上传的前后端源码和日志对照检查了一遍，**根因基本可以确认**：

> **Gunicorn 使用了 --preload，但应用在 Gunicorn fork 工作进程之前已经执行了多次数据库查询，导致 SQLAlchemy 连接池里的 psycopg2/libpq 连接被多个 worker 进程继承。并发请求到来后，多个进程可能操作同一个 PostgreSQL TCP 连接，从而出现结果串线、游标状态错乱。**

这正好会产生日志中的两种异常：

```text
psycopg2.DatabaseError:
error with status PGRES_TUPLES_OK and no message from the libpq
sqlalchemy.exc.ResourceClosedError:
This result object does not return rows.
It has been closed automatically.
```

其中 `PGRES_TUPLES_OK` 本来表示查询成功并返回了可读取的数据行，不是数据库正常返回的失败状态；现在却同时抛出 `DatabaseError`，说明客户端拿到的结果对象状态已经不一致。([postgresql.org](https://www.postgresql.org/docs/current/libpq-exec.html?utm_source=chatgpt.com))

```text

        ↓

        ↓
```

SQLAlchemy 官方明确说明：连接池中的 TCP 连接不能被 fork 后的多个进程继承，否则不同 Python 进程可能并发访问同一个文件描述符，最常见结果就是数据库消息协议损坏和结果串线。([SQLAlchemy 文档](https://docs.sqlalchemy.org/en/20/core/pooling.html))

Psycopg 官方也说明，连接可以用于普通线程，但不应该被 fork 后的进程共享；采用 fork 型部署方式时，连接必须在 fork 之后创建。([Psycopg](https://www.psycopg.org/docs/usage.html))

# 四、最少改动的修复方式

你当前可以继续保留 `--preload`，但是必须在启动初始化执行完之后、Gunicorn fork 之前清空连接池。

修改：

```text
app.py
```

在：

```python
ensure_prompt_configs_initialized(app)
```

下面增加：

```python
# Gunicorn 使用 --preload 时，以上数据库初始化查询会在 master 进程执行。
# fork worker 前清空 master 创建的 Session 和连接池，
# 避免 PostgreSQL/libpq 连接被多个 worker 继承。
with app.app_context():
    db.session.remove()
    db.engine.dispose()
```

修改后文件底部应为：

```python
app = create_app()
app.json.ensure_ascii = False

# 初始化提示词配置
ensure_prompt_configs_initialized(app)

# 关键修复：
# 清空 preload 阶段创建的数据库连接，确保 worker 启动后各自新建连接。
with app.app_context():
    db.session.remove()
    db.engine.dispose()

if __name__ == '__main__':
    env = Env()
    env.read_env()
    port = env.str('PORT') if env.str('PORT') else 9000
    app.run(port=port, host='0.0.0.0', debug=False)
```

这样当前启动流程会变为：

```text
master 执行初始化查询
        ↓
db.engine.dispose() 关闭并清空连接池
        ↓
fork worker
        ↓
每个 worker 首次请求时建立自己的 PostgreSQL 连接
```

SQLAlchemy 官方也把“在创建子进程前执行 `Engine.dispose()`”列为解决 fork 连接继承的标准方式。([SQLAlchemy 文档](https://docs.sqlalchemy.org/en/20/core/pooling.html))

# 五、更正式的生产修复

更稳妥的方式是在 Gunicorn worker fork 后，强制为每个 worker 重建连接池。

在：

```text
gunicorn.py
```

增加：

```python
def post_fork(server, worker):
    """
    Gunicorn master 使用 preload 加载应用后，
    worker fork 完成时丢弃继承的 SQLAlchemy 连接池。
    """
    from app import app
    from extensions.ext_database import db

    with app.app_context():
        db.session.remove()
        db.engine.dispose(close=False)

    server.log.info(
        "SQLAlchemy connection pool recreated for worker pid=%s",
        worker.pid,
    )
```

然后在：

```text
docker/entrypoint.sh
```

的 Gunicorn 命令中增加配置文件：

```bash
gunicorn \
  --config /current_prod_vigor_api/gunicorn.py \
  --bind "${DIFY_BIND_ADDRESS:-0.0.0.0}:${DIFY_PORT:-9103}" \
  --workers ${GUNICORN_WORKERS:-2} \
  --worker-class ${GUNICORN_WORKER_CLASS:-gthread} \
  --threads ${GUNICORN_THREADS:-6} \
  --worker-connections ${GUNICORN_WORKER_CONNECTIONS:-200} \
  --timeout ${GUNICORN_TIMEOUT:-28800} \
  --graceful-timeout ${GUNICORN_GRACEFUL_TIMEOUT:-30} \
  --max-requests ${GUNICORN_MAX_REQUESTS:-1000} \
  --max-requests-jitter ${GUNICORN_MAX_REQUESTS_JITTER:-100} \
  --log-level ${GUNICORN_LOG_LEVEL:-warning} \
  --preload \
  app:app
```

SQLAlchemy 官方更推荐在子进程初始化阶段执行：

```python
engine.dispose(close=False)
```

这样子进程不会接触父进程的连接，而是建立自己的新连接池。([SQLAlchemy 文档](https://docs.sqlalchemy.org/en/20/core/pooling.html))

对于当前项目，建议同时保留前面的：

```python
db.engine.dispose()
```

作为第一层保护，或者采用 `post_fork` 方案作为长期修复。

## 最终判断

这次异常不是治理接口代码本身，也不是 `users.id`、UUID、分页查询或前端 `Promise.all` 的错误。

**最核心的代码组合是：**

```text
docker/entrypoint.sh 使用 --preload
+
app.py 在模块导入阶段访问数据库
+
SQLAlchemy QueuePool 保留了启动阶段连接
+
Gunicorn fork 两个 worker
+
多个 worker 继承同一个 psycopg2/libpq TCP 连接
```

优先执行这两个修改即可：

```python
# app.py：初始化完成后
with app.app_context():
    db.session.remove()
    db.engine.dispose()
# config.py
'pool_pre_ping': True,
```

然后重新构建并完整重建容器，而不是只执行 restart：

```bash
docker compose down
docker compose build --no-cache
docker compose up -d
```

仅执行：

```bash

```

不会加载新镜像中的代码。
