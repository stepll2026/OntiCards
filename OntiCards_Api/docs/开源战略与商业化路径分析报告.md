## 一、项目概述

### 1.1 项目背景

OntiCards 作为一款面向 B 端企业的智能数据中枢产品，经历了多轮迭代，已形成完整的产品矩阵（自然语言查询、数据盘点、数据治理-质检、SSO、术语库等）。

在当前的市场推广和产品演进过程中，团队遇到了显著的瓶颈：

#### 商务层面的瓶颈

- **售前成本高**：从客户接触到签合同，需要无偿部署（前后端+数据库+模型）、长期试用陪跑、demo 搭建
- **人力投入大**：教客户搭智能体 demo、优化数据卡片内容、提升问数准确性
- **依赖合作方**：必须绑定火山引擎 HiAgent 等平台联合推广，且需要利润分成
- **品牌弱势**：作为初创公司，知名度不足，直客获取困难

#### 产品层面的瓶颈

- **内部测试场景单一**：团队规模有限，只能在自有的几个客户场景下做测试，覆盖不到各行各业的真实业务环境
- **迭代反馈链路长**：客户反馈→销售转发→产品整理→研发修复→客户验证，链路冗长
- **生态扩展乏力**：新数据源、新行业模板、新插件的扩展完全依赖团队自身人力
- **品牌信任建立慢**：闭源软件需要客户做大量尽调才能建立信任

### 1.2 项目核心目标

**开源带来三大战略价值：商务赋能、产品进化、生态共建。**

### 1.3 项目核心原则


| 原则          | 说明                         |
| ----------- | -------------------------- |
| **开源代码即门面** | 开源出去的代码必须规范、整洁，体现团队工程能力    |
| **场景完整性**   | 开源版需覆盖主要业务场景，让客户能跑通完整闭环    |
| **服务即变现**   | 商业增值服务是真正的变现来源，不是"功能升级"    |
| **可持续运营**   | 开源社区和商业服务并行推进，相互导流         |
| **社区即测试者**  | 拥抱社区反馈，把外部用户当作免费的质量团队和需求来源 |

## 二·附、开源对产品本身的赋能价值

> 本节专门阐述**开源对产品本身**的战略价值，而非商务层面。
> 商务层面价值已在 1.2 节阐述。

### A.1 价值一：让真实用户成为免费测试者

**核心逻辑**：

- 闭源产品只能靠内部 QA + 少量种子客户测试，覆盖场景有限
- 开源产品被下载到各行各业的真实生产环境，**部署量就是测试覆盖量**
- 用户在实际业务中遇到的问题，比内部测试更真实、更刁钻、更全面

**具体收益**：


| 收益           | 说明                                          |
| ------------ | ------------------------------------------- |
| **多样化场景覆盖**  | 金融、制造、零售、教育、医疗等不同行业用户带来不同数据源、不同业务场景、不同负载    |
| **真实生产环境验证** | 大数据量、高并发、复杂权限、极端边界条件都是真实环境才有的               |
| **Bug 提前暴露** | 闭源阶段往往要在客户现场才发现的问题，开源阶段在 GitHub Issue 上就能看到 |
| **改进点反向输入**  | 用户提交的功能建议、API 设计建议、文档改进点往往比内部讨论更接地气         |
| **降低内部测试成本** | 用户成为"分布式测试团队"，部分 QA 工作外移                    |


**预期指标**：

- 6 个月内外部 Issue 数 ≥ 50 个
- 12 个月内外部 PR 数 ≥ 20 个（合入 ≥ 6 个）
- 关键 Bug（如阻塞性、数据准确性）100% 通过 Issue 跟踪

### A.2 价值二：加速产品迭代速度

**核心逻辑**：

- 内部迭代：需求→设计→开发→内部测试→客户试用→反馈→修改（周期 2-4 周）
- 开源迭代：用户使用→Issue 反馈→团队响应→快速修复→版本发布（周期 3-7 天）

**具体收益**：


| 收益         | 说明                                   |
| ---------- | ------------------------------------ |
| **缩短反馈链路** | 用户直接提 Issue，省去销售/客服中转，反馈链路从 5 步变 2 步 |
| **提升响应速度** | 公开的 Issue 有"社交压力"，团队响应更及时            |
| **优先级更准确** | 用户点赞、复现、补充说明，比内部拍脑袋的优先级排序更准          |
| **快速版本验证** | 每周/每两周发版，开源用户自动升级，验证速度提升 5-10 倍      |
| **降低试错成本** | 闭源阶段客户不敢用新功能，开源阶段用户可以自行尝鲜，反馈成本低      |


**预期指标**：

- 开源后每月发版 2 次以上（v1.0 后）
- 用户 Issue 平均首次响应 ≤ 24 小时
- Issue 平均关闭时间 ≤ 7 天（普通 Bug）

### A.3 价值三：共建产品生态与拓展使用场景

**核心逻辑**：

- 闭源产品只能由团队自己扩展数据源、行业模板、插件
- 开源产品有"看不见的开发者团队"在帮我们拓展边界

**具体可想象的扩展方向**：

#### 1. 第三方数据源连接器（贡献方向 #1）

```
典型场景：

- 覆盖更多客户的数据栈，降低销售阻力

```

#### 2. 行业模板与场景包（贡献方向 #2）

典型场景：

#### 4. 集成与插件生态（贡献方向 #4）

**预期指标**：

- 12 个月内出现 ≥ 5 个第三方数据源连接器
- 12 个月内出现 ≥ 3 个行业模板包
- 12 个月内出现 ≥ 10 个社区贡献者
- 12 个月内出现 ≥ 3 家系统集成商合作伙伴

### A.4 价值四：建立技术品牌与开发者心智

**核心逻辑**：

- 闭源产品在开发者群体中"看不见"
- 开源产品在 GitHub、Hacker News、掘金、CSDN、技术大会上有"曝光位"

**具体收益**：


| 收益         | 说明                                  |
| ---------- | ----------------------------------- |
| **招聘加分**   | 开发者更愿意加入有开源项目的公司，技术招聘竞争力提升          |
| **技术大会演讲** | 开源项目更容易获得技术大会的演讲邀请                  |
| **媒体曝光**   | OSCHINA、InfoQ、掘金等技术媒体的报道            |
| **客户信任**   | 客户在做尽调时可以直接看 GitHub 代码，比"商业宣传"更有说服力 |
| **建立标准**   | 争取成为某个细分领域的事实标准（如 NL2SQL、智能问数）      |


**预期指标**：

- 6 个月内 OSCHINA、InfoQ 等媒体报道 ≥ 3 篇
- 12 个月内在技术大会演讲 ≥ 2 次

### A.5 价值五：促进内部工程质量提升

**核心逻辑**：

- "开源的代码必须能见人"，倒逼团队提升工程标准
- "白盒交付"的代码必须可读、可维护、有文档

**具体收益**：


| 收益         | 说明                         |
| ---------- | -------------------------- |
| **代码质量提升** | 阶段 1 的代码规整不只是为了开源，更是为长期维护  |
| **文档意识增强** | 每个模块都需要 README、API 文档、设计文档 |
| **架构更清晰**  | 强行解耦，强制抽象，避免"意大利面代码"       |
| **测试覆盖加强** | 开源用户的"挑剔眼光"会逼着团队补齐测试       |
| **错误处理规范** | 用户对错误信息的容忍度更低，倒逼团队规范化      |


### A.6 价值六：构建数据飞轮与产品演进护城河

**核心逻辑**：

- 用户用得越多，反馈越多，产品越好
- 产品越好，吸引更多用户，反馈更多
- 这就是开源的"飞轮效应"

**数据飞轮示意**：

```
         用户使用
            ↓
       反馈 Issue / PR
            ↓
       团队响应 + 迭代
            ↓
       产品更稳定、功能更完善
            ↓
       吸引更多用户 ←──┐
            ↓          │
         用户使用 ──────┘
              (循环)
```

**飞轮价值**：

- 早期冷启动可能慢，但一旦转动起来就形成壁垒
- 竞争对手即使"复制代码"，也复制不了"社区氛围"
- 用户沉淀的模板、案例、配置成为产品护城河

## 三、范围说明

| 类别       | 内容                        |
| -------- | ------------------------- |

| **商业产品** | 权限管理系统、数据治理第二阶段开发         |

| **社区运营** | Issue 处理、技术博客、社区互动        |


#### 不包含的工作


| 类别                    | 说明                             |
| --------------------- | ------------------------------ |
| **前端重构**              | 仅做必要的兼容性和主题适配，不做大规模前端重构        |
| **数据库迁移**             | 保持 PostgreSQL 元数据库不变           |
| **国产化深度适配**           | 保持现有 KingBase/OceanBase/达梦支持深度 |
| **SaaS 化改造**          | 商业版仍以独立部署为主，不做 SaaS 平台         |

- 团队现有 3-5 名研发人员可以投入（部分时间）
- 产品现有代码可以正常运行，关键功能无 P0 级 bug
- 已有 1-2 家潜在客户可作为种子用户验证开源版
- 法务资源可支持许可证审核
- 商业版可以基于现有代码模块增量开发

## 四、开源版本与商业版本边界定义

> ⚠️ **版本边界说明**（2026年8月10日确认）

### 4.1 开源基础版（Free Open Source）

以下功能纳入开源版本，客户可自行部署使用：


| 功能模块           | 具体功能                                              | 开源理由               |
| -------------- | ------------------------------------------------- | ------------------ |
| **数据质检（第一阶段）** | 规则库管理、三种规则创建模式、规则执行、质量评分、AI报告生成                   | 完整的数据质量发现问题能力，技术亮点 |

#### 阶段 5·附：开源与商业的双向飞轮

> 阶段 5 的商业化推进，**不是脱离开源独立运作**，而是与阶段 3 的开源运营形成双向飞轮。

**飞轮模型**：

```
        开源社区                                    商业客户
           │                                          │
           │  自助使用 → 试用客户                        │
           ├─────────────────────────────────────────→ │
           │                                          │
           │  ←─────────────────────────────────────────┤
           │  反哺：商业客户的深度需求反向优化开源版     │
           │                                          │
           │  ←─────────────────────────────────────────┤
           │  反哺：商业客户的真实案例丰富官网/文档       │
           │                                          │
           │  自下而上：贡献者、合作伙伴、案例              │
           │  自上而下：商业反哺、案例反哺、需求反哺        │
```

**关键联动机制**：


| 联动点      | 商务反哺开源           | 开源反哺商务            |
| -------- | ---------------- | ----------------- |
| **产品功能** | 商业客户的定制需求，抽象后开源  | 开源社区的最佳实践，引入商业版   |
| **行业场景** | 商业客户的行业案例，丰富官网   | 开源贡献者的行业模板，给商业做参考 |
| **销售线索** | 商业客户的成功故事，作为销售物料 | 开源用户的咨询，反哺销售线索    |
| **招聘**   | 商业团队扩张需要人才       | 开源品牌带来更好的人才招聘     |


**核心原则**：

- ✅ 商业版的成功案例可以脱敏后用作开源版宣传
- ✅ 开源版的活跃数据可以作为商务谈判的"信任背书"
- ✅ 商业客户的需求优先级 ≥ 开源社区的需求优先级（付费客户第一）
- ❌ 避免商业版完全脱离开源版独立演进（避免双产品分裂）

### 10.1 风险矩阵


| 风险             | 发生概率 | 影响程度 | 风险等级 | 应对预案                        |

| **商业版差异化不足**   | 中    | 高    | 🟡 中 | 持续打磨智能体搭建服务，构建服务壁垒          |
| **法务合规问题**     | 低    | 高    | 🟢 低 | 提前咨询法务，许可证选择保守              |
| **种子用户反馈差**    | 中    | 高    | 🟡 中 | 阶段 1 充分内部测试，阶段 2 小范围内测      |
| **团队资源不足**     | 中    | 高    | 🟡 中 | 优先级管理，非核心功能砍掉或延后            |
| **License 选错** | 低    | 高    | 🟢 低 | 选 AGPLv3（保护衍生作品），如需可后续调整    |
| **客户永远只用免费版**  | 中    | 中    | 🟢 低 | 服务能力作为核心壁垒，软件可降级销售          |


### 10.2 关键风险应对详情

#### 风险 1：代码规整工作量超预期

**触发条件**：

- 硬编码提示词超过预期数量
- 工具类代码分散严重，整合难度大
- 重构引入新 bug

**应对措施**：

1. 阶段 1 启动前做充分评估，量化工作量
2. 设置"非关键项延后"策略，聚焦核心代码
3. 每日 standup 同步进度，及时调整
4. 阶段 1 规划 2 周，但预留 1 周 buffer

#### 风险 2：社区冷启动

**触发条件**：

- 发布后 1 个月 GitHub Stars < 30
- 几乎无 Issue 和 PR
- 无用户反馈

**应对措施**：

1. 提前准备 5-10 家种子用户，发布前 1 周预热
2. 联系行业 KOL、技术媒体投稿
3. 在知乎、思否、CSDN 主动回答 NL2SQL 相关问题引流
4. 提供 GitHub Star 抽奖等激励机制
