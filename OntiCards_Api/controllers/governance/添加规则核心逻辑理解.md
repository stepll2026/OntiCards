# 添加规则核心逻辑理解文档

> 基于 `governance_api.py` 真实实现的梳理

---

## 一、三种模式的核心区分

### 1.1 模式定义


| 模式         | 英文标识   | 入口       | 核心能力                             |
| ---------- | ------ | -------- | -------------------------------- |
| **专家模式**   | 手动配置   | 专家模式 Tab | 用户直接指定表、列、规则类型、条件表达式             |
| **自然语言模式** | NL2SQL | 自然语言 Tab | 用户输入自然语言 → LLM/模式匹配 → 自动识别表/列/规则 |
| **模板导入模式** | 模板选择   | 模板 Tab   | 从规则模板库选择模板，可指定或默认应用表/列           |


### 1.2 模式对比


| 维度         | 专家模式   | 自然语言模式         | 模板模式    |
| ---------- | ------ | -------------- | ------- |
| **输入方式**   | 表单选择   | 自然语言文本         | 模板选择    |
| **表/列指定**  | 用户手动选择 | 自动识别（LLM+数据卡片） | 可指定，可默认 |
| **条件表达式**  | 用户手动输入 | 自动生成           | 模板自带    |
| **SQL 预览** | 支持     | 支持             | 支持      |
| **适用场景**   | 精确控制   | 快速配置           | 批量复用    |

## 二、三个作用域（Scope）的区分

### 2.1 作用域定义


| 作用域      | 英文标识    | target_table | target_column | 说明                  |
| -------- | ------- | ------------ | ------------- | ------------------- |
| **列级规则** | column  | ✅ 必填         | ✅ 必填          | 针对特定列的校验，如"手机号不能为空" |
| **表级规则** | table   | ✅ 必填         | ❌ 不填          | 针对整表的校验，如"订单总金额>0"  |
| **库级规则** | library | ❌ 不填         | ❌ 不填          | 针对整个规则库的质检计划        |


### 2.2 作用域区分依据

**不是由前端传参决定，而是由 `target_table` 和 `target_column` 的实际值决定：**

```
同时传入 target_table + target_column → 列级规则 (scope='column')
仅传入 target_table               → 表级规则 (scope='table')
都不传入                         → 错误（预览接口会报错）
```

### 2.3 实际代码逻辑（preview 接口）

```python
# governance_api.py 第 1440-1454 行
if target_column:
    # 列级规则：生成完整 SQL
    sql = adapter.build_check_sql(...)
else:
    # 表级规则：仅生成表级 SQL
    sql = adapter.build_table_check_sql(...)
```

## 三、核心接口解析

### 3.1 `/rules/parse` - 自然语言规则解析（已优化）

**用途**：在用户指定的表上，将自然语言转换为结构化规则配置

**请求参数**：

```json
{
    "user_input": "手机号码不能为空",
    "datasource_id": "e41f6654-7d36-4f21-b75e-deafbf0df178",
    "target_table": "users",
    "target_column": "phone",
    "db_type": "postgresql"
}
```

| 参数 | 必填 | 说明 |
|------|------|------|
| `user_input` | ✅ | 自然语言规则描述 |
| `datasource_id` | ✅ | 数据源 ID |
| `target_table` | ✅ | **用户必须指定目标表** |
| `target_column` | ❌ | 可选，指定则直接使用，未指定则自动推断 |
| `db_type` | ❌ | 数据库类型，默认 postgresql |

**处理流程**：

```
1. 前端传入 user_input + datasource_id + target_table (+ target_column)
         ↓
2. 后端验证 target_table 不能为空
         ↓
3. 获取目标表的 Schema（数据卡片优先，否则从数据库获取）
         ↓
4. 根据是否指定 target_column 分支处理:
         ↓
   ├─ 已指定列 → 调用 parse_with_column() 直接解析
   └─ 未指定列 → 调用 parse_for_table() 在表中推断列
         ↓
5. 生成 SQL 预览
         ↓
6. 返回解析结果供用户确认
```

**返回结构**：

```json
{
    "success": true,
    "primary": {
        "rule_type": "null_check",
        "target_table": "users",
        "target_column": "phone",
        "condition_expr": "phone IS NULL OR phone = ''",
        "severity": "warning",
        "confidence": 0.95,
        "needs_confirmation": false,
        "reasoning": "在指定表 users 的列 phone 上解析规则"
    },
    "alternatives": [],
    "sql_preview": "SELECT COUNT(*) as total, SUM(CASE WHEN phone IS NULL OR phone = '' THEN 1 ELSE 0 END) as failed FROM users",
    "target_table": "users",
    "target_column": "phone"
}
```

**列推断逻辑**：

当用户只指定表而未指定列时，系统按以下优先级推断列：

1. **注释匹配**：列的 `comment` 包含用户描述的关键词（如"手机号"）
2. **列名匹配**：列名包含用户描述的关键词
3. **数据类型+规则类型匹配**：根据规则类型匹配合适的数据类型列

**推断失败时返回**：

```json
{
    "success": false,
    "message": "无法解析规则描述，请检查输入或使用专家模式手动配置",
    "alternatives": [
        {"column": "mobile", "comment": "手机号码", "data_type": "varchar", "reasoning": "..."},
        {"column": "tel", "comment": "联系电话", "data_type": "varchar", "reasoning": "..."}
    ],
    "target_table": "users",
    "target_column": null
}
```

### 3.2 `/rules/preview` - SQL 预览

**用途**：生成最终的校验 SQL

**请求参数**：

```json
{
    "rule_type": "null_check",
    "target_table": "users",
    "target_column": "phone",
    "condition_expr": "column IS NULL OR column = ''",
    "db_type": "postgresql"
}
```

**作用域判断**：

```
target_column 存在 → 调用 build_check_sql() 生成列级 SQL
target_column 不存在 → 调用 build_table_check_sql() 生成表级 SQL
```

**返回示例**：

```json
{
    "success": true,
    "sql": "SELECT COUNT(*) as total, SUM(CASE WHEN phone IS NULL OR phone = '' THEN 1 ELSE 0 END) as failed FROM users",
    "scope": "column"
}
```

### 3.3 `/rules` POST - 创建规则

**用途**：保存规则到数据库

**请求参数**：

```json
{
    "rule_name": "用户手机号格式校验",
    "rule_type": "format",
    "library_id": "规则库ID",
    "target_table": "users",
    "target_column": "phone",
    "condition_expr": "phone !~ '^1[3-9]\\d{9}$'",
    "severity": "warning",
    "description": "手机号必须符合中国标准格式",
    "enabled": true
}
```

**支持多条件**（复合规则）：

```json
{
    "rule_name": "用户信息完整性校验",
    "rule_type": "composite",
    "library_id": "规则库ID",
    "target_table": "users",
    "conditions": [
        {"column": "phone", "rule_type": "null_check", "condition": "phone IS NULL OR phone = ''"},
        {"column": "email", "rule_type": "format", "condition": "email !~ '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\\.[A-Za-z]{2,}$'"}
    ],
    "condition_mode": "AND"
}
```

## 四、交互流程设计

### 4.1 专家模式（手动配置）

```
┌─────────────────────────────────────────────────────────┐
│  步骤1: 选择规则类型                                     │
│  ├─ null_check (空值检查)                               │
│  ├─ format (格式校验)                                   │
│  ├─ threshold (阈值检查)                               │
│  ├─ unique (唯一性检查)                                │
│  └─ custom_sql (自定义SQL)                            │
└─────────────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────────┐
│  步骤2: 指定目标表和列                                   │
│  ├─ 从下拉列表选择 target_table                        │
│  └─ 从下拉列表选择 target_column（可选，表级可不选）   │
└─────────────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────────┐
│  步骤3: 填写条件表达式                                  │
│  ├─ 单条件: 直接输入 condition_expr                    │
│  └─ 多条件: 添加多个条件，选择 AND/OR 连接             │
└─────────────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────────┐
│  步骤4: 预览SQL → 确认 → 创建规则                      │
└─────────────────────────────────────────────────────────┘
```

**调用流程**：

1. 用户选择/输入 → 调用 `/rules/preview` → 显示 SQL 预览
2. 用户确认 → 调用 `/rules` POST → 创建规则

### 4.2 自然语言模式（NL2SQL）

```
┌─────────────────────────────────────────────────────────┐
│  步骤1: 输入自然语言描述                                 │
│  示例: "手机号码不为空，且格式符合中国标准手机号码格式"  │
└─────────────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────────┐
│  步骤2: 点击解析                                         │
│  调用 /rules/parse → 后台处理                          │
│  ├─ 获取数据源信息 (datasource_id)                     │
│  ├─ 获取 Schema (数据卡片 + 数据库)                    │
│  ├─ 模式匹配 / LLM 解析                                │
│  └─ 生成结构化规则 + SQL 预览                          │
└─────────────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────────┐
│  步骤3: 确认/修改解析结果                               │
│  ├─ 显示识别的: 表、列、规则类型、条件表达式           │
│  ├─ 显示: SQL 预览                                     │
│  └─ 支持用户修改确认                                   │
└─────────────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────────┐
│  步骤4: 确认 → 创建规则                                  │
│  调用 /rules/preview (可选，用于确认)                   │
│  调用 /rules POST → 创建规则                           │
└─────────────────────────────────────────────────────────┘
```

**数据卡片的作用**：

- 提供表结构的业务描述（中文注释）
- 帮助 LLM 更准确理解"手机号码"对应哪张表的哪个列
- 如果数据卡片已标注"phone"列的业务含义为"手机号"，则能准确匹配

### 4.3 模板导入模式

```
┌─────────────────────────────────────────────────────────┐
│  步骤1: 浏览规则模板库                                   │
│  调用 /templates → 获取可用模板列表                     │
└─────────────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────────┐
│  步骤2: 选择模板                                        │
│  ├─ 查看模板详情: 规则类型、条件表达式模板              │
│  └─ 支持批量选择                                       │
└─────────────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────────┐
│  步骤3: 指定应用范围（可选）                             │
│  ├─ 指定 target_table (不指定则对所有相关表生效)       │
│  ├─ 指定 target_column (不指定则应用模板默认配置)      │
│  └─ 可批量应用到多个表                                  │
└─────────────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────────┐
│  步骤4: 预览 → 确认 → 导入创建                          │
│  调用 /templates/import POST → 批量创建规则             │
└─────────────────────────────────────────────────────────┘
```

## 五、真实代码示例

### 5.1 parse 接口核心逻辑（已优化）

```python
# governance_api.py 第 1186-1364 行

# 1. 验证必填参数
user_input = data.get('user_input', '').strip()
datasource_id = data.get('datasource_id')
target_table = data.get('target_table', '').strip()
target_column = data.get('target_column', '').strip() or None

if not datasource_id:
    return resp(code=400, msg="datasource_id 不能为空")
if not target_table:
    return resp(code=400, msg="target_table 不能为空，请先选择目标表")

# 2. 获取目标表的 Schema
schemas = []
if card_schemas:
    schemas = card_schemas
else:
    # 从数据库获取目标表结构
    schemas.append(TableSchema(
        table_name=target_table,
        schema_name=schema_name,
        columns=col_list
    ))

# 3. 根据是否指定列选择解析方法
if target_column:
    # 用户已指定列，直接解析
    parsed, alternatives = parser.parse_with_column(
        user_input, schemas, target_table, target_column
    )
else:
    # 用户只指定表，推断列
    parsed, alternatives = parser.parse_for_table(
        user_input, schemas, target_table
    )

# 4. 返回结果
return resp(data={
    'success': True,
    'primary': parsed.to_dict(),
    'alternatives': alternatives,
    'sql_preview': sql_preview,
    'target_table': target_table,
    'target_column': parsed.target_column
})
```

## 七、关键数据模型

### 7.1 ParsedRule（解析结果）

```python
@dataclass
class ParsedRule:
    rule_type: str              # null_check, format, threshold, unique, composite
    target_table: str          # 目标表
    target_column: str         # 目标列（可选）
    condition_expr: str         # 条件表达式
    severity: str               # critical, warning, info
    confidence: float           # 置信度 0-1
    needs_confirmation: bool   # 是否需要用户确认
    reasoning: str              # 推理说明
    conditions: List[ColumnCondition]  # 多条件（composite 类型）
    condition_mode: str         # AND/OR（多条件时）
```

### 7.2 ColumnCondition（列条件）

```python
@dataclass
class ColumnCondition:
    column: str         # 列名
    rule_type: str     # 规则类型
    condition: str      # 条件表达式
    description: str    # 描述
```

## 八、总结

1. **三种模式是入口不同**，最终都生成相同的规则配置结构
2. **作用域由 target_table/target_column 决定**，不是由模式决定
3. **自然语言模式依赖数据卡片**提供业务上下文，辅助 LLM 识别表/列
4. **所有模式都需要预览确认**，让用户最终确认 SQL
5. **多条件复合规则**通过 `conditions` 数组 + `condition_mode` 实现
