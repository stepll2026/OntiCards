你是一位专业的数据库专家和数据分析师。你的任务是为数据库表生成高质量的"数据名片"(DataCard)。

# 输入信息

## 1. 目标表的完整结构
```json
{{table_schema_detail}}
```

## 2. 数据库全局上下文（表关系摘要）
```json
{{database_schema_summary}}
```

## 3. 采样数据分析结果（可选，如提供则用于增强生成质量）
```json
{{sampling_analysis_result}}
```

# 你的任务

为上述表生成数据名片中的四个核心字段：**Abstract**、**Domain**、**KeyConcepts**、**Tags**。

---

# 第一步：多维度信息分析

在生成内容前，你必须先对表进行**系统性分析**，分析以下所有维度：

## 维度 A：表名语义
- 表名的英文含义（拆分单词、理解缩写）
- 表名后缀含义：如 `_detail`（明细）、`_log`（日志）、`_config`（配置）、`_tmp`（临时）
- 常见命名模式：`t_`（表）、`v_`（视图）、`dim_`（维度）、`fact_`（事实）

## 维度 B：表描述（如果有）
- 直接使用表描述中的信息
- 提取核心业务功能描述

## 维度 C：字段分析（按重要性排序）

### C1. 核心业务字段
识别最核心的业务字段（如：客户名、订单号、产品名、金额、数量）
- **英文名** + **中文注释**（如果有）
- 字段的业务含义

### C2. 枚举值字段（重要！）
识别包含枚举值/值域信息的字段，**枚举值来源优先级**：

| 优先级 | 来源 | 说明 |
|--------|------|------|
| 1 | 字段注释中的明确枚举值 | 如 "状态：正常、冻结、注销" 或 "type(1-客户,2-供应商)" |
| 2 | 字段名+类型推断 | 如 `status VARCHAR(10)` 可能包含有限状态 |
| 3 | 泛化的业务概念 | 如 "客户类型"、"订单状态" |

**重要**：
- 如果字段注释中有明确的枚举值，**必须原样使用**，不要修改或推测
- 如果字段注释中**没有**枚举值，不要捏造，标注"枚举值详见字典文件"或"请参考实际数据"

### C3. 外键字段
识别外键字段及其关联表：
- 关联到哪个表（如 `customer_id` → 客户表）
- 外键字段的业务含义

### C4. 技术字段（通常不需要详细描述）
以下字段类型可以简化描述或省略：
- `id`：主键标识
- `create_time`、`update_time`、`create_by`、`update_by`：审计字段
- `version`、`is_deleted`：技术字段

### C5. 字段类型分析
- `INT/BIGINT` + `id` 后缀：可能是主键或外键
- `VARCHAR` + `name/code` 后缀：可能是名称或编码
- `DECIMAL/FLOAT` + `amount/price/cost` 后缀：金额字段
- `DATE/DATETIME/TIMESTAMP`：时间字段
- `TEXT/LONGTEXT`：大文本字段
- `BOOLEAN/TINYINT(1)`：布尔字段

## 维度 D：采样数据分析（如果有采样数据）

如果有提供采样数据分析结果，请结合以下信息：

### D1. 敏感字段识别
- 如果字段被标记为 `is_sensitive: true`，在描述时**不要输出该字段的数据示例**
- 敏感字段只描述字段用途，如"手机号(脱敏)"、"身份证号(脱敏)"

### D2. 非敏感字段数据特征
- **枚举型字段**（category: enum）：可以使用 enum_values 和 enum_meanings
- **数值型字段**（category: numeric）：可以使用 statistics（min/max/avg）和 sample_display
- **日期型字段**（category: date）：可以使用 range 和 sample_display
- **文本型字段**（category: text）：使用 sample_display 中的简短示例

### D3. 示例使用规则
```
✓ 正确使用：
   - 状态字段：枚举值 [0, 1, 2]，含义 {0: "禁用", 1: "正常", 2: "待激活"}
   - 余额字段：范围 0.00 ~ 15888.88 元，平均 1250.50
   - 城市字段：北京、上海、深圳、广州、杭州、成都、武汉、南京
   - 创建时间：2024-01-15 10:30:00

✗ 错误使用：
   - 敏感字段（phone、id_card、password）：输出实际数据示例
   - 超长文本：输出完整文本而非简短示例
```

---

## 维度 E：表关系分析
基于外键和表名判断：
- **主表 vs 从表**：如 `t_order`（主表）vs `t_order_item`（从表）
- **一对多关系**：如 1个订单 → N个订单明细
- **lookup表**：如 `t_dict_*`（字典表）

## 维度 F：业务领域判断
基于以上所有信息，综合判断表所属的业务领域：
- 用户管理、财务管理、订单管理、库存管理
- 日志记录、系统配置、数据统计、消息队列
- 或者多个领域的组合

# 第二步：生成数据名片内容

## 1. Abstract（摘要）

**重要**：Abstract 是向量检索的核心依据，描述越详细越有助于 NL2SQL 准确匹配数据表。

**要求**：
- **200-400字**（比之前更长，确保覆盖所有字段）
- 必须包含：
  1. 表的核心功能描述
  2. **所有字段**的逐一描述（中英文名 + 业务含义 + 枚举值/范围）
  3. 采样数据分析得出的关键统计信息（如枚举值、金额范围、日期范围等）
  4. 常见查询场景

**结构模板**：
```
本表为[业务领域]表，用于[核心功能描述]。

【字段详情】
[按字段顺序逐一描述，格式如下：]
- [字段英文名]([字段中文注释])：[业务含义]【如有关键枚举值/范围/示例，标注清楚】
  - 枚举值：[值1, 值2, 值3]（来源于采样数据或字段注释）
  - 数值范围：[min] ~ [max]（如适用）
  - 示例：[sample_display]

【查询场景】
- [场景1]
- [场景2]
- [场景3]
```

**示例**：
```
本表为用户信息表，用于记录平台注册用户的基础信息、账户状态与财务数据。

【字段详情】
- id：用户主键ID，用于唯一标识用户记录
- username：用户名，用户登录凭证
- created_at(TIMESTAMP)：账户创建时间，示例：2024-01-15 10:30:00 ~ 2025-08-10 18:45:00
- status(SMALLINT)：账户状态，枚举值：[0=禁用, 1=正常, 2=待激活, 3=冻结]
- balance(NUMERIC)：账户余额，范围：0.00 ~ 15888.88 元，平均：1250.50 元
- vip_level(SMALLINT)：VIP等级，枚举值：[0=非VIP, 1=铜牌, 2=银牌, 3=金牌, 4=钻石]
- user_type(SMALLINT)：用户类型，枚举值：[1=普通, 2=VIP, 3=企业]
- phone(VARCHAR)：手机号（脱敏字段），敏感信息，已做数据脱敏处理

【查询场景】
- 查询指定类型用户及其账户信息
- 统计VIP等级分布和用户类型占比
- 筛选异常账户（禁用、冻结）
- 分析用户交易金额与活跃度
- 用户画像分析和精准营销
```

## 2. Domain（业务领域）

**要求**：
- 单一领域或多个领域的组合
- 基于维度A-E的综合判断

**示例**：
```
用户管理, 客户关系管理
```

或单一领域：
```
订单管理
```

## 3. KeyConcepts（核心概念）

| 字段 | 说明 | 示例 |
|------|------|------|
| canonical_topic | 表的统一主题 | "客户信息"、"订单交易"、"库存记录" |
| alias | 表的别称 | ["客户表", "客户主数据", "customer_master"] |
| taxonomy_code | 分类编码（可为空） | "" |
| key_entities | 核心业务实体 | 基于枚举值或泛化概念，如：["普通客户", "战略客户", "重点客户", "客户类型"] |
| applicable_scenarios | 适用场景 | 包含具体查询意图，如："查询指定类型客户"、"统计行业分布"、"客户活跃度分析" |
| tags | 标签（与外层Tags一致） | 省略此字段，在外层统一返回 |

**key_entities 注意事项**：
- **优先使用**字段注释中的枚举值（如有）
- **可以包含**泛化的业务概念（如"客户"、"订单"、"产品"）
- **禁止**捏造具体的枚举值（如"VIP"、"华东"）

## 4. Tags（标签）

**要求**：
- 用于向量检索，关键词要丰富
- 覆盖多种检索场景

**Tags 结构**：
```
[
  // 表名相关
  "表名（中英文）",
  "表名别名",

  // 核心字段（中英文）
  "字段名1",
  "字段名1_中文",
  "字段名2",
  "字段名2_中文",

  // 枚举值（仅来自注释）
  "枚举值1",
  "枚举值2",

  // 业务术语（泛化概念）
  "业务术语1",
  "业务术语2",

  // 查询关键词
  "查询关键词1",
  "统计",
  "筛选",

  // 常见检索词
  "哪些",
  "怎么查询",
  "如何获取"
]
```

**示例**：
```json
["t_customer", "客户信息表", "customer", "客户表",
 "customer_id", "客户ID", "customer_name", "客户名称",
 "customer_type", "客户类型", "普通客户", "战略客户", "重点客户",
 "industry", "所属行业", "电子制造", "工业设备",
 "status", "客户状态", "正常", "冻结",
 "客户管理", "客户关系", "客户画像",
 "查询客户", "统计客户", "客户筛选",
 "有哪些客户", "怎么查询客户"]
```

# 第三步：质量检查

在输出前，检查以下问题：

| 检查项 | 合格标准 | 不合格示例 |
|--------|----------|------------|
| 枚举值 | 仅来自字段注释或采样数据，无捏造 | ❌ 字段注释没有枚举值，却写了"VIP、普通" |
| Abstract长度 | 200-400字，确保详细 | 太短（遗漏字段）或太长（冗余） |
| 字段覆盖 | **所有字段**都要描述，不能遗漏 | 只描述部分字段 |
| 枚举值完整性 | 注释/采样中的枚举值都包含 | 遗漏部分枚举值 |
| 数值/日期范围 | 使用采样数据的实际范围 | 缺失或捏造 |
| Tags丰富度 | 至少20个标签 | 只有3-5个标签 |
| Domain准确性 | 与表内容匹配 | Domain与表无关 |
