## 一、关联类型定义（必须严格区分）

### 1. foreign_key（外键关联）
两张表之间通过主键-外键形成的真正外键关系。
**判定标准（必须同时满足）**：
- 字段A是某表的"引用标识"（通常是 xxx_id），字段B是被引用表的主键（通常是 id）
- 两端的**业务实体**必须一致：user_id 指向 user 表，order_id 指向 order 表
- 数据类型必须兼容
- 基数关系必须正确：被引用端的唯一值数量应大于等于引用端

### 2. shared_field（共享字段关联）
两张表有相同或相似的业务字段，表示相同的业务实体属性。
**判定标准**：
- 两端字段名相同或语义等价（如 receiver_name ↔ receiver_name, phone ↔ mobile）
- 可能存在于任何两张业务相关的表中
- 典型场景：用户表和订单表都有 nickname，物流表和地址表都有 receiver_name

### 3. semantic（语义关联）
基于业务语义形成的关联，而非直接的字段引用。
**判定标准**：
- 字段名或注释表明存在业务关联
- 但不是直接的外键或共享字段关系
- 通常需要结合业务背景判断

### 4. value_overlap（值域重叠）
基于实际数据值分析发现的关联。
**判定标准**：
- 两端字段的 sample_values 或 top_values 有实际重叠
- 或 distinct_count 比例合理（外键端远小于被引用端）

## 二、字段关系判定规则

### 规则1: 识别有效关联字段
**应该考虑**：
- 主键/唯一键：id, xxx_id, xxx_code, xxx_no
- 外键引用：user_id, order_id, product_id
- 业务标识：name, title, phone, email, address
- 共享业务字段：receiver_name, create_user, update_time

**应该忽略**：
- 系统字段：created_at, updated_at, deleted_at, is_deleted
- 状态字段：status, state, is_active, is_enabled（除非有特殊含义）
- 排序/权重：sort, order, priority, weight
- 坐标：latitude, longitude, lng, lat
- 描述/备注：remark, memo, description

### 规则2: 外键关系判定
**✅ 正确示例**：
- orders.user_id → users.id（用户下的订单）
- order_items.product_id → products.id（订单项引用的商品）
- logistics.order_id → orders.id（物流关联的订单）

**❌ 错误示例（不要判断为外键）**：
- user_id ↔ category_id（两个都是外键，指向不同实体）
- create_user_id ↔ update_user_id（都是用户，但无直接关联）
- user_id ↔ order_id（id 命名相同但实体不同）

### 规则3: 共享字段判定
**✅ 正确示例**：
- addresses.receiver_name ↔ logistics.receiver_name（收件人）
- addresses.receiver_phone ↔ logistics.receiver_phone（收件电话）
- orders.nickname ↔ users.nickname（昵称）

**判定依据**：
1. 字段名完全相同
2. 字段名语义等价（receiver_name ≈ consignee ≈ contact_name）
3. 属于同一业务属性组（联系人信息、地址信息等）

### 规则4: 置信度评分标准（与用户阈值联动）

| 置信度区间 | 证据要求 | 适用阈值档 |
|-----------|----------|-----------|
| 0.95-1.0 | **完美匹配**：外键命名完全对应 + 数据类型严格兼容 + 基数关系正确 + 画像佐证（如 distinct_count 比对） | 仅在很高阈值（≥0.85）下输出 |
| 0.85-0.95 | **强证据**：外键命名清晰 + 类型兼容 / 字段名完全相同 + 业务含义一致 | 高阈值（≥0.7）下输出 |
| 0.70-0.85 | **较强证据**：明确的命名匹配 + 类型兼容 / 共享业务字段 + 类型匹配 | 高阈值档（≥0.7） |
| 0.55-0.70 | **中等证据**：命名部分匹配 或 同义词匹配 或 注释相似 | 中阈值档（0.5）下输出 |
| 0.40-0.55 | **弱证据**：仅命名相似 / 弱语义关联 | 低阈值档（0.3）下输出 |
| <0.40 | 证据不足，**不要输出** | 任何阈值都不应保留 |

> **重要**：请根据 `{confidence_threshold}` 调整你的判断严格度。
> {confidence_threshold} 越高，越倾向于"宁缺毋滥"；越低，越倾向于"广撒网"。

### 规则5: type_hint 辅助判断
- **identifier**: 高基数唯一标识，适合作为外键引用端
- **enum**: 低基数枚举值，适合作为分类/状态字段
- **datetime**: 时间字段，通常不是外键端
- **amount**: 金额/数值，可能与统计相关
- **boolean_flag**: 布尔标志，通常不是关联字段

## 三、基数关系判定规则（重要）

### cardinality 取值说明
- **one_to_one (1:1)**: 一端的一条记录最多对应另一端的一条记录
- **one_to_many (1:N)**: 一端的一条记录对应另一端的多条记录（从一端看）
- **many_to_one (N:1)**: 多条记录对应同一条记录（从多端看）
- **many_to_many (N:N)**: 两端的多条记录相互对应

### 判断方法
1. **外键关系**：检查 from 端和 to 端的 distinct_count 比例
   - 如果 from 端的 distinct_count 远小于 to 端 → many_to_one
   - 如果 to 端的 distinct_count 远小于 from 端 → one_to_many
   - 如果两端比例接近且都较低 → one_to_one
   - 如果两端比例都较高且值域重叠大 → many_to_many

2. **共享字段**：通常 many_to_one（多个记录共享同一属性值）

### ⚠️ 特别注意
- **is_deleted、del_flag、status 等系统字段的关联不能作为基数判断依据**
- 基数判断应基于业务主键/外键字段，而非系统字段
