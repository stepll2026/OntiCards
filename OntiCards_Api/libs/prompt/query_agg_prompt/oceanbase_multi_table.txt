6. **字段白名单绝对约束** ⭐⭐⭐⭐⭐（最重要）：
   - **只能使用白名单中明确列出的字段，绝对禁止使用任何不在白名单中的字段**
   - **生成SQL前必须逐个检查每个字段是否在对应表的白名单中**

   - **WHERE子句中绝对禁止使用聚合函数**（SUM、COUNT、AVG、MAX、MIN等）
   - **聚合函数只能在以下位置使用**：SELECT子句、HAVING子句、ORDER BY子句

【聚合函数使用示例】⭐⭐⭐⭐⭐（必读，避免常见错误）

**错误示例1：在WHERE子句中使用聚合函数**
❌ 错误（会导致SQL执行失败）：
```sql
SELECT COUNT(*) AS mismatch_count
FROM shop_order AS t2
JOIN order_item AS t1 ON t1.order_id = t2.order_id
WHERE t2.pay_amount != (SUM(t1.item_amount) + t2.shipping_fee - IFNULL(t2.coupon_amount, 0))
GROUP BY t2.order_id
```
错误原因：WHERE子句在GROUP BY之前执行，此时还没有进行聚合计算，不能使用SUM()

✅ 正确方式1（使用HAVING子句）：
```sql
SELECT COUNT(*) AS mismatch_count
FROM (
    SELECT t2.order_id
    FROM shop_order AS t2
    JOIN order_item AS t1 ON t1.order_id = t2.order_id
    GROUP BY t2.order_id, t2.pay_amount, t2.shipping_fee, t2.coupon_amount
    HAVING t2.pay_amount != (SUM(t1.item_amount) + t2.shipping_fee - IFNULL(t2.coupon_amount, 0))
) AS subquery
```

✅ 正确方式2（使用子查询）：
```sql
SELECT COUNT(*) AS mismatch_count
FROM shop_order AS t2
WHERE t2.order_id IN (
    SELECT t1.order_id
    FROM order_item AS t1
    GROUP BY t1.order_id
    HAVING SUM(t1.item_amount) != (
        SELECT t2.pay_amount - t2.shipping_fee + IFNULL(t2.coupon_amount, 0)
        FROM shop_order AS t2
        WHERE t2.order_id = t1.order_id
    )
)
```

**错误示例2：同时使用WHERE和HAVING且条件重复**
❌ 错误（逻辑混乱）：
```sql
SELECT t1.product_id, SUM(t1.quantity) AS total_qty
FROM order_item AS t1
WHERE SUM(t1.quantity) > 100  -- 错误：WHERE中不能用聚合函数
GROUP BY t1.product_id
HAVING SUM(t1.quantity) > 100  -- 重复的条件
```

✅ 正确（只在HAVING中使用聚合函数）：
```sql
SELECT t1.product_id, SUM(t1.quantity) AS total_qty
FROM order_item AS t1
GROUP BY t1.product_id
HAVING SUM(t1.quantity) > 100
```

**关键规则总结**：
1. WHERE用于过滤原始行（在分组之前），不能使用聚合函数
2. HAVING用于过滤分组结果（在分组之后），可以使用聚合函数
3. 如果需要基于聚合结果过滤，使用HAVING或子查询，绝不使用WHERE
4. 不要同时在WHERE和HAVING中写相同的聚合条件

【统计查询结果保证】⭐⭐⭐⭐⭐（重要的用户体验优化）

当用户询问"数量"、"统计"、"有多少"等统计类问题时，必须确保SQL返回一个明确的数值，即使结果为0。

**核心要求**：
- 统计查询（COUNT、SUM等）必须保证返回一行结果，不能返回空结果集
- 即使没有符合条件的记录，也要返回 0 或其他默认值
- 用户期望看到一个具体的数字（如 0、1、100），而不是"无数据"或空结果

**实现方式**：

✅ **方式1：使用IFNULL或COALESCE确保返回默认值**（推荐）
```sql
-- 统计数量查询
SELECT IFNULL(COUNT(*), 0) AS count_result
FROM (
    SELECT ...
    WHERE ...
) AS subquery

-- 统计总和查询
SELECT IFNULL(SUM(amount), 0) AS total_amount
FROM orders
WHERE ...

-- 统计平均值查询
SELECT IFNULL(AVG(price), 0) AS avg_price
FROM products
WHERE ...
```

✅ **方式2：对于子查询统计，确保外层COUNT始终有结果**
```sql
-- 即使子查询返回0行，外层COUNT(*)也会返回0
SELECT COUNT(*) AS mismatch_count
FROM (
    SELECT t2.order_id
    FROM shop_order AS t2
    JOIN order_item AS t1 ON t1.order_id = t2.order_id
    GROUP BY t2.order_id
    HAVING ...
) AS subquery
```

**注意事项**：
1. COUNT(*) 本身会返回0（不会返回NULL），但使用IFNULL可以更明确
2. SUM/AVG在没有匹配行时会返回NULL，必须使用IFNULL或COALESCE包装
3. 对于复杂的统计查询，优先使用子查询+外层COUNT的方式，确保结果稳定

**典型场景示例**：

场景1：统计不符合条件的订单数量
```sql
-- ✅ 推荐：即使没有不符合条件的订单，也返回 count=0
SELECT IFNULL(COUNT(*), 0) AS mismatch_count
FROM (
    SELECT t2.order_id
    FROM shop_order AS t2
    JOIN order_item AS t1 ON t1.order_id = t2.order_id
    GROUP BY t2.order_id, t2.pay_amount, t2.shipping_fee, t2.coupon_amount
    HAVING t2.pay_amount != (SUM(t1.item_amount) + IFNULL(t2.shipping_fee, 0) - IFNULL(t2.coupon_amount, 0))
) AS subquery
```

场景2：统计某个状态的记录数
```sql
-- ✅ 即使没有该状态的记录，也返回 count=0
SELECT IFNULL(COUNT(*), 0) AS status_count
FROM orders
WHERE status = 'completed'
```

场景3：统计总金额
```sql
-- ✅ 即使没有订单，也返回 total=0（而不是NULL）
SELECT IFNULL(SUM(amount), 0) AS total_amount
FROM orders
WHERE order_date >= DATE_SUB(CURDATE(), INTERVAL 30 DAY)
```

【第0阶段：深度语义理解】⭐⭐⭐⭐⭐
这是最关键的阶段！必须花费足够的时间和精力来准确理解用户意图，然后才能生成正确的SQL。

1. **实体识别与匹配**
   - 识别用户提到的具体实体（如"充电宝"、"蓝牙耳机"、"广州"等）
   - 根据**字段名称、字段类型、字段注释**，将实体映射到正确的字段：
     * 商品名称关键词（如"充电宝"、"手机"）→ 字符串类型的 `name`、`product_name`、`title` 等字段
     * 地点关键词（如"广州"、"深圳"）→ 字符串类型的 `warehouse`、`location`、`address`、`region` 等字段
     * 类别关键词（如"数码"、"外设"）→ 字符串类型的 `category`、`type` 等字段
   - **禁止将实体映射到类型不匹配的字段**：
     * ❌ 错误：将"充电宝"映射到 `product_id`（int 类型）
     * ✅ 正确：将"充电宝"映射到 `name`（varchar 类型）

2. **自然语言到字段的智能映射**⭐⭐⭐⭐⭐（最关键）
   这是大模型最容易出错的地方！必须仔细分析用户使用的词汇，并映射到正确的字段。
   
   **核心规则**：
   - **同义词识别**：用户可能用不同词汇表达同一概念
     * "价格/多少钱/单价/售价" → `price`、`unit_price` 字段
     * "数量/有多少/库存" → `quantity`、`stock`、`amount` 字段
     * "状态/情况" → `status`、`state` 字段
     * "评分/评级/等级" → `rating`、`level`、`grade` 字段
   
   - **泛化概念理解**：
     * "无线产品" → `name LIKE '%无线%' OR name LIKE '%蓝牙%'`
     * "数码类商品" → `category = '数码'` 或 `category LIKE '%数码%'`
     * "高价商品" → `price > 500`（根据业务判断阈值）
     * "有库存" → `quantity > 0` 或 `stock > 0`
     * "在售商品" → `status = '在售'` 或 `is_active = 1`
     
     * **销量/销售相关概念**⭐⭐⭐⭐⭐（特别重要，极易出错）：
       - "卖得最好/最畅销/销量最高/卖得最多" → 必须映射到销量字段，如 `sales`、`sales_num`、`qty`、`sales_qty`、`sold_count`
       - ❌ **绝对禁止**：将"卖得好"映射到 `price`（价格）字段！价格高≠卖得好
       - ✅ **正确理解**："卖得好" = 销售数量多，应使用 `SUM(qty)` 或 `SUM(sales_num)` 排序
       - **示例**：
         * "卖得最好的产品" → `ORDER BY SUM(sales_num) DESC` 或 `ORDER BY SUM(qty) DESC`
         * "销量前10的商品" → `ORDER BY sales_count DESC LIMIT 10`
         * "哪个产品最畅销" → `ORDER BY total_sales DESC LIMIT 1`
       - **特别注意**：如果当前表没有销量字段，处理方式：
         * ❌ **禁止使用 LIMIT 1 随意返回一条记录**（会导致返回错误的产品）
         * ✅ **正确做法**：返回所有候选产品的基本信息（不使用LIMIT），让系统在跨数据源融合时通过销量筛选
         * ✅ 或者：如果白名单要求必须包含entity_key，则只返回 `SELECT product_id FROM table`（不限制数量）
         * ✅ 同时在 note 中说明："当前表未包含销量字段，需要销售数据表提供销量信息进行排序"
         * **关键**：让其他数据源（如sales_orders表）通过销量排序后，系统自动融合出正确结果
   
   - **报文方向识别** ⭐⭐⭐（特别重要，用于支付/通信系统）：
     
     ⚠️⚠️⚠️ **极其重要：必须先检查白名单** ⚠️⚠️⚠️
     **前置条件：**
     1. 首先在白名单中查找是否存在报文方向相关字段
     2. 常见字段名包括：`AHIO_FLAG`、`IO_FLAG`、`MSG_DIRECTION`、`DIRECTION`、`MSG_TYPE_FLAG` 等
     3. **如果白名单中不存在任何报文方向字段，则不要添加方向筛选条件**
     4. **绝对不能使用下面示例中的字段名，除非它们在白名单中存在**
     
     * **关键字段**（仅供参考，必须以白名单为准）：
       - 常见名称：`AHIO_FLAG`、`IO_FLAG`、`MSG_DIRECTION` 等
       - 通常为字符串类型（varchar、char）
     
     * **发出/发送/输出报文**：
       - 关键词："发出"、"发送"、"输出"、"outgoing"、"sent"、"output"
       - 映射逻辑（假设白名单中有 AHIO_FLAG 字段）：`WHERE AHIO_FLAG = 'O'`
       - 映射逻辑（假设白名单中有 IO_FLAG 字段）：`WHERE IO_FLAG = 'OUT'`
       - 示例（仅当白名单中有相关字段时）：

     * **接收/输入报文**：
       - 关键词："接收"、"收到"、"输入"、"incoming"、"received"、"input"、"收入"

       - 映射逻辑（假设白名单中有 IO_FLAG 字段）：`WHERE IO_FLAG = 'IN'`

     * **典型枚举值**（以字段注释为准）：
       - 'O'/'OUT'/'1' → 输出/发出
       - 'I'/'IN'/'0' → 输入/接收
     
     * **重要注意事项**：
       - ⚠️ **如果白名单中没有报文方向相关字段，则不要添加方向筛选条件**
       - ⚠️ **上面的 AHIO_FLAG、IO_FLAG 只是示例，不能直接使用**
       - ⚠️ **必须在白名单中查找实际的字段名，然后使用实际字段名**
       - 如果用户只说"报文数量"而不指定方向，则不添加方向筛选（查询全部）
   
   - **字段语义验证**（三重检查）：
     ① **字段名检查**：字段名是否包含相关关键词
     ② **字段类型检查**：类型是否匹配（数值/字符串/日期）
     ③ **字段注释检查**：注释是否说明了该字段的用途
   
   - **反例学习**（避免错误映射）：
     * ❌ 用户问"充电宝的价格" → 错误映射到 `product_id = 充电宝`（类型不匹配）
     * ✅ 正确：先找到 `name LIKE '%充电宝%'` 的记录，再查 `price` 字段
     * ❌ 用户问"有多少钱" → 错误映射到 `quantity`（语义不匹配）
     * ✅ 正确：应映射到 `price` 或 `amount` 字段
     
     * ❌ **严重错误**：用户问"卖得最好的产品" → 错误映射到 `ORDER BY price DESC`（用价格排序）
     * ✅ **正确**：应映射到 `ORDER BY sales_num DESC` 或 `ORDER BY SUM(qty) DESC`（用销量排序）
     * ❌ 用户问"最畅销的商品" → 错误返回价格最高的商品
     * ✅ 正确：应返回销量最多的商品，查找 `sales`、`qty`、`sales_count` 等字段

3. **业务逻辑推理**
   - 理解隐含的业务逻辑，补全查询条件：
     * "有库存" → `quantity > 0`
     * "在售" → `status = '在售'` 或 `is_active = 1`
     * "近期" → 根据上下文判断时间范围（如近7天、近30天）
     * "热销" → `sales_num > 某阈值` 或 `ORDER BY sales_num DESC`

   - **地理层次识别** ⭐⭐⭐（特别重要）：
     * **省公司级别**：广东、山东、江苏、浙江等 → 使用 `PROVINCE_NAME LIKE '%省名%'`
     * **地市局级别**：梅州、深圳、广州、佛山、东莞、中山等 → 需要**同时使用省份和地市局条件**
     * **地市局查询逻辑**：
       - 梅州/韶关/惠州/汕头/湛江/茂名/肇庆/江门/珠海/潮州/揭阳/汕尾/河源/阳江/清远/云浮 → 广东省下属地市局
       - 济南/青岛/淄博/枣庄/烟台/潍坊/威海等 → 山东省下属地市局
     * **示例查询模式**：
       - "梅州的缺陷" → `WHERE PROVINCE_NAME LIKE '%广东%' AND BUREAU_NAME LIKE '%梅州%'`
       - "深圳的缺陷" → `WHERE PROVINCE_NAME LIKE '%广东%' AND BUREAU_NAME LIKE '%深圳%'`
       - "济南的缺陷" → `WHERE PROVINCE_NAME LIKE '%山东%' AND BUREAU_NAME LIKE '%济南%'`

4. **多表关联推理**
   - 根据用户问题，推理需要哪些表：
     * "商品的价格" → 需要 `product_catalog` 表
     * "商品的库存" → 需要 `inventory_stock` 表
     * "商品在某地的库存" → 需要 JOIN `product_catalog` 和 `inventory_stock`
   - 根据白名单中的 JOIN 关系，找到正确的关联字段
   - 如果白名单缺少必要的 JOIN 关系，考虑使用子查询

5. **查询类型识别** ⭐⭐⭐（特别重要）
   - **统计数量查询**：当用户问及数量、统计、计数时：
     * "有多少" → `SELECT COUNT(*) AS count`
     * "数量是" → `SELECT COUNT(*) AS count` 
     * "统计...的数量" → `SELECT COUNT(*) AS count`
     * "...有几个" → `SELECT COUNT(*) AS count`
     * **示例**: "状态为已归档的缺陷单有多少？" → `SELECT COUNT(*) AS defect_count FROM sp_pd_defect_03 WHERE STATE = 6`
     * **重要**: 统计查询只返回聚合结果，**不要包含任何其他字段**，**不要使用GROUP BY**，**不要包含{{entity_key}}字段**
   
   - **聚合统计查询**：
     * "总金额" → `SELECT SUM(amount) AS total_amount`
     * "平均价格" → `SELECT AVG(price) AS avg_price`
     * "最大值/最小值" → `SELECT MAX(field)/MIN(field)`
     * **重要**: 聚合查询只返回聚合结果，除非用户明确要求按某个维度分组

   - **分布情况查询** ⭐⭐⭐（特别重要）：
     * 当用户问及"分布情况"、"分布统计"、"各地区分布"时，这是**地理分布查询**
     * **优先级规则**：
       1. **地市局分布**：如果有 `BUREAU_NAME`（地市局）字段，优先按地市局分组
       2. **省份分布**：如果没有地市局字段，按 `PROVINCE_NAME`（省份）分组  
       3. **城市分布**：按 `CITY_NAME`（城市）等地理字段分组
     * **示例**: 
       - "统计广东的缺陷分布情况" → `SELECT BUREAU_NAME, COUNT(*) AS defect_count FROM sp_pd_defect_03 WHERE PROVINCE_NAME LIKE '%广东%' GROUP BY BUREAU_NAME ORDER BY defect_count DESC`
       - "各省份的设备分布" → `SELECT PROVINCE_NAME, COUNT(*) AS device_count FROM devices GROUP BY PROVINCE_NAME`
     * **重要**: 分布查询必须包含 `GROUP BY` 和地理维度字段，**不要按业务类型字段分组**（如缺陷类型、设备类型等）
   
   - **详细记录查询**：当用户需要具体记录信息时：
     * "显示详细信息" → `SELECT 具体字段`
     * "列出所有" → `SELECT 具体字段`
     * "查看...的信息" → `SELECT 具体字段`

【字段类型与操作符匹配规则】（必须严格遵守）
- **数值类型字段**（int, bigint, smallint, tinyint, decimal, numeric, float, double 等）：
  ✅ 只能使用 =, !=, <, >, <=, >=, IN, BETWEEN 等数值比较操作符
  ❌ 禁止使用 LIKE 等文本匹配操作符
  ❌ 禁止用商品名称等文本关键词直接匹配数值类型的 ID 字段

- **字符串类型字段**（varchar, text, char 等）：
  ✅ 可以使用 =, !=, LIKE 等文本操作符
  ✅ 对于名称、地址等字段，优先使用 LIKE '%关键词%' 进行模糊匹配

- **⭐⭐⭐ *_code 字段类型识别规则（极其重要，容易出错）**：
  ⛔ **很多 *_code 字段实际上是字符串类型（varchar/text），而不是整数类型**：
     - supplier_code（供应商编码）→ 通常是 varchar，如 'S001'、'SUP-2024-001'
     - customer_code（客户编码）→ 通常是 varchar，如 'CUST-001'、'KH-10001'
     - product_code（产品编码）→ 通常是 varchar，如 'P-1001'、'PROD-A001'
     - order_code（订单编码）→ 通常是 varchar，如 'ORD-2024-001'
     - invoice_code（发票编码）→ 通常是 varchar，如 'INV-001'
     - account_code（账户编码）→ 通常是 varchar
  ✅ **判断方法**：
     1. 查看白名单中的类型信息（varchar/char/text = 字符串，int/bigint = 数值）
     2. 如果类型是 varchar/char/text，**必须当作字符串处理**
     3. 如果注释中包含编码示例（如 'S001'、'C-001'），**一定是字符串类型**
  ❌ **错误示例**：
     ```sql
     -- ❌ 错误：supplier_code 可能是 'S001'（字符串），不能进行数值运算
     SELECT supplier_name, SUM(CAST(supplier_code AS SIGNED)) AS total_score
     ```
  ✅ **正确示例**：
     ```sql
     -- ✅ 正确：如果需要统计，按字符串处理或使用其他数值字段
     SELECT supplier_name, SUM(amount) AS total_amount
     FROM suppliers
     GROUP BY supplier_name
     ```

- **日期时间类型字段**（date, datetime, timestamp 等）：
  ✅ 使用 =, <, >, BETWEEN 以及日期函数（如 CURDATE(), DATE_SUB()）
  🚨🚨🚨 **日期字段类型安全处理（极其重要，防止类型转换错误）** 🚨🚨🚨：
  - **datetime/timestamp字段转换为date**：
    * ✅ **正确**：`DATE(update_time) = CURDATE()` 或 `DATE(create_time) = CURDATE()`（适用于datetime/timestamp类型）
    * ✅ **安全**：`CAST(update_time AS DATE) = CURDATE()`（显式转换）
    * ❌ **错误**：`CAST(update_time AS CHAR) = CURDATE()`（类型不匹配）
    * ❌ **错误**：`DATE(CAST(update_time AS CHAR))`（双重转换导致错误）
  - **date字段直接比较**：
    * ✅ **正确**：`sta_date = CURDATE()`（date类型直接比较）
    * ✅ **正确**：`CAST(sta_date AS DATE) = CURDATE()`（显式转换，虽然不必要）
    * ❌ **错误**：`sta_date = CAST(CURDATE() AS CHAR)`（类型不匹配）
    * ❌ **错误**：`CAST(sta_date AS CHAR) = CAST(CURDATE() AS CHAR)`（不必要的字符串转换）
  - **日期比较**：
    * ✅ **正确**：`DATE(update_time) = CURDATE()`（datetime字段提取日期部分后比较）
    * ✅ **正确**：`sta_date = CURDATE()`（date字段直接比较）
    * ❌ **错误**：`update_time = CAST(CURDATE() AS DATETIME)`（如果update_time是datetime，应该用DATE()提取日期部分）
    * ❌ **错误**：`sta_date = CAST(CURDATE() AS CHAR)`（date类型不应该转换为CHAR比较）
  - **关键规则**：
    * 如果字段是datetime/timestamp类型，使用 `DATE(字段)` 提取日期部分
    * 如果字段是date类型，直接使用字段名，不需要转换
    * 如果字段是varchar类型且存储日期，使用 `STR_TO_DATE(字段, '%Y-%m-%d')` 或 `CAST(字段 AS DATE)`
    * **绝对禁止**：将date类型字段转换为CHAR再与CURDATE()比较

【第1阶段：时间维度动态处理】⭐⭐⭐⭐⭐（极其重要）
当用户提到时间相关的关键词时，必须使用数据库的动态时间函数，**绝对禁止硬编码具体日期**。

🚨🚨🚨 **铁律：禁止硬编码日期** 🚨🚨🚨
════════════════════════════════════════════════
⛔ **绝对禁止**以下行为：
1. ❌ 禁止使用固定年份：`WHERE FIND_TIME >= '2024-07-01'`
2. ❌ 禁止使用固定日期：`WHERE CREATE_TIME < '2024-10-01'`
3. ❌ 禁止假设当前年份是2024或其他固定值
4. ❌ 禁止在WHERE条件中使用任何具体的年、月、日数字

✅ **唯一正确做法**：
- 必须使用MySQL的动态时间函数（NOW(), CURDATE(), YEAR(NOW())等）
- 根据用户的时间关键词，计算相对于当前时间的范围
- 确保生成的SQL在任何时候执行都能得到正确的时间范围
════════════════════════════════════════════════

**1. 关键词识别与函数映射**⭐⭐⭐⭐⭐（最重要）

**当前时间关键词**：
- **"今年"、"本年度"、"当年"** → 使用 `YEAR(字段) = YEAR(NOW())`
  ```sql
  -- ✅ 正确：动态获取当前年份
  WHERE YEAR(FIND_TIME) = YEAR(NOW())
  
  -- ❌ 错误：硬编码年份
  WHERE FIND_TIME >= '2024-01-01' AND FIND_TIME < '2025-01-01'
  ```

- **"今天"、"当天"、"今日"** → 使用 `DATE(字段) = CURDATE()`（适用于datetime/timestamp字段）
  ```sql
  -- ✅ 正确：datetime/timestamp字段提取日期部分后比较
  WHERE DATE(CREATE_TIME) = CURDATE()
  WHERE DATE(update_time) = CURDATE()
  
  -- ✅ 正确：date类型字段直接比较
  WHERE sta_date = CURDATE()
  
  -- ❌ 错误：硬编码日期
  WHERE CREATE_TIME >= '2024-11-24'
  
  -- ❌ 错误：类型不匹配（将date转换为CHAR比较）
  WHERE sta_date = CAST(CURDATE() AS CHAR)
  
  -- ❌ 错误：对datetime字段使用错误的转换方式
  WHERE CAST(update_time AS CHAR) = CAST(CURDATE() AS CHAR)
  ```

- **"当前"、"现在"、"目前"** → 根据上下文使用相应函数
  ```sql
  -- 如果指当前年份
  WHERE YEAR(字段) = YEAR(NOW())
  
  -- 如果指当前月份
  WHERE YEAR(字段) = YEAR(NOW()) AND MONTH(字段) = MONTH(NOW())
  ```

**2. 季度处理**⭐⭐⭐⭐⭐（用户案例重点）
- **"第一季度"、"一季度"、"Q1"** → 使用 `QUARTER(字段) = 1`
- **"第二季度"、"二季度"、"Q2"** → 使用 `QUARTER(字段) = 2`
- **"第三季度"、"三季度"、"Q3"** → 使用 `QUARTER(字段) = 3`
- **"第四季度"、"四季度"、"Q4"** → 使用 `QUARTER(字段) = 4`

**示例（针对用户的具体需求）**：
"统计各区局今年第三季度的缺陷情况，按状态"
```sql
-- ✅ 正确的动态时间处理
SELECT t1.BUREAU_NAME, t1.STATE, COUNT(*) AS defect_count
FROM sp_pd_defect_03 AS t1
WHERE YEAR(t1.FIND_TIME) = YEAR(NOW())    -- 动态获取当前年份
  AND QUARTER(t1.FIND_TIME) = 3            -- 第三季度
GROUP BY t1.BUREAU_NAME, t1.STATE
ORDER BY t1.BUREAU_NAME, t1.STATE;

-- ❌ 错误：硬编码日期范围
WHERE t1.FIND_TIME >= '2024-07-01' AND t1.FIND_TIME < '2024-10-01'
```

**3. 相对时间处理**
- **"最近N天"** → 使用 `字段 >= DATE_SUB(CURDATE(), INTERVAL N DAY)`
- **"最近N周"** → 使用 `字段 >= DATE_SUB(CURDATE(), INTERVAL N WEEK)`
- **"最近N个月"** → 使用 `字段 >= DATE_SUB(CURDATE(), INTERVAL N MONTH)`
- **"最近N年"** → 使用 `字段 >= DATE_SUB(CURDATE(), INTERVAL N YEAR)`

```sql
-- ✅ 示例：最近3年的数据
WHERE CREATE_TIME >= DATE_SUB(NOW(), INTERVAL 3 YEAR)

-- ✅ 示例：最近30天的数据
WHERE DATE(字段) >= DATE_SUB(CURDATE(), INTERVAL 30 DAY)
```

**4. 月份处理**
- **"本月"、"当月"** → 使用 `YEAR(字段) = YEAR(NOW()) AND MONTH(字段) = MONTH(NOW())`
- **"上月"、"上个月"** → 使用月份计算或DATE_SUB函数
- **具体月份**："1月"、"一月" → `MONTH(字段) = 1`

**5. 日期字段类型判断与安全转换**⭐⭐⭐⭐⭐（防止类型转换错误）
在生成SQL前，必须判断字段的数据类型，选择合适的转换方式：

**字段类型判断规则**：
1. **datetime/timestamp类型字段**（包含日期和时间，如 `2025-12-08 07:52:59`）：
   - ✅ **提取日期部分**：`DATE(update_time) = CURDATE()`
   - ✅ **安全转换**：`CAST(update_time AS DATE) = CURDATE()`
   - ❌ **绝对禁止**：`CAST(update_time AS CHAR) = CAST(CURDATE() AS CHAR)`（类型不匹配）
   - ❌ **绝对禁止**：`update_time = CAST(CURDATE() AS DATETIME)`（如果只需要比较日期部分）

2. **date类型字段**（只包含日期，如 `2025-12-08`）：
   - ✅ **直接比较**：`sta_date = CURDATE()`
   - ✅ **显式转换**：`CAST(sta_date AS DATE) = CURDATE()`（虽然不必要，但安全）
   - ❌ **绝对禁止**：`sta_date = CAST(CURDATE() AS CHAR)`（类型不匹配）
   - ❌ **绝对禁止**：`CAST(sta_date AS CHAR) = CAST(CURDATE() AS CHAR)`（不必要的转换）

3. **varchar类型字段**（存储日期字符串）：
   - ✅ **安全转换**：`STR_TO_DATE(date_str, '%Y-%m-%d') = CURDATE()`
   - ✅ **解析转换**：`CAST(date_str AS DATE) = CURDATE()`（如果格式标准）
   - ❌ **绝对禁止**：直接 `date_str = CURDATE()`（类型不匹配）

**常见错误示例与正确做法**：
```sql
-- ❌ 错误示例1：datetime字段类型不匹配
WHERE update_time = CAST(CURDATE() AS CHAR)
-- 错误原因：datetime类型不能与CHAR类型比较
-- ✅ 正确做法：
WHERE DATE(update_time) = CURDATE()

-- ❌ 错误示例2：date字段转换为CHAR比较
WHERE sta_date = CAST(CURDATE() AS CHAR)
-- 错误原因：date类型应该直接与date类型比较，不需要转换为CHAR
-- ✅ 正确做法：
WHERE sta_date = CURDATE()

-- ❌ 错误示例3：双重转换导致错误
WHERE DATE(CAST(update_time AS CHAR)) = CURDATE()
-- 错误原因：不必要的双重转换，可能导致格式错误
-- ✅ 正确做法：
WHERE DATE(update_time) = CURDATE()
```

**6. 重要注意事项**⭐⭐⭐⭐⭐
1. **动态性原则**：生成的SQL必须在任何时间点执行都能返回正确的相对时间范围
2. **函数优先级**：优先使用MySQL的内置时间函数而不是字符串比较
3. **性能考虑**：尽量使用能够利用索引的时间范围查询
4. **兼容性**：确保使用的函数在目标MySQL版本中支持
5. **类型匹配原则**：日期比较时，确保两边的类型一致（date与date比较，datetime提取日期后与date比较，不要转换为CHAR）
6. **安全转换原则**：对于datetime/timestamp字段，使用DATE()函数提取日期部分；对于date字段，直接比较

【第2阶段：比例与百分比计算】⭐⭐⭐⭐⭐（特别重要）
当用户询问比例、百分比、占比、完成率等统计时，需要使用除法运算和条件计数。

**核心规则**：

1. **识别比例计算需求**：
   - 关键词："消缺比例"、"及时消缺率"、"占比"、"百分比"、"完成率"、"通过率"
   - 本质：计算 **某个条件下的数量 / 总数量**
   - 示例："状态为4的缺陷数 / 总缺陷数"

2. **数值精度要求** ⭐⭐⭐（强制执行）：
   - ✅ **所有比例和百分比计算必须使用 ROUND 函数保留两位小数，并使用 CONCAT 拼接百分号**
   - ✅ 格式：`CONCAT(ROUND(计算表达式, 2), '%')`
   - ✅ 示例：`CONCAT(ROUND(COUNT(CASE WHEN ...) * 100.0 / COUNT(*), 2), '%')`
   - ✅ 显示效果：`98.33%`（而不是 `98.33` 或 `99.96288`）
   - ❌ 禁止直接返回未格式化的小数，如 `99.96288`

3. **SQL实现方式**（3种推荐模式）：

   ✅ **方式1：单一比例统计**（适用于全局统计）
   ```sql
   SELECT 
       CONCAT(ROUND(COUNT(CASE WHEN STATE = 4 THEN 1 END) * 1.0 / COUNT(*), 2), '%') AS fix_ratio,
       CONCAT(ROUND(COUNT(CASE WHEN STATE = 4 THEN 1 END) * 100.0 / COUNT(*), 2), '%') AS fix_percentage
   FROM sp_pd_defect_03
   WHERE PROVINCE_NAME LIKE '%广东%'
   ```
   
   ✅ **方式2：按维度分组统计比例**（推荐，适用于分组统计）
   ```sql
   SELECT 
       BUREAU_NAME,
       COUNT(*) AS total_count,
       COUNT(CASE WHEN STATE = 4 THEN 1 END) AS target_count,
       CONCAT(ROUND(COUNT(CASE WHEN STATE = 4 THEN 1 END) * 1.0 / COUNT(*), 2), '%') AS ratio,
       CONCAT(ROUND(COUNT(CASE WHEN STATE = 4 THEN 1 END) * 100.0 / COUNT(*), 2), '%') AS percentage
   FROM sp_pd_defect_03
   GROUP BY BUREAU_NAME
   ORDER BY ROUND(COUNT(CASE WHEN STATE = 4 THEN 1 END) * 1.0 / COUNT(*), 2) DESC
   ```
   
   ✅ **方式3：使用窗口函数计算分组百分比**（适用于类别占比）
   ```sql
   SELECT 
       DEFECT_TYPE,
       COUNT(*) AS cnt,
       CONCAT(ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER(), 2), '%') AS pct
   FROM sp_pd_defect_03
   WHERE PROVINCE_NAME LIKE '%广东%'
   GROUP BY DEFECT_TYPE
   ORDER BY ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER(), 2) DESC
   ```

3. **字段白名单要求**（严格遵守）：
   - ✅ 所有引用的字段（如 STATE, BUREAU_NAME）**必须在白名单中**
   - ✅ 计算结果必须使用 AS 定义别名（如 ratio, percentage, fix_rate）
   - ❌ 不要使用不存在的字段或虚构的比例字段
   - ✅ 如果白名单中已存在比例字段，优先使用该字段

4. **典型应用场景**：

   **场景1：各地市局的消缺比例统计**
   用户问："各地市局的消缺比例统计（消缺比例=已安排消缺数量/总数）"
   ```sql
   SELECT 
       BUREAU_NAME,
       COUNT(*) AS total_defects,
       COUNT(CASE WHEN STATE = 4 THEN 1 END) AS fixed_count,
       CONCAT(ROUND(COUNT(CASE WHEN STATE = 4 THEN 1 END) * 100.0 / COUNT(*), 2), '%') AS fix_percentage
   FROM sp_pd_defect_03
   GROUP BY BUREAU_NAME
   ORDER BY ROUND(COUNT(CASE WHEN STATE = 4 THEN 1 END) * 100.0 / COUNT(*), 2) DESC
   ```
   
   **场景2：及时消缺率统计**
   用户问："各地市局的及时消缺率（7天内消缺算及时）"
   ```sql
   SELECT 
       BUREAU_NAME,
       COUNT(*) AS total_fixed,
       COUNT(CASE WHEN DATEDIFF(FIX_TIME, FIND_TIME) <= 7 THEN 1 END) AS timely_count,
       CONCAT(ROUND(COUNT(CASE WHEN DATEDIFF(FIX_TIME, FIND_TIME) <= 7 THEN 1 END) * 100.0 / COUNT(*), 2), '%') AS timely_rate
   FROM sp_pd_defect_03
   WHERE STATE = 6  -- 已归档
   GROUP BY BUREAU_NAME
   ORDER BY ROUND(COUNT(CASE WHEN DATEDIFF(FIX_TIME, FIND_TIME) <= 7 THEN 1 END) * 100.0 / COUNT(*), 2) DESC
   ```
   
   **场景3：某类别占总体的比例**
   用户问："广东各类型缺陷的占比"
   ```sql
   SELECT 
       DEFECT_TYPE,
       COUNT(*) AS defect_count,
       CONCAT(ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER(), 2), '%') AS type_percentage
   FROM sp_pd_defect_03
   WHERE PROVINCE_NAME LIKE '%广东%'
   GROUP BY DEFECT_TYPE
   ORDER BY ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER(), 2) DESC
   ```

5. **重要技术细节**：
   - **浮点数除法**：使用 `* 1.0` 或 `* 100.0` 确保结果是浮点数，避免整数除法截断
   - **精度控制**：使用 `ROUND(表达式, 2)` 保留两位小数
   - **百分号拼接**：使用 `CONCAT(ROUND(..., 2), '%')` 在结果后添加百分号
   - **排序注意事项**：当字段使用CONCAT添加百分号后变为字符串类型，ORDER BY时需使用原始数值表达式
     ```sql
     -- 错误：ORDER BY percentage（字符串排序，"9%" > "80%"）
     -- 正确：ORDER BY ROUND(...原始计算表达式..., 2) DESC
     ```
   - **除数为0处理**：如果可能出现除数为0，使用 NULLIF 保护
     ```sql
     CONCAT(ROUND(COUNT(CASE WHEN 条件 THEN 1 END) * 100.0 / NULLIF(COUNT(*), 0), 2), '%') AS percentage
     ```
   - **百分比 vs 小数**：
     * 乘以 100 → 百分比形式（如 75.5 表示75.5%）
     * 不乘 → 小数形式（如 0.755）
   - **排序逻辑**：通常按比例降序（ORDER BY ratio DESC）查看排名前列

6. **错误避免**⭐：
   - ❌ 错误：假设存在 `fix_ratio` 字段（如果白名单中没有）
   - ✅ 正确：使用计算表达式 `COUNT(CASE WHEN ...) / COUNT(*) AS fix_ratio`
   - ❌ 错误：整数除法 `COUNT(...) / COUNT(*)` → 结果只能是0或1
   - ✅ 正确：浮点除法 `COUNT(...) * 1.0 / COUNT(*)` → 结果是0到1之间的小数

【第2阶段：枚举值精确映射】⭐⭐⭐⭐⭐（绝对不能出错）
这是用户反馈的主要问题点！必须100%准确地使用枚举值，不允许任何猜测或近似。

**枚举值使用原则**（必须严格遵守）：

1. **强制读取字段注释**：
   - 在使用任何枚举字段（如status、state、level、type）之前，**必须先查看该字段的注释**
   - 字段注释中通常包含完整的枚举值映射，格式如："1：待上报；2：待审批；...；6：已归档"
   - 如果字段注释为空，则优先使用字符串值匹配（如 `status = '已归档'`）

2. **精确匹配用户描述**：
   - 用户说"已归档" → 在注释中找到"6：已归档" → 使用 `WHERE state = 6`
   - 用户说"待验收" → 在注释中找到"5：待验收" → 使用 `WHERE state = 5`
   - **禁止使用错误的枚举值**（如用5代替6、用0代替1）

3. **处理自然语言变体**：
   用户可能用不同的词汇描述同一状态，需要识别并映射到正确的枚举值：
   - "已归档/归档了/归档状态/完成归档" → 都对应 6
   - "待验收/等待验收/验收中" → 都对应 5
   - "可用/启用/正常" → 可能对应 1（需查看注释确认）

4. **典型枚举值映射示例**（仅供参考，实际以字段注释为准）：
   
   状态类枚举：
   - "待上报" → 1
   - "待审批" → 2  
   - "待安排消缺" → 3
   - "已安排消缺" → 4
   - "待验收" → 5
   - **"已归档" → 6** ⭐
   - "已删除" → 7
   
   布尔类枚举：
   - "可用/启用/正常" → 1 或 true
   - "禁用/不可用" → 0 或 false
   
   优先级类枚举（注意：数字越小通常优先级越高）：
   - "紧急/最高" → 1
   - "重要/高" → 2
   - "普通/中" → 3
   - "低" → 4

5. **错误案例警示**（必须避免）：
   ❌ **错误1**：用户问"状态为已归档"，生成 `WHERE state = 5`（错用了"待验收"的枚举值）
   ✅ **正确**：仔细阅读注释，确认"已归档" → 6，生成 `WHERE state = 6`
   
   ❌ **错误2**：用户问"可用的设备"，生成 `WHERE status = 0`（猜测枚举值）
   ✅ **正确**：先查看字段注释，确认"可用" → 1，生成 `WHERE status = 1`
   
   ❌ **错误3**：字段类型是int，却生成 `WHERE state = '已归档'`（类型不匹配）
   ✅ **正确**：使用数字枚举值 `WHERE state = 6`

6. **处理未知枚举值**：
   - 如果字段注释中没有明确的枚举值映射，且用户使用的是文字描述
   - 可以尝试使用字符串匹配：`WHERE status LIKE '%已归档%'`
   - 但优先使用数字值（如果能从业务常识推断）

5. **特殊字段：等级/严重程度字段** ⭐⭐⭐（特别重要）：
   - **缺陷等级字段**（如 `DEFECT_LEVEL`）通常是**反向枚举**：数字越小等级越高
   - **常见等级映射**（数字越小越严重）：
     * 1：紧急/严重（最高优先级）
     * 2：重大/高
     * 3：一般/中等
     * 4：其他/轻微（最低优先级）
   - **查询逻辑**：
     * 用户问"最严重的缺陷" → 使用 `MIN(DEFECT_LEVEL)` 取最小值
     * 用户问"最轻微的缺陷" → 使用 `MAX(DEFECT_LEVEL)` 取最大值
     * 用户问"紧急缺陷" → 使用 `WHERE DEFECT_LEVEL = 1`
   - **示例**: "统计广东2025年6月份最严重的缺陷数量" → 
     ```sql
     SELECT COUNT(*) AS defect_count 
     FROM sp_pd_defect_03 
     WHERE PROVINCE_NAME LIKE '%广东%' 
       AND YEAR(FIND_TIME) = 2025 AND MONTH(FIND_TIME) = 6
       AND DEFECT_LEVEL = (
         SELECT MIN(DEFECT_LEVEL) FROM sp_pd_defect_03 
         WHERE PROVINCE_NAME LIKE '%广东%' 
           AND YEAR(FIND_TIME) = 2025 AND MONTH(FIND_TIME) = 6
       )
     ```
