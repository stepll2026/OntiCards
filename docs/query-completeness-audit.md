# 问数完整性核验与改进

核验日期：2026-09-15。代码基线：`7286516`。

## 结论与证据范围

代码中确实存在“条件或字段遗漏，仍按成功返回”的路径。旧提示词明确允许忽略白名单无法支持的条件、少返回字段，并假设后续融合可以补齐；执行器主要验证 SQL 安全和可执行性，没有逐项核对原始需求。

在相同合成数据上，向旧执行器注入遗漏姓名条件的 SQL，会返回 **2 行且没有错误**；新路径发现遗漏、修复并复核后返回 **1 行**。这验证了问题类型，不代表复现了第三方的业务数据。

反馈中的原始业务库、数据卡片版本、完整 SQL 和会话日志未提供；测试服务器没有这些原始业务数据。因此，反馈中的 **944 / 7、241 / 222** 行数及完整操作经过仍属于用户报告，不能据此声称已独立确认这些具体计数。

## 必须注意的行为变化

1. **无法验证的结果返回失败。** 缺少校验报告、模型输出无效、缺表、缺字段、二进制结果、重复表头和实际取数截断均不能继续作为成功结果展示。合法的零行查询保留输出列元数据，可以成功返回。
2. **传统多数据源融合暂停返回成功结果。** 旧融合只向模型提供受限的行列样本，无法据此验证全部条件和行数。多个独立连接需要传统融合时，在分簇后直接返回 `422 / unverified`，避免继续执行无法验证的分量查询。单连接内的多表 SQL 继续支持；已有 Trino 统一查询路径进行整体 SQL 校验。恢复传统融合需要确定性的完整数据关联执行及相应测试。
3. **多数据库与多数据源分别处理。** 方言解析支持 MySQL、PostgreSQL、SQL Server、Oracle、SQLite、Trino，以及项目已有的 Kingbase、OceanBase MySQL 模式、DM 映射；这不等于已经连接九种数据库完成集成验证。
4. **检索保留授权范围。** 初始卡片和依赖补查均限定用户与所选数据源；兼容旧卡片的空归属冗余字段，以 schema 的所有者和连接范围核对。同名表需要明确 schema；重复连接名称会报错，避免选错连接。
5. **有明确容量边界。** 每次查询最多 16 个不同检索问题、80 张卡片；超过容量明确报错。取数超过 1,000 行会标记截断并返回失败，需要缩小范围。SQL 中未经原句授权的 LIMIT/TOP/ROWNUM 由独立模型审核，尚未形成完整的确定性证明。
6. **增加模型与检索成本。** 新增一次需求解析和一次 SQL 审核；修复时增加修复与再审核。逐项召回也会增加 embedding/rerank 调用。已移除查询前无必要的融合策略模型调用。不能承诺所有场景的耗时下降。
7. **校验不是业务正确性的数学证明。** 需求解析和独立审核仍可能误解原句，也可能误拦有效查询。SQL 语法树证据检查、行列结构检查和数据库执行共同降低遗漏风险；实际验收仍应使用原始业务库、真实提问及对照 SQL。
