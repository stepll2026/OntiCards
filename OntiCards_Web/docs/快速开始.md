# 快速开始

**欢迎使用 OntiCards AI数据中枢**

- OntiCards 让您可以**用自然语言提问**来查询数据库，就像和数据库"聊天"一样简单。  
- 无需学习 SQL，无需了解表结构，只要会说话，就能查数据、看报表、做分析。

---

## 一、我能用它做什么？

- **查数据**：随时查询订单、库存、客户、资金等各类业务数据  
- **做分析**：快速对比不同时间、地区、门店、产品的业务表现  
- **跨系统汇总**：一次提问，同时查询多个系统并自动整合结果  
- **发现问题**：主动发现库存告警、异常交易、异常波动等情况  
- **辅助决策**：为补货、促销、风控、运营决策提供及时数据支撑
- **数据质检**：对数据库质量进行定期检查，发现空值、格式错误、重复等数据问题
- **质量报告**：生成数据质量报告，了解数据健康状况和问题分布

> **一句话概括**：把您平时要找技术或数分同事帮忙做的查询，现在都可以自己一句话搞定。

---

## 二、完整使用流程一览

1. **连接数据库**：把您的业务数据库接入系统
2. **生成数据卡片**：系统自动理解表结构和业务含义
3. **数据盘点（可选）**：建立表间关系，提升多表查询准确率
4. **配置术语库（可选）**：建立业务术语标准，提升查询准确率
5. **自然语言提问**：在查询框输入问题即可
6. **查看结果与解释**：看到数据、来源以及系统的理解方式
7. **按需调整问题**：不满意就换一种问法再问一次
8. **数据质检（可选）**：对数据质量进行检查，发现数据问题
9. **生成质量报告**：了解数据健康状况，指导数据改进

下面按步骤详细说明。

## 三、SSO单点登录（可选功能）

如果您所在企业已配置统一身份认证，可以通过SSO方式快速登录OntiCards，无需单独注册账号。

### 3.1 什么是SSO单点登录

SSO（Single Sign-On，单点登录）是一种企业级身份认证方式，允许用户使用企业统一账号登录OntiCards，实现一次登录、多系统通行。

**适用场景：**
- 企业已部署统一身份认证平台（如LDAP、OAuth、OIDC等）
- 希望员工使用企业邮箱/工号登录，无需单独管理OntiCards账号
- 需要与现有企业系统（如钉钉、企业微信、飞书等）集成

### 3.2 SSO登录方式

**JWT Token模式（推荐）**

该模式适用于已建立自己用户体系的企业系统，通过JWT Token实现与OntiCards的免登录对接。

**核心流程：**
```
1. 企业系统验证用户身份
2. 企业后端生成JWT Token（包含用户信息）
3. 跳转到OntiCards SSO接口完成登录
4. OntiCards创建/关联用户并返回Token
5. 登录成功，自动跳转回目标页面
```

**JWT Token包含的字段：**

| 字段 | 必填 | 说明 |
|------|------|------|
| username | ✅ | 用户唯一标识 |
| user_id | ✅ | 用户在企业系统中的ID |
| nickname | ❌ | 用户昵称 |
| email | ❌ | 用户邮箱 |
| source | ❌ | 来源标识，默认default |
| exp | ✅ | Token过期时间（建议5分钟内） |

**详细接入指南：** 请联系产品研发团队

### 3.3 企业账号登录（传统模式）

如果没有配置SSO，用户也可以使用独立的OntiCards账号登录：
- 输入用户名和密码
- 支持密码找回功能
- 支持记住登录状态

## 四、第一步：连接您的数据库

**这一步做什么？**  
把您的业务数据库接入 OntiCards，让系统知道“到哪里去查数据”。

**典型适用数据库：**
- 业务系统数据库：电商、ERP、CRM、仓储、财务等
- 常见类型：Oracle、MySQL、PostgreSQL、SQL Server、SQLite、Trino、**电科金仓（KingBase）**、**OceanBase（MySQL 租户模式）**、**达梦（DMBase）** 等
> **💡 TIP**：OceanBase 原生提供 MySQL 与 Oracle 双兼容模式，当前已支持 **MySQL 租户模式**；**Oracle 租户模式将在后续版本中支持**。

**操作步骤：**

1. 进入系统后，打开**数据源管理 / 添加数据源**页面  
2. 填写数据库连接信息（一般由 IT/DBA 提供）：
   - **数据源名称**：给这个数据库起个容易记的名字，如“电商生产库”“华南仓库库”
   - **数据库类型**：选择 MySQL、Oracle、PostgreSQL、SQL Server、SQLite、Trino、**电科金仓（KingBase）**、**OceanBase（MySQL 租户模式）**、**达梦（DMBase）** 等
   - **主机地址**：数据库服务器地址（IP 或域名）
   - **端口号**：数据库端口（通常使用默认值即可）
   - **用户名/密码**：数据库账号和密码
   - **数据库名**：需要查询的具体数据库名称
3. 点击 **“测试连接”**，确认能否正常连接  
4. 测试通过后，点击 **“保存”**，系统会开始自动扫描表结构

**小贴士：**
- 如果您不确定连接信息，请联系 IT/DBA 获取  
- 一个账号可以添加多个数据源，后续查询时系统会自动选择合适的数据源

## 五、第二步：等待数据卡片生成

**这一步做什么？**  
系统会自动分析您数据库中的所有表，理解每张表的用途、字段含义，并生成智能化的**数据卡片**。  
有了这些卡片，系统才能听懂您说的“销量”“库存不足”“高价值客户”等业务词。

**数据卡片大致包含：**
- **表是做什么的**：比如“商品基础信息”“订单明细”“仓库库存”等  
- **关键字段说明**：如 price=价格，stock=库存数量，warehouse=仓库  
- **常见查询场景**：如“按时间统计销量”“按地区对比销售额”“库存告警筛选”等  
- **业务关键词**：如“蓝牙耳机、数码产品、退款单、黑名单客户”等

**通常需要多长时间？（仅需首次生成）**
- 10 张表以内：约 2–3 分钟  
- 50 张表：约 10–15 分钟  
- 100 张表：约 25–30 分钟

**注意：**
- 数据卡片**只需生成一次**，之后系统会自动使用并按需增量更新
- 如果后续数据库结构有明显变更，可以在数据源管理中执行"刷新数据源"

## 六、第三步：数据盘点（可选但推荐）

**这一步做什么？**
数据盘点帮助系统理解表与表之间的关系（如订单表和客户表通过customer_id关联），从而在多表查询时生成更准确的SQL。

**为什么要做数据盘点？**
- 提升多表查询准确率20-25%
- 减少JOIN条件错误和笛卡尔积问题
- 支持跨数据源关系识别
- 让系统更好地理解您的业务数据结构

**两种盘点方式：**

### 方式一：全域盘点（推荐新手）

**适用场景**：快速建立完整的数据关系图谱

**操作步骤**：
1. 进入**数据盘点 / 全域盘点**页面
2. 选择要盘点的数据源（可选择单个或多个数据源）
3. 点击**"开始盘点"**
4. 等待系统自动分析（通常5-30秒）
5. 查看盘点结果：发现了多少表关系、生成了多少关系卡片

**特点**：
- 全自动，无需人工干预
- 一键完成所有表的关系发现
- 支持跨数据源关系识别

### 方式二：定向盘点（适合精细化管理）

**适用场景**：对核心业务表进行精细化治理

**操作步骤**：
1. 进入**数据盘点 / 定向盘点**页面
2. 选择目标表（需要补充注释的表）
3. 选择参考表（用于提供候选注释）
4. 点击**"开始盘点"**
5. 查看并确认系统推荐的字段注释
6. 查看并确认系统推断的表关系
7. 点击**"生成关系卡片"**

**特点**：
- 支持字段级别的注释推荐
- 需要人工确认，质量更高
- 适合逐步推进的数据治理项目

**小贴士**：
- 如果您是第一次使用，建议先用**全域盘点**快速建立关系图谱
- 数据盘点不是必须的，但强烈推荐，尤其是需要多表查询的场景
- 盘点结果会自动保存，后续查询时系统会优先使用这些关系信息

## 七、第四步：配置业务术语库（可选但推荐）

**这一步做什么？**
业务术语库帮助系统理解您企业的业务术语，如"高价值客户"、"核心商品"等业务概念的真正含义，从而在查询时自动识别和展开这些术语。

**为什么要配置术语库？**
- 统一企业业务语言，消除部门间的理解歧义
- 提升查询准确率，减少因术语理解偏差导致的查询错误
- 新员工可以快速了解业务术语标准，无需深入了解数据库字段

**术语库包含：**
- **术语库**：按业务领域分类，如"销售术语库"、"库存术语库"
- **术语**：每个业务术语的名称、定义、同义词、关联字段
- **关联数据卡片**：术语涉及的原始数据卡片

**典型应用场景：**

| 用户提问 | 系统理解 |
|---------|---------|
| "查询高价值客户的订单" | 高价值客户 → VIP等级='钻石' 且 累计消费>10000 |
| "核心商品的库存情况" | 核心商品 → 产品分类 IN ('A类', 'B类') |
| "沉默用户的激活情况" | 沉默用户 → 最近90天无购买行为 |

**操作步骤：**
1. 进入**术语库管理**页面
2. 创建术语库（如"销售术语库"），设置名称和描述
3. 添加业务术语，设置术语名称、定义和关联字段
4. 将术语库关联到对应的数据源
5. 启用术语库，开始在查询中使用

**小贴士：**
- 术语库是可选的，但不配置时系统只能基于数据卡片理解查询
- 术语同义词功能强大，可以识别"销售额"、"营收"、"收入"等多种叫法
- 术语库可以按数据源关联，不同数据源使用不同的术语库

## 八、第五步：用自然语言开始提问

**这一步做什么？**  
您只需要像跟同事说话一样，直接把问题打出来，系统会自动：
- 理解您的业务意图  
- 找到最相关的表和字段  
- 自动生成并执行查询  
- 把结果整理好返回给您

### 8.1 推荐的提问方式

在查询框中输入完整的问题，例如：

| 提问示例 | 系统会做什么 |
|---------|-------------|
| “广州仓库有哪些库存低于 50 的商品？” | 查找库存相关表，筛选仓库=广州且库存 < 50 的记录 |
| “统计最近 30 天销量超过 100 件的商品” | 查找订单相关表，按时间和销量条件进行统计 |
| “价格在 100 到 300 元之间的数码产品” | 查找商品表，按价格区间与品类筛选 |
| “在广州和深圳都有库存的商品” | 跨多个仓库数据库查询，找出有共同库存的商品 |

### 8.2 不推荐的提问方式

| 提问示例 | 问题所在 |
|---------|---------|
| “查一下库存” | 太模糊：不知道查什么仓库、什么商品、哪个时间段 |
| “商品” | 只有一个词，无法判断想要看什么指标 |
| “帮我看看数据” | 没有具体目标，系统无法理解 |

### 8.3 提问小技巧

1. **说清楚查什么**：商品、订单、客户、门店、仓库、资金等  
2. **说清楚条件**：如“最近 30 天”“价格低于 100”“库存不足安全库存”等  
3. **说清楚范围**：时间范围、地区范围、门店范围、金额区间等  
4. **用业务语言表达**：说“销量最好的商品”，而不是“order_count 最大的记录”

## 九、第六步：查看和理解查询结果

**这一步做什么？**  
系统会把查询结果整理成易于理解的形式，同时告诉您“数据从哪来、条件怎么用的”。

**结果页面通常包含：**

1. **数据表格**  
   - 以行列形式展示数据  
   - 支持按列排序、简单筛选等操作  
2. **数据来源说明**  
   - 显示数据来自哪个数据库、哪些表  
   - 方便您核对数据是否可信、是否完整  
3. **查询理解说明**  
   - 系统会用自然语言说明：它是如何理解您的问题的  
   - 比如：“按仓库=广州、当前库存 < 50 进行筛选”  
4. **提示与告警**  
   - 某些条件无法满足时，会明确提示哪些条件被忽略、为什么被忽略  
   - 跨库查询时，也会说明具体整合方式

**简要示例：**

```
【查询】广州仓库库存低于 50 的商品

【结果】共找到 3 条记录

┌────────────┬────────┬──────────┬──────────┐
│  商品名称   │  仓库  │ 当前库存 │ 安全库存 │
├────────────┼────────┼──────────┼──────────┤
│  蓝牙耳机   │  广州  │    45    │   100    │
│  充电宝     │  广州  │    32    │    80    │
│  无线鼠标   │  广州  │    18    │    50    │
└────────────┴────────┴──────────┴──────────┘

【数据来源】电商数据库 > inventory 表
【查询说明】筛选条件：仓库位置='广州' 且 当前库存<50
```

如果结果不符合预期，您可以：
- 查看“查询说明”，看系统是否理解偏了  
- 稍微改写问题，再查询一次（例如补充时间、地区等条件）

## 十一、数据治理模块 - 数据质检（入门指南）

数据治理是帮助企业检查数据质量、发现数据问题的重要工具。OntiCards 提供完整的数据质检能力，让您可以系统化地管理和提升数据质量。

### 11.1 什么是数据质检

数据质检是指对数据库中的数据进行系统性检查，发现空值、格式错误、重复数据、违规划数据等问题。质检结果可以生成报告，帮助数据团队了解数据健康状况并指导改进。

**两阶段设计：**
- **第一阶段 - 数据质检（当前功能）**：检查数据问题、生成质量报告
- **第二阶段 - 实际治理（规划中）**：修复数据问题、对账核对、告警通知

### 11.2 数据质检的两种模式

数据质检模块提供两种检测模式，满足不同的质检需求：

**模式一：基于规则库的质检**

通过自定义质检规则，对数据进行系统性检查。适合有明确质量标准的数据检测场景。

- **规则库管理**：按业务领域或数据类型创建规则库
- **多模式规则创建**：支持模板模式、AI自然语言模式、手动模式三种方式
- **多类型规则支持**：非空检查、唯一性检查、格式校验、范围检查、枚举值检查、正则匹配等

**模式二：基础空值检测**

自动扫描数据库中各表的空值情况，快速发现数据完整性问题。适合快速了解数据健康状况。

- **自动扫描**：无需配置，系统自动扫描所有表的空值情况
- **统计全面**：统计每个字段的空值率，帮助定位问题
- **快速上手**：一键执行，即刻了解数据完整性

**统一体验**

两种模式的执行明细统一存储，形成完整的质量检测记录，便于后续治理阶段的实施和质量趋势分析。

### 11.3 完整使用流程

1. **创建规则库**：为特定业务场景建立规则集合
2. **添加质检规则**：定义需要检查的数据质量标准
3. **执行规则**：批量运行规则，收集检测结果
4. **生成报告**：输出可读的质量报告，记录问题详情
5. **问题分析**：根据报告分析问题原因，制定改进计划

### 11.4 规则库管理

规则库是质检规则的组织单位，建议按业务领域或数据类型划分：

**操作步骤：**
1. 进入**数据治理 / 规则库管理**页面
2. 点击**"创建规则库"**
3. 设置规则库名称和关联的数据源
4. 保存后即可开始添加规则

**小贴士：**
- 一个规则库建议关联一个数据源
- 可以按业务线或数据类型创建多个规则库
- 规则库支持修改名称和描述

### 11.5 添加质检规则

质检规则定义了数据需要满足的质量标准。OntiCards 支持三种创建方式：

**方式一：模板模式（推荐新手）**

从预设的规则模板中选择，系统已为常见场景预置了规则。

**适用场景：**
- 快速建立质检体系
- 通用数据质量检查
- 标准化质量要求

**方式二：AI自然语言模式（推荐）**

用日常语言描述您想检查的规则，系统自动转换为质检规则。

**示例：**
| 您说的话 | 系统理解的规则 |
|---------|---------------|
| "检查邮箱格式是否正确" | 字段格式校验：邮箱正则 |
| "检查手机号是否为11位" | 长度校验：手机号字段 |
| "检查金额字段不能为空" | 非空校验：金额字段 |

**方式三：手动模式（适合专家）**

直接配置规则的各项参数，适合有经验的用户。

**支持的规则类型：**
- 非空检查：字段值不能为空
- 唯一性检查：字段值不能重复
- 格式校验：邮箱、手机号、身份证等格式
- 范围检查：数值在合理范围内
- 枚举值检查：值必须在指定列表中
- 正则匹配：自定义规则表达式
- 跨表比对：两张表的数据一致性
- 自定义SQL：使用SQL定义复杂规则

### 11.6 执行质检规则

规则创建完成后，可以批量执行进行检查。

> **执行质检的重要注意事项**
>
> 1. **数据静态性要求**：如果要使用质检功能，最好确保业务系统数据库（数据源或数据空间中的相关数据库表）中没有实时数据中途更新，否则会影响质检结果。质检过程中针对的数据范围是静态数据场景，请合理安排执行时间。
>
> 2. **执行时间建议**：质检执行可能消耗一定数据库资源，建议在业务低峰期执行大规模质检。

**操作步骤：**
1. 进入**数据治理 / 规则执行**页面
2. 选择要执行的规则库或指定具体规则
3. 点击**"开始执行"**
4. 等待执行完成（可查看进度）
5. 查看执行结果和统计数据

**执行结果包含：**
- 总数据量：通过和失败的数量统计
- 质量评分：基于通过率计算的质量分数
- 失败明细：不符合规则的具体数据样本
- 问题分布：按规则类型统计问题数量

**质量评分等级：**
| 等级 | 分数范围 | 说明 |
|------|---------|------|
| 优秀 | 95分以上 | 数据质量非常好 |
| 良好 | 85-95分 | 数据质量良好 |
| 一般 | 70-85分 | 有改进空间 |
| 较差 | 60-70分 | 问题较多 |
| 差 | 60分以下 | 严重问题 |

### 11.7 生成质量报告

执行完成后，可以生成详细的质量报告。

**操作步骤：**
1. 在执行结果页面，点击**"生成报告"**
2. 选择报告格式（Markdown/Word/PDF/Excel）
3. 系统自动生成报告
4. 下载或在线查看报告

**报告包含内容：**
- **执行概览**：执行时间、数据量、评分等级
- **问题汇总**：按类型统计问题数量和分布
- **详细结果**：每条规则的具体执行结果
- **样本数据**：失败数据的具体示例
- **改进建议**：基于问题的优化方向
- **趋势分析**：与历史执行结果的对比

**报告价值：**
- 满足合规审计要求
- 记录数据质量变化趋势
- 为数据改进提供依据
- 方便团队沟通和汇报

### 11.8 典型使用场景

**场景一：上线前数据验证**

在新系统上线或数据迁移后，批量执行质检规则，确保数据质量符合预期。

**场景二：定期质量巡检**

按周或月定期执行质检，监控数据质量变化趋势，及时发现新出现的问题。

**场景三：关键数据监控**

对核心业务表设置质检规则，在数据异常时快速发现并处理。

**场景四：第三方数据校验**

对接外部数据源时，用质检规则验证外部数据的完整性和准确性。

### 11.9 与数据查询的协同

数据治理模块与智能查询模块相互配合，形成完整的数据管理闭环：

1. **质检发现的问题** → 通过查询模块深入分析问题数据
2. **查询发现的异常** → 可以创建质检规则持续监控
3. **数据盘点建立的关系** → 质检规则可利用关系信息进行跨表校验
4. **术语库定义的概念** → 质检规则可基于业务术语进行检查

## 十二、常见问题（新用户必看）

### 12.1 查不到想要的数据怎么办？

**可能原因：**
- 数据卡片尚未生成完成  
- 提问不够具体，系统无法准确理解  
- 数据库结构刚刚发生了变化，尚未刷新

**建议做法：**
- 在“数据源管理”中查看数据卡片生成进度，如有需要执行“刷新数据源”  
- 换一种更具体的问法，例如：  
  - × “查库存” → √ “查询广州仓库库存低于 50 的商品”  
  - × “销量” → √ “统计最近 30 天销量超过 100 件的商品”

---

### 12.2 为什么提示“部分条件已忽略”？

说明系统理解了您的问题，但在当前数据库中找不到某些条件对应的字段。  
为保证您仍然能看到有价值的结果，系统会：
- 先执行那些“能满足”的条件  
- 在结果中明确提示哪些条件被忽略，例如：“已忽略条件：好评率（字段不存在）”

**如何减少这种情况：**
- 使用您所在企业数据表中真实存在的业务字段/口径  
- 如不确定，可以先问一句：“商品相关都有哪些字段可以查？”

---

### 12.3 查询多个数据库时，我需要做什么配置？

您**不需要写任何复杂配置**。只要：
- 在系统中分别添加多个数据源  
- 在提问中自然表达您的意图，例如：
  - “在广州和深圳都有库存的商品”  
  - “汇总所有仓库最近 30 天的销量”

系统会自动：
1. 找到涉及的所有数据源和数据表  
2. 分别查询  
3. 根据您的语义选择合适的整合方式（交集 / 并集 / 汇总）

---

### 12.4 查询速度有点慢怎么办？

**常见原因：**
- 单个表数据量很大  
- 查询条件过于宽泛，未限制时间或范围  
- 第一次查询某些表时，系统需要额外理解表结构

**建议：**
- 增加时间范围限制，如“最近 30 天”“本月”“本周”  
- 尽量加上必要的筛选条件（地区、品类、金额区间等）  
- 避免一次性查询过多表或所有历史数据

---

### 12.5 数据源结构变了需要我做什么？

如出现以下情况，建议在系统中**刷新数据源**：
- 新增了表  
- 删除了表  
- 字段有较大调整（新增、删除、重命名）  
- 表的业务含义发生了明显变化

在“数据源管理”中：
1. 找到对应的数据源  
2. 点击“刷新数据源”  
3. 选择合适的刷新方式（如仅测试连接、或完整刷新结构）  
系统会智能识别变化的表，只更新有变更的部分，节省时间。

---

### 12.6 系统如何保障数据安全？

- **访问隔离**：每位用户只能访问自己添加的数据源，互相不可见  
- **只读查询**：系统只执行查询操作，不提供修改、删除数据的入口  
- **敏感信息保护**：数据库密码加密存储，不会出现在界面、结果或日志中  

> 您可以放心使用：OntiCards 只负责“帮您查”，不会“帮您改”任何业务数据。

## 十三、使用技巧与最佳实践

### 13.1 用日常业务语言提问

- **推荐**：  
  - “查询销量最好的商品”  
  - “最近 30 天退货率最高的前 20 个商品”
- **不太推荐**：  
  - “查询 order_count 字段最大的商品”

---

### 13.2 把复杂问题拆成几步

对于特别复杂的问题，建议拆成几条简单的查询：

- 复杂问题示例：  
  “统计每个地区销量前 10 的商品，并对比不同地区的价格差异”
- 拆分方式：  
  1. “统计广州地区销量前 10 的商品”  
  2. “统计深圳地区销量前 10 的商品”  
  3. “对比同一商品在不同地区的价格”

---

### 13.3 善用时间范围

清晰的时间范围可以：
- 提升查询速度  
- 让结论更加贴近当前业务情况  
- 避免被多年历史数据“稀释”

示例提问：
- “最近 7 天的订单情况”  
- “本月的销售额及去年同期对比”  
- “2024 年 1 月的新注册用户数”

---

### 13.4 整理常用问题

对于高频使用的查询，建议：
1. 把提问内容整理到文档或知识库  
2. 每次直接复制粘贴原问题，保证口径一致  
3. 如有多名同事共用，可统一一份“常用问题库”

## 十四、历史查询与监控

### 14.1 查看历史查询记录

每次查询后，系统会自动记录完整的查询信息，包括：

- **查询内容**：您的问题、生成的SQL、涉及的数据源
- **性能指标**：总耗时、各环节耗时（向量检索、重排序、SQL执行等）
- **Token消耗**：Embedding、Rerank、LLM各类Token数量
- **查询质量**：召回卡片数、重排序分数等

**如何查看：**
1. 进入**历史查询**页面
2. 可以按时间范围、数据源、状态等筛选
3. 点击任意记录查看详情

**跨数据源查询同步：**
- 在跨数据源查询场景下，系统会自动记录完整的查询来源和涉及的数据源
- 无论从哪个数据源发起查询，都可以在被涉及的数据源历史中查看这条记录
- 支持按任意涉及的数据源筛选，快速追溯跨数据源查询的全貌

### 14.2 监控中心

监控中心提供系统使用情况的全面概览：

**监控总览**
- 实时统计：今日和最近24小时的查询量、成功/失败次数
- Token消耗统计：各类Token的使用量
- 成本预估：基于配置的Token价格计算预估成本
- 趋势对比：与昨日、上周同期对比

**趋势分析**
- 每日趋势：展示最近30天的查询量变化
- 各环节耗时分布：快速识别性能瓶颈
- 数据源使用排行：了解哪些数据源使用频率最高

**性能分析**
- 各环节耗时：向量检索、重排序、SQL生成、SQL执行
- 慢查询TOP：耗时最长的查询记录
- 查询复杂度分布：简单查询、多表查询、跨库查询占比

### 14.3 成本配置

管理员可以配置Token价格，用于成本预估：

| 配置项 | 默认值            | 说明 |
|--------|----------------|------|
| Embedding价格 | 0.0005元/千token | 向量检索成本 |
| Rerank价格 | 0.0008元/千token | 重排序成本 |
| LLM输入价格 | 0.0024元/千token | SQL生成输入成本 |
| LLM输出价格 | 0.0096元/千token | SQL生成输出成本 |

**注意**：成本为预估值，实际费用以云厂商账单为准。

### 14.4 数据保留策略

系统支持配置历史数据的保留天数，避免数据无限增长：

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| 查询日志保留 | 180天 | 历史查询明细保留时间 |
| 聚合统计保留 | 365天 | 日聚合数据保留时间 |

数据会由定时任务自动清理，也可以手动触发清理。

## 十五、其他小问题

### 15.1 退出系统时偶尔看到错误提示

- 在部分版本中，退出登录时可能偶尔出现 “Missing Authorization token” 一类提示  
- 这是由于退出过程中清除登录信息时，某些后台请求正好在执行  
- **不影响退出结果，也不影响数据安全**，可以直接忽略  
- 新版本已优化退出流程，这种情况会明显减少

---

### 15.2 查询结果与其它系统不一致时怎么办？

- 确认是否使用了相同的时间范围、统计口径和筛选条件  
- 检查数据卡片是否已经刷新到最新表结构  
- 如仍有疑问，可将问题描述发给管理员或数据团队协助排查
