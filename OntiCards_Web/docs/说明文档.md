## 一、产品概述

### 1.1 什么是 OntiCards？

- OntiCards 是一个**智能数据查询系统**，让您可以用**自然语言**（就像日常说话一样）直接查询企业各类业务数据库。  
- 您不需要编写 SQL，也不需要知道“数据在哪张表、字段叫什么”，只需描述业务问题，系统会自动帮您找到数据并给出结果。

### 1.2 为什么需要这个系统？

在传统的数据查询方式中，您可能会遇到这些困扰：

- **技术门槛高**：不会 SQL，查个数据要反复找技术同事帮忙  
- **响应时间长**：从提需求到拿到数据，可能要等几小时甚至几天  
- **跨系统困难**：订单、库存、财务、门店等数据分散在不同系统中，整合非常麻烦  
- **表结构复杂**：不知道某个数据在哪张表、用什么字段名存储  
- **临时分析成本高**：每次要查点“临时问题”，都需要重新写 SQL 或改报表

**OntiCards 解决的，就是这些问题：**

- **零门槛查询**：会说话就会查数据  
- **自助式使用**：业务人员可以自己完成大部分查询  
- **跨系统统一入口**：一次提问，可以同时查多个数据库  
- **自动理解业务语义**：不需要记字段名，说“销量”“库存不足”“高价值客户”即可  
- **快速响应**：大部分查询几秒内即可得到结果

## 二、我能用它做什么？

从用户视角看，OntiCards 可以帮您：

- **快速查数据**：  
  - 今天有多少新注册用户？  
  - 本月销售额是多少？  
  - 某个商品在各个仓库的库存情况怎样？  
- **做对比和分析**：  
  - 本月与上月的销售趋势对比？  
  - 华东和华南两个区域的销售表现差异？  
  - 新老用户在客单价上的差异？  
- **跨系统整合信息**：  
  - 同时在财务系统和订单系统中存在的客户有哪些？  
  - 各个分公司/门店的经营数据，如何一键汇总？  
- **做异常监控与预警**：  
  - 库存低于安全库存的商品有哪些？  
  - 近期是否有异常交易行为或异常退货情况？  
- **提升沟通和决策效率**：  
  - 自己查到数据，现场就能完成讨论和决策  
  - 不再依赖“排队等报表”“排队等脚本”

> **简而言之**：OntiCards 可以变成您和团队的“数据助手”，随叫随到，回答各类与数据相关的问题。

## 三、核心功能与模块

本节从“用户能感知到的功能”角度，对系统的主要能力做一个总览。

### 3.1 自然语言查询

**功能说明**  
您只需要用日常语言提问，系统就能理解您的意图并返回查询结果。

**示例：**

| 您的提问 | 系统做什么 |
|---------|-----------|
| “广州仓库有哪些商品库存不足？” | 查找库存相关表，筛选广州仓库的低库存商品 |
| “最近一个月哪些商品卖得最好？” | 统计最近一个月的销售数据并按销量排序 |
| “价格低于 200 元的数码产品” | 在商品相关表中按价格和品类筛选 |

**核心价值：**
- **门槛低**：不需要学习 SQL 或专业术语  
- **表达自然**：像和同事聊天一样提问  
- **响应快**：适合日常频繁查询和临时问题

---

### 3.2 智能数据目录（数据卡片）

**功能说明**  
系统会自动为数据库中的每张表生成一份“数据卡片”（类似表的说明书），记录：

- **表的业务用途**：例如“订单明细表”“商品基础信息表”“仓库库存表”等  
- **关键字段说明**：字段代表什么含义，如“price=价格，stock=库存数量”  
- **典型值示例**：字段中常见的值，如“蓝牙耳机、充电宝”等  
- **常见查询场景**：该表常用来回答哪些问题  
- **业务关键词和别名**：例如“商品/产品/SKU”等

**对您的意义：**

- 您可以不用记住具体字段名，系统会根据这些卡片做语义理解
- 当数据库结构调整时，系统会自动刷新卡片，减少维护工作
- 对"陌生库"也能快速上手使用

---

### 3.3 数据盘点系统

**功能说明**
数据盘点帮助系统理解表与表之间的关系（如订单表和客户表通过customer_id关联），从而在多表查询时生成更准确的SQL。

**两种盘点方式：**

#### 方式一：全域盘点（自动化）
- 自动扫描数据源所有表
- 批量发现表间关系
- 支持单数据源和多数据源模式
- 自动识别跨数据源关系
- 一键完成，无需人工干预

#### 方式二：定向盘点（精细化）
- 用户选择目标表和参考表
- AI推荐字段注释
- 推断表间关系
- 用户确认后生成关系卡片
- 适合核心业务表的精细化治理

**核心价值：**
- **提升多表查询准确率20-25%**：JOIN条件更准确
- **减少错误**：显著减少笛卡尔积等常见问题
- **跨源支持**：识别跨数据源关系，支持异构数据融合
- **自动化治理**：快速建立数据资产目录

---

### 3.4 跨数据库查询与结果融合（关系卡片增强版）

**功能说明**  
对于同时分布在多个系统或多个地区数据库中的数据，OntiCards 支持一次提问、统一查询、自动整合。

**典型场景：**

- **查交集**：  
  - “在广州和深圳都有库存的商品” → 需要在两个仓库/数据库中都出现  
- **查并集**：  
  - “在广州或深圳有库存的商品” → 只要在任意一个仓库有即可  
- **做汇总**：  
  - “汇总所有仓库的商品总库存” → 需要把多地的库存相加合并  

**系统会自动完成：**

1. 找到需要参与查询的多个数据源
2. 分别执行查询
3. **利用关系卡片信息进行智能融合**（如果已完成数据盘点）
4. 根据问题语义（如"都、同时、或、汇总"等）选择合适的整合方式
5. 返回已经融合好的最终结果

**关系卡片增强效果：**
- SQL生成阶段：优先使用关系卡片中的JOIN条件，准确率提升15-20%
- 结果融合阶段：利用关系信息进行智能融合，准确率提升25%
- 跨源查询：自动识别跨数据源关系，支持异构数据融合

**核心价值：**
- **打破数据孤岛**：多个系统的数据可以同时被利用  
- **统一视图**：以业务语言看到“全局结果”，不用来回切换系统  
- **避免手工导出和拼表**：不再需要 Excel 手动合并

### 3.5 API集成能力

**功能说明**
OntiCards提供灵活的API接口，支持第三方系统和智能体平台无缝接入查询功能。

**两种认证方式：**

#### 方式一：传统登录态认证
- 适用于Web前端和内部系统
- 基于Session/Cookie认证
- 需要用户登录

#### 方式二：API Key认证
- 适用于第三方集成、智能体平台、API调用
- 无需登录态，直接通过API Key认证
- 支持三种格式：Authorization、Bearer Token、X-API-Key
- 支持状态管理（active/disabled）和过期控制

**核心价值：**
- **简化集成**：无需处理复杂的登录流程
- **安全隔离**：每个API Key绑定特定用户，严格的数据隔离
- **灵活管理**：支持多个API Key，便于不同系统独立管理
- **完整功能**：与登录态体系功能完全一致

**典型应用场景：**
- 智能体平台接入（如Dify、Coze等）
- RPA系统集成
- 数据分析工具对接
- 第三方应用调用

### 3.6 SSO单点登录（SSO）

**功能说明**
OntiCards支持SSO（Single Sign-On，单点登录）功能，允许企业用户通过统一的身份认证系统登录OntiCards，实现一次登录、多系统通行。

**JWT Token模式（推荐）**

该模式适用于已建立自己用户体系的企业系统，通过JWT Token实现与OntiCards的免登录对接。

**核心特点：**
- **安全认证**：使用HMAC-SHA256算法对JWT Token签名，确保传输安全
- **自动用户管理**：首次SSO登录时自动创建用户，后续登录自动关联
- **灵活配置**：支持配置回调地址，满足不同前端集成需求
- **完整对接**：提供Token生成指南、多语言示例代码、测试工具

**工作流程：**
```
1. 企业系统验证用户身份
2. 企业后端生成JWT Token（包含username、user_id等用户信息）
3. 拼接SSO登录URL：{OntiCards API地址}/sso/login?token={JWT Token}&redirect_url={回调地址}
4. 用户浏览器跳转到SSO接口
5. OntiCards验证JWT签名和有效期
6. 创建/关联用户，生成平台Token
7. 跳转到回调地址，携带access_token
8. 前端接收Token，完成登录
```

**JWT Token必填字段：**

| 字段 | 类型 | 说明 |
|------|------|------|
| username | string | 用户的唯一标识，必填 |
| user_id | string | 用户在企业系统中的ID，必填 |
| exp | number | Token过期时间（Unix时间戳），必填，建议5分钟内 |

**JWT Token可选字段：**

| 字段 | 类型 | 说明 |
|------|------|------|
| nickname | string | 用户昵称 |
| email | string | 用户邮箱 |
| source | string | 来源标识，区分不同系统，默认default |
| iat | number | Token签发时间 |

**安全机制：**
- Token有效期限制（建议5分钟），防止Token泄露风险
- HMAC-SHA256签名验证，防止Token篡改
- 用户级数据隔离，SSO用户与其他用户数据隔离
- 完整的登录审计日志

**适用场景：**
- 企业已部署统一身份认证平台
- 需要与现有企业系统（如钉钉、企业微信、飞书等）集成
- 希望员工使用企业邮箱/工号登录，无需单独管理OntiCards账号

**核心价值：**
- **统一身份管理**：员工使用企业统一账号，简化账号管理
- **提升安全性**：集中管控登录入口，减少密码泄露风险
- **改善用户体验**：一次登录，多系统通行
- **降低运维成本**：无需单独维护OntiCards账号体系

### 3.7 智能容错与友好提示

**功能说明**  
现实中，用户的提问不一定完全“严谨”，可能：
- 使用了数据库里不存在的字段  
- 混用了几个不同系统中的口径  
- 条件过于复杂或不完整

OntiCards 会尽量“听懂”并给出可用结果，而不会轻易报错。

**主要策略：**

1. **自动降级**：某些条件暂时无法满足时，会先执行其它可以满足的条件  
2. **清晰提示**：在结果中说明哪些条件被忽略，以及原因  
3. **保留可用结果**：优先给出部分有价值的数据，而不是一条“错误信息”

**示例：**

> 提问：**“查询价格低于 100 且好评率高于 90% 的商品”**  
> 如果当前商品表中没有“好评率”字段：  
> - 系统会执行“价格低于 100”的筛选  
> - 并在结果中提示：**“已忽略条件：好评率（字段不存在）”**

**对您的好处：**
- 不必担心“一句没问准就直接报错”  
- 可以快速通过结果和提示，调整提问方式

### 3.8 多数据源统一管理

**功能说明**  
OntiCards 支持连接和管理多个不同类型的数据库，例如：
- Oracle、MySQL、PostgreSQL、SQL Server、SQLite、Trino、**电科金仓（KingBase，原名：人大金仓）**、**OceanBase（MySQL 租户模式）**、**达梦（DMBase）** 等
> **💡 TIP**：OceanBase 原生提供 MySQL 与 Oracle 双兼容模式，当前已支持 **MySQL 租户模式**；**Oracle 租户模式将在后续版本中支持**。

在一个界面中，您可以：

- **添加数据源**：填写连接信息，一键接入  
- **测试连接**：确认数据库是否可正常访问  
- **刷新结构**：数据库结构变化后重新识别更新  
- **删除数据源**：不再需要时安全移除

**核心价值：**

- 所有数据源在一个系统中集中管理，避免“系统越多越乱”  
- 根据业务发展随时扩展新的数据源
- 为后续的统一查询和分析打好基础

### 3.9 业务术语库管理

**功能说明**
业务术语库帮助系统理解企业特有的业务术语，实现业务语言的标准化查询。

**核心概念：**

- **术语库**：按业务领域分类，如"销售术语库"、"库存术语库"
- **术语**：每个业务术语的名称、定义、同义词、关联字段
- **术语模板**：包含多个术语组合的标准查询

**典型应用场景：**

| 用户提问 | 系统理解 |
|---------|---------|
| "查询高价值客户的订单" | 高价值客户 → VIP等级='钻石' 且 累计消费>10000 |
| "核心商品的库存情况" | 核心商品 → 产品分类 IN ('A类', 'B类') |

**术语识别与重写流程：**

1. 用户提交包含业务术语的查询
2. 系统自动识别提问中的业务术语
3. 将术语展开为对应的字段条件和值
4. 生成语义更明确的问题供SQL生成
5. 返回结果中展示匹配的术语信息

**核心价值：**
- **统一业务语言**：不同部门使用同一套术语标准
- **消除歧义**：业务术语自动映射到精确字段条件
- **提升准确率**：减少因理解偏差导致的查询错误
- **知识沉淀**：建立企业级业务术语资产

### 3.10 历史会话查询

**功能说明**
历史会话查询功能完整记录每一次用户查询的详细信息，支持回溯和分析。

**记录内容**
- **查询明细**：用户问题、生成的SQL、涉及的数据源
- **性能指标**：总耗时、各环节耗时（向量检索、重排序、SQL执行等）
- **Token消耗**：Embedding、Rerank、LLM输入/输出Token数量
- **查询质量**：召回卡片数、精选卡片数，重排序分数等

**使用场景**
- 查看历史查询：了解之前的查询内容和结果
- 问题复现：重新执行之前的查询
- 数据追溯：查看特定时间段内的查询记录
- 跨数据源查询同步：在跨数据源查询场景下，历史记录会自动同步到被涉及的数据源中，方便从任意数据源追溯完整的跨库查询

### 3.11 监控中心

**功能说明**
监控中心提供全面的系统使用监控和分析功能。

**核心功能**

1. **监控总览**
   - 实时统计：最近24小时和今日的查询量
   - 成功率统计：成功/失败/超时次数
   - Token消耗：各类Token使用量统计
   - 成本预估：基于Token价格计算预估成本

2. **趋势分析**
   - 每日趋势：展示最近30天的查询量变化
   - 对比分析：与昨日、上周同期对比
   - 周规律：工作日和周末的查询分布

3. **性能分析**
   - 各环节耗时：向量检索、重排序、SQL生成、SQL执行
   - 慢查询TOP：耗时最长的查询记录
   - 数据源性能：各数据源响应时间对比

**⚠️ 成本说明**
成本为预估值，实际费用以云厂商账单为准。

### 3.12 成本配置

**功能说明**
管理员可以配置Token价格，用于成本预估计算。

**配置项**

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| Embedding价格 | 0.0007元/千token | 向量检索成本 |
| Rerank价格 | 0.002元/千token | 重排序成本 |
| LLM输入价格 | 0.002元/千token | SQL生成输入成本 |
| LLM输出价格 | 0.006元/千token | SQL生成输出成本 |

**成本计算**

```
预估成本 = Embedding Token数/1000 × Embedding价格
        + Rerank Token数/1000 × Rerank价格
        + LLM输入Token数/1000 × LLM输入价格
        + LLM输出Token数/1000 × LLM输出价格
```

### 3.13 数据保留策略

**功能说明**
系统支持配置历史数据的保留天数，避免数据无限增长。

**配置项**

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| 查询日志保留 | 180天 | 历史查询明细保留时间 |

### 3.14 数据治理模块 - 数据质检（第一阶段）

OntiCards 提供了完善的数据治理能力，帮助企业建立数据质量保障体系。数据治理分为两个阶段：**第一阶段为数据质检**（当前功能），**第二阶段为实际治理**（规划中）。本章节详细介绍第一阶段"数据质检"的完整功能和价值。

#### 14.1 什么是数据治理

数据治理是企业数据管理的重要组成部分，旨在建立数据质量标准、监控数据质量状况、发现并解决数据问题。OntiCards 的数据治理模块帮助企业实现：

- **数据标准化**：建立统一的规则库，规范数据质量标准
- **质量监控**：持续监控数据质量状况，及时发现质量问题
- **问题追溯**：定位数据问题的根源，指导数据修复
- **持续改进**：通过质量报告分析，推动数据质量不断提升

**两阶段设计理念：**

数据治理分为两个阶段，形成完整的数据质量保障闭环：

| 阶段 | 名称 | 状态 | 说明 |
|------|------|------|------|
| 第一阶段 | 数据质检 | **已完成** | 检查数据问题、生成质量报告 |
| 第二阶段 | 实际治理 | 规划中 | 修复数据问题、对账核对、告警通知 |

**第一阶段（数据质检）完整链路：**

```
规则库构建 → 规则创建 → 规则执行 → 报告生成
    ↑            ↑          ↑           ↓
    └────────────┴──────────┴───────────┘
              持续迭代优化
```

#### 14.2 数据质检模块概述

数据质检模块提供两种检测模式，满足不同的质检需求：

**模式一：基于规则库的质检**

通过自定义质检规则，对数据进行系统性检查。适合有明确质量标准的数据检测场景。

- **规则库管理**：按业务领域或数据类型创建规则库

- **多类型规则支持**：非空检查、唯一性检查、格式校验、范围检查、枚举值检查、正则匹配等

**模式二：基础空值检测**

自动扫描数据库中各表的空值情况，快速发现数据完整性问题。适合快速了解数据健康状况。

- **自动扫描**：无需配置，系统自动扫描所有表的空值情况
- **统计全面**：统计每个字段的空值率，帮助定位问题
- **快速上手**：一键执行，即刻了解数据完整性

**统一体验**

两种模式的执行明细统一存储，形成完整的质量检测记录，便于：
- 后续数据治理阶段的实施，提供可追溯的检测历史
- 统一查看和管理所有质检结果
- 质量趋势分析，了解数据质量变化

**方式一：模板模式（推荐新手）**

**方式二：AI自然语言模式（推荐）**

**典型示例：**

| 您说的话 | 系统理解的规则 |

#### 14.6 规则执行

规则执行是数据质检的核心环节，系统会批量执行配置的规则并收集结果。

> **执行质检的重要注意事项**
>
> 1. **数据静态性要求**：如果要使用质检功能，最好确保业务系统数据库（数据源或数据空间中的相关数据库表）中没有实时数据中途更新，否则会影响质检结果。质检过程中针对的数据范围是静态数据场景，请合理安排执行时间。
>
> 2. **执行时间建议**：质检执行可能消耗一定数据库资源，建议在业务低峰期执行大规模质检。

**执行过程：**

1. **规则选择**
   - 可按规则库批量执行
   - 也可指定具体规则执行

2. **自动检测**
   - 系统自动对每条规则生成对应的检测SQL
   - 在目标数据库上执行检测
   - 统计通过数量和失败数量

3. **结果采集**
   - 记录总数据量、通过量、失败量
   - 计算失败率和通过率
   - 采集违规数据的样本供分析

4. **评分计算**
   - 基于通过率和失败严重程度计算质量评分
   - 量化评估数据质量水平

**两种质检模式：**

1. **基于规则库的质检**
   - 批量执行配置的质检规则
   - 自动收集检测结果（通过/失败数量、失败率）
   - 计算质量评分和等级

2. **基础空值检测**
   - 自动扫描所有表的空值情况
   - 统计每个字段的空值率
   - 帮助发现数据完整性问题

**质量评分体系：**

| 等级 | 评分范围 | 说明 |
|------|---------|------|
| 优秀 | ≥95分 | 数据质量非常好，值得信赖 |
| 良好 | ≥85分 | 数据质量良好，可以正常使用 |
| 一般 | ≥70分 | 数据质量一般，存在改进空间 |
| 较差 | ≥60分 | 数据质量问题较多，需要关注 |
| 差 | <60分 | 数据质量存在严重问题 |

**用户价值：**
- 一键执行批量质检规则，无需逐条检查
- 实时获取质量评分和等级，直观了解数据状况

## 五、系统工作原理

本节不讲具体技术，只用类比和流程，让您了解系统“脑子里在想什么”。

### 5.1 从提问到结果的 7 个步骤

当您输入一个问题时，系统大致会经历以下步骤：

1. **理解问题**  
   - 把您的自然语言问题拆分为“想查什么 + 在什么条件下 + 以什么口径展示”等信息  
   - 类比：像一个助手先把您的口头需求整理成要点

2. **在数据卡片中找表**  
   - 到所有数据卡片中，寻找可能存放这些数据的表  
   - 类比：在图书馆里，根据书的简介而不是书名来找书

3. **筛选最合适的数据表**  
   - 在候选表中，选出最能回答问题的那几张表  
   - 类比：把最有可能的几本书放到桌面上准备参考

4. **设计“查询方案”**  
   - 决定需要关联哪些表、用哪些字段、按什么条件筛选、如何统计和排序  
   - 类比：先写出“查询思路”的提纲

5. **生成数据库查询语句（SQL）**  
   - 根据上面的“查询方案”自动生成具体的查询语句  
   - 类比：秘书根据提纲写出一份正式的文件

6. **安全检查并执行查询**  
   - 确认只做“查”的操作，不涉及增删改  
   - 确认访问的都是允许访问的表和字段  
   - 然后去各个数据库执行查询

7. **整理并返回结果**  
   - 把查询结果整理成表格  
   - 标注数据来源  
   - 用自然语言解释“本次是如何理解并执行您的问题的”

---

### 5.2 为什么它能听懂业务语言？

关键在于**智能数据卡片**：

- 传统的数据字典只记录字段名和类型，例如：  
  - 字段：price  
  - 类型：DECIMAL  
- 但 OntiCards 的数据卡片会记录更多业务信息，例如：  
  - “price” 表示价格，单位为“元”  
  - 典型取值范围  
  - 相关词汇：价格、单价、售价、价位  
  - 常见使用场景：价格筛选、区间统计、排序等

这样，当您说：
- “单价低于 100 的商品” → 系统会理解“单价”就是“price”  
- “无线产品的库存” → 系统会联想到数据卡片里列出的“蓝牙耳机、无线鼠标、蓝牙音箱”等具体商品

> 您不需要记住字段名，只需用熟悉的业务词汇描述问题即可。

---

### 5.3 跨数据库查询是怎么完成的？

以问题“在广州和深圳都有库存的商品”为例：

1. 系统识别到：  
   - 需要查询两个地方（广州、深圳）的库存数据  
   - 关键词“都有”代表希望取交集（两地都存在）
2. 分别在“广州数据库”和“深圳数据库”中，查出有库存的商品列表  
3. 对两个列表按商品编号取交集，找出“两个地方都出现的商品”  
4. 再补充每个商品的库存数量和名称，展示给您

类似地，当您使用“或、任一、汇总、合并”等字眼时，系统会自动选择不同的结果融合方式。

## 七、数据安全保障

OntiCards 在设计之初就把“数据安全”放在首位，从以下几个方面保障您的数据安全：

### 7.1 访问权限与用户隔离

- 每个用户只能访问自己添加的数据源，互相之间的数据完全隔离  
- 即使两位用户连接了同一套业务数据库，在系统中看到的也只是“自己添加的数据源”  
- 支持按角色控制权限：普通用户仅能查询数据，管理员可以管理数据源和查询记录

---

### 7.2 严格的只读查询

- 系统只允许执行查询（SELECT）操作  
- 明确禁止：新增、修改、删除数据以及修改表结构等操作  
- 不提供“写入入口”，最大程度避免误操作风险

---

### 7.3 连接信息保护

- 数据库密码加密存储，即便存储介质泄露，也无法直接看到明文密码  
- 在界面中不展示数据库密码  
- 在日志和错误提示中，对可能包含连接信息的内容做脱敏处理

---

### 7.4 审计和异常监控

- 记录每一次查询：谁、什么时候、问了什么、访问了哪些表、是否成功  
- 对频繁的异常行为做监控，如短时间内大量失败查询、尝试访问未授权表等  
- 管理员可以根据日志进行审计、排查问题和风险

> 总结一句：OntiCards 只帮您“看数据”，不会在您的业务库里“动数据”。

## 九、常见疑问

### Q1：系统会不会理解错我的问题？

系统采用了智能语义理解能力，大多数日常问题都能较为准确地理解。  
如果理解有偏差，您可以：

1. 在结果中查看“查询说明”，看看系统是如何理解您的问题的  
2. 调整表达方式，使问题更具体或更明确  
3. 换一种业务说法再次提问，例如加上时间、地区、对象等限定

---

### Q2：系统能处理多复杂的查询？

系统适合大多数日常业务查询，例如：

- 简单筛选：价格低于某值、库存不足、时间范围筛选等  
- 聚合统计：按地区、门店、品类等维度做汇总  
- 多表关联：如订单 + 订单明细 + 商品信息  
- 跨数据库查询：汇总多个仓库或多个系统的数据

对于极其复杂、需要嵌套多层逻辑或复杂数学计算的场景，建议拆成几步，用多次查询实现。

---

### Q3：如果数据库结构变了，需要做什么？

当出现以下情况时，建议在系统中执行“刷新数据源”：

- 数据库新增了表  
- 表中字段有明显变化（新增、删除、重命名）  
- 某张表的业务含义发生了变化

刷新后，系统会自动：

1. 识别发生变化的表  
2. 更新对应的数据卡片  
3. 让后续查询自动适配到新的结构

---

### Q4：系统会不会泄露我的数据？

不会。系统在多个层面进行保护：

- 数据库密码加密存储  
- 用户之间数据隔离  
- 只允许只读查询，不提供修改、删除入口  
- 查询操作有审计记录，便于追踪和核查  
- 业务数据始终保留在您的业务数据库中，系统只在查询时临时访问

---

### Q5：和 BI 工具有什么区别？可以一起用吗？

**BI 工具（如 Tableau、Power BI 等）**：
- 长于固定报表和可视化仪表盘  
- 适合已定义好指标、维度的场景  
- 需要提前做数据建模和配置

**OntiCards**：
- 长于临时查询和探索性分析  
- 不需要提前配置模型，即问即答  
- 适合经常需要“临时追问细节”的场景

二者是**互补关系**：  
- 用 BI 做固定报表和长期监控  
- 用 OntiCards 解决临时问题和深挖细节
